## Problem And Evidence
- Behavior to improve: the **creator of any newly created group cannot send anything, ever** — first text send fails in ~64 ms with the false per-message reason "Couldn't send — you're no longer in this group", the banner "You were removed from this group. You can still read past messages.", and a locked composer. Live-confirmed: invitee acceptance does NOT heal it (a `member_joined` event releases the latch via `_loadSecurityStatus`, the user resends, the send re-fails and re-latches); the invitee CAN send (asymmetry explained below). Reaction-remove in the same state also falsely latches "removed"; reaction-add silently flickers; media/voice sends are a silent dead button.
- Impact: every plain group created on a post-`8d86501e4` build is unusable for its creator from birth, with no user-reachable recovery (the only authority-writing entry point, QR device-link, is compiled out: `kDirectLinkedDevicesEnabled` off). Both of the user's live groups are bricked this way.
- Confirmed root cause (Defect 1 — survived the refute pass): a **predicate mismatch between the plan-363/364 wave's meaning of "initialized" and the code's test for it**.
  - `createGroupWithMembers` stamps a **self-bound** `GroupMemberDeviceIdentity` (deviceId == transportPeerId == account peerId — informationally identical to `GroupMember.legacyDeviceIdentity`) on the creator's own member row: `create_group_with_members_use_case.dart:220-239` (since `4a7675cb0`, 2026-05-25; added only so the members_added signed-audit/publish/invites carry sender-device fields).
  - `8d86501e4` (2026-08-15) unconditionally installs `buildProtectedGroupContentAuthoringResolver` in `production_application_bootstrap.dart:8348` (inside `_prepareNormalApplication`, no gate). Resolver ladder (`protected_group_content_authoring_resolver.dart:50-133`): devices non-empty ⇒ requires a settled authority proof; `loadLatestSettledProtectedContentAuthority` (bootstrap `:8213-8280`) finds none (plain creation appends ONLY `group_created` to `group_event_log` — device-log-proven) ⇒ `refuse` at `:79-81`.
  - `send_group_message_use_case.dart:2358-2367`: `kind == refuse` (or devices-non-empty + resolver-installed + kind != strict) ⇒ `SendGroupMessageResult.unauthorized`, reason `strict_group_content_authority_unavailable`.
  - Plan 364:96 states the contract: strict custody is selected by a "**Plan-363-initialized explicit self-device roster**"; "only an **uninitialized ordinary-primary** group retains incumbent behavior byte-for-byte". The code's initialized test is `devices.isNotEmpty` (`:2350`, resolver `:66`), which the self-bound creator stamp trips; the wave's authoring gates use the narrower `hasProtectedGroupPhysicalAuthority` (`protected_group_authority.dart:245-255` — a device is initializing only when `deviceId != member.peerId || transportPeerId != member.peerId`), which the same stamp does NOT trip. The stamp satisfies neither wave's precondition nor carries information `legacyDeviceIdentity` lacks; it exists only to break the tripwire.
  - Asymmetry proof: invitee rows are created device-less (production passes no `selectedContactDeviceBindings`; `create_group_picker_wired.dart:197-209`), the join path never stamps self (`handle_incoming_group_invite_use_case.dart:1097-1102`), so the joiner resolves `legacyUninitialized` → legacy lane → sends fine. `devices empty` is a stable plain-group invariant for every row EXCEPT the creator's own — the stamp is the sole violator.
- Confirmed root cause (Defect 2): the UI equates `unauthorized` with membership loss. `_terminalReadOnlyForSendResult` (`group_conversation_wired.dart:7130-7143`) maps ANY `unauthorized` → `_TerminalReadOnly.removed` (banner + per-bubble reason + hidden composer, `group_conversation_screen.dart:320`). Plan 144:37 defined `unauthorized` as "(you were removed / lost membership)" against four membership-read producers; plan 259:51/:249 audited exactly one non-removal producer (`roster_unavailable`) and accepted it as "rare, transient, self-healing" with "behavior work" deferred and **no successor owner**. The `strict_group_content_*` producers added by the 363-366 wave violate all three acceptance predicates (deterministic, every plain-group send, never self-healing). Reaction lanes are worse: remove-refusal collapses to `RemoveGroupReactionResult.notMember` (`remove_group_reaction_use_case.dart:162-167`) → false removed latch at `group_conversation_wired.dart:7692-7696`; add-refusal (`SendGroupReactionResult.unauthorizedSenderKey`) silently flickers.
- Existing coverage: `send_group_message_use_case_test.dart:1039` 'TC-364-01a…' locks refuse-⇒-all-zero for an initialized roster AND legacy success for the empty-devices ordinary primary (`:1792-1842`); `group_conversation_wired_test.dart:6273` locks genuine role-based unauthorized → removed banner; `:6667` locks remount reconstruction for a genuinely-removed membership.
