## real scope

The Move Account feature is correct at small scale (the chained E2E moves a ~12–14 MB account byte-identically) but its architecture assumes the whole account fits in memory several times over. Three compounding issues:

- **C1 — sender materializes the whole account in RAM.** `AccountMigrationProductionBundleSource.call()` reads every media file (`_buildFilePayload`, `account_migration_bundle_transfer.dart:286-406`, `readAsBytes` at :329) and the full DB snapshot (`readAsBytes` at :196) into RAM, base64s everything into one JSON document (`_AccountMigrationBundlePayload.toJson` :1584-1602, canonical-JSON utf8 encode :205-207), splits it (`_splitSegments` :1455-1466, `segmentSize = 256 * 1024` default at :71), and ML-KEM-encrypts **all** segments up front (`_buildEncryptedTransferBundle` :1393-1453, phase `encryptSegments` :209-215) before the first byte moves. Peak ≈ 4–6× account size on the main isolate.
- **C2 — receiver re-inflates the whole document at complete().** Segments stream to disk per-arrival (`acceptSegment` :981-1020, write at :1015-1017), but `complete()` (:1022-1087) concatenates every `<index>.bin` back into one buffer, utf8-decodes and jsonDecodes it (`_readBundlePayload` :1304-1332), then base64-decodes the full DB plus every file into coexisting byte arrays (`fromJson` :1541-1582). Peak ≈ 2.7–3.7×. On a 4 GB phone this is the first wall; failure shape is the worst possible: minutes of successful transfer, then jetsam at "complete," and retry restarts from zero (the checkpoint store is wired at `main.dart:1539-1545` but its only writer `importSegments` has no production caller — functionally dead).
- **C3 — the wire is slow at scale.** Strictly sequential POSTs, a fresh `HttpClient` per segment (`_postJson`, `account_migration_local_transfer_runtime.dart:1484`, force-closed :1548), one full ML-KEM-768 encapsulate/decapsulate + two bridge round-trips per 256 KiB segment (`migration_segment_crypto.dart:90-139` → `message.encrypt`; Go `crypto/encrypt.go:49` encapsulates inside every call). Measured ~6 s/MB → a 1 GB account is hours of foreground transfer with no resume. Receiver disk amplification ≈ 2.4× with no cleanup (session staging dir is never deleted in production; `MigrationFileImportCleanup`/`MigrationDatabaseImportCleanup` are dead code).

Root cause: the bundle is one atomic JSON document instead of a stream of independently verifiable entries. That single decision forces whole-payload materialization on both ends and blocks resumability.

Three phases, cheapest first:

- **Phase 0 — stop crashing, start measuring.** Wire the dead `MigrationStoragePreflight` into the receiver manifest path, add a sender-side account-size estimate + explicit cap at the QR/confirm stage (typed "too large to move" instead of jetsam), and build a synthetic-account device benchmark (200/500/1000 MB) to replace the estimated ceiling with a measured cap.
- **Phase 1 — transport efficiency, no protocol change.** One keep-alive `HttpClient` per transfer session; raise the default segment size 256 KiB → 1 MiB. (The session-KEM change originally sketched for Phase 1 *does* change the encrypted-segment wire shape, so it is folded into Phase 2's protocol bump as "1b".)
- **Phase 2 — entry-streamed bundle, protocol v2 (the real fix).** Manifest-first, entry-addressed stream: per-entry size+sha256 in the manifest; sender streams each entry from disk in ~1 MiB chunks under one session-derived AEAD key (chunked-AEAD/secretstream pattern, counter nonces, real GCM AAD); receiver decrypts chunk-on-arrival straight to the entry's staging path with incremental sha256; `complete()` shrinks to a ledger check; resume falls out as (entry, offset). O(1-chunk) memory both ends.

Out of scope for all phases: relay/cloud fallback, QR pairing changes, cutover authority semantics (MIG-008/MIG-009), the group-media durability bug (MIG-012), old-phone quiesce redesign, and platform background-service work beyond the existing wake locks.

## closure bar

- **Phase 0:** an account larger than the cap is blocked at the confirm stage with "This account is too large to move (X MB of Y MB max)" — never a mid-transfer OOM; a receiver without enough free disk rejects the manifest typed before any segment is sent; and the cap value is a *measured* number from the device benchmark, not an estimate.
- **Phase 1:** a transfer of the realistic E2E fixture completes with ≤ a handful of TCP connections instead of one per segment, and segment count drops ~4× — with zero change to manifest/payload schema and all existing move-feature gates green.
- **Phase 2:** a generated 100 MB account moves end-to-end on host with bounded memory (RSS delta far below account size on both ends), an interrupted transfer resumes from (entry, offset) instead of restarting, disk amplification during import is ~1× (rename, not copy), staging is cleaned up after cutover, and all existing E2E assertions (byte-identical files, relay-free audits, quiesce/cutover ordering, secret promotion) carry over unchanged.

## exact problem statement

A real account (phone full of photos, hundreds of MB to GBs) cannot move today:

- Sender peak RAM ≈ 4–6× account size at the `encryptSegments` stage (`bundle_transfer.dart:209-215`) → OOM/ANR on the old phone for large accounts, identical on every retry.
- Receiver peak RAM ≈ 2.7–3.7× at `complete()` (`bundle_transfer.dart:1304-1332`, :1541-1582) → jetsam *after* a long successful transfer; no resume, restart from segment 0.
- Throughput ~6 s/MB measured (one TCP connect + one KEM + two bridge round-trips per 256 KiB, all sequential) → 1 GB ≈ hours of screen-on foreground time.
- No preflight: neither phone checks disk space or account size before starting (`MigrationStoragePreflight` exists at `migration_storage_preflight.dart:35-77` with **zero production callers**, and even its accounting ignores the DB snapshot, base64 expansion, and staging amplification).
- ~2.4× receiver disk amplification (plaintext segment `.bin`s + staged DB + final copies) and the session dir is never deleted — plaintext-adjacent residue persists after a successful move.

Must stay unchanged across all phases: relay-free policy (no relay media fetch on either side), QR pairing/auth transcript semantics, cutover authority states and migrated-out network gates, the typed `localTransferTimedOut` classification and telemetry contracts, and the group-media durability regression coverage.

## risks and edge cases

- **Nonce reuse** is the catastrophic failure of chunked AEAD: counter nonces must be scoped per session key and unique across entries *and* resume attempts (fresh key per attempt sidesteps cross-attempt reuse — P2-2/P2-7 must pin this).
- **Truncation attacks**: without an `isFinal` flag in the AAD, an attacker (or a bug) can silently drop trailing chunks; P2-2's truncated-final test is mandatory, not optional.
- **Resume vs tampering**: the ledger stores plaintext hashes/offsets; resumed bytes are re-verified by the incremental entry hash, so a corrupted partial fails the entry, not the account.
- **Rename across volumes** silently degrades to copy; staging must live on the same volume as `documentsRootPath` (it does today — both under app documents) and P2-6 should assert the staging root choice.
- **RSS assertions are inherently noisy** on host: use generous bounds, sample at stage boundaries, and treat the device benchmark as the authoritative memory evidence.
- **Keep-alive client vs server idle timeouts**: a reused connection dying between segments must re-resolve into the typed timeout path (P1-1 covers the kill case).
- **1 MiB segments raise per-request receiver materialization** (`_readJsonTimed` reads the whole body) — acceptable at 1.33 MB/request, but do not raise segment size beyond ~4 MiB while bodies are JSON-in-RAM.
- **Estimate drift**: the account can grow between estimate (confirm stage) and manifest build; the receiver preflight re-checks against actual manifest totals, so the cap is advisory-accurate, the preflight is the hard gate.
- **Backward compatibility**: there is no mixed-version support by design — both phones must run the same build; P2-1 makes the failure typed and the copy actionable.
- Sensitive-data policy unchanged: no ciphertext, keys, nonces, file contents, or absolute paths in telemetry; new events carry counts/sizes/ids only.
