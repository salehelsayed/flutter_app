## Problem And Evidence

- Behavior to improve: a newly authored protected or View Once direct-media initial must durably own both its encrypted blob and its exact encrypted message envelope before either network path can become the only copy. It must survive node-off, crash/restart, sender-open races, receiver restart, and explicit private download without degrading to a proof-less upload or destructive inbox path.
- User impact: the current private flow durably saves a private parent and pending plaintext, but it is explicitly excluded from Plan 347 strict blob selection and Plan 342 v108 custody. Blob LAN/legacy relay upload happens before v111 authority, the private handoff persists only `wire_envelope`, and a live delivery may cancel the legacy inbox hedge. A crash or terminal private-media transition can therefore remove the only resumable bytes/key before exact inbox/blob custody has transferred.
- Shared policy: protected and View Once use the same `isOutgoingPrivateOneMoreLook` predicate, private pending/completion coordinator, envelope handoff, transfer registry, media lifecycle lock, and cleanup owner. Splitting them would repeat the same storage/network boundaries. The producer matrix is nevertheless exact: Protected permits one image or video; View Once permits one image only. View-Once video and GIF remain pre-network refusals for newly authored sends.
- Existing durable authority to reuse: the current private parent plus its single convention-owned pending attachment is the preparation owner; v111 owns exact ciphertext/proof; v108 owns the immutable initial envelope; the existing private lifecycle state is the only reveal/consume/cleanup authority. Physical v108/v111 rows are policy-neutral and have no FK, so their obligations can survive private parent/attachment cleanup. No v112, new table, new outbox, or new scheduler is needed.
- Do not widen v110: `direct_media_custody_intent_id` is deliberately ordinary-only in composer, send, repository, and retry. Private already has a stronger dedicated pending/completion CAS. Minting v110 for private would create a second preparation owner and broaden Plans 345/347 unnecessarily.
- Sender exclusion: `conversation_wired.dart` requires `privateTransferLease == null` before selecting strict blob custody, so protected/View Once still call the legacy upload path. `send_chat_message_use_case.dart` explicitly excludes `isOutgoingPrivateOneMoreLook` from v108 ownership and protected store selection; `_commitOutgoingDirectPrivateEnvelopeForTransport` commits only the envelope.
- Retry exclusion: prepared-v111 reopen requires an ordinary v110 intent. Existing protected/View Once failed/incomplete retry therefore rearms private state and uses legacy upload/re-encryption instead of reopening the exact v111 artifact. The generic unacked path already suppresses any exact v108 owner and needs preservation evidence, not a new Plan-354 branch.
- Receiver exclusion: strict media parsing, repository conversion, and `dbStageIncomingDirectMediaBlobCustody` reject every redacted policy. Private receive therefore persists parent and attachment separately before its delivery receipt. `downloadMedia` selects the private legacy path before the strict v111 owner, and the strict local-path commit accepts ordinary parents only.
- Completion/restart mismatch: a newly stored strict result still points at the convention-pending plaintext path, while the private completion CAS accepts only the canonical private path. Failed/incomplete restart also loses the process completion token. Exact v111 reopen must therefore reuse the existing private-owned no-network canonicalization and `OutgoingDirectPrivateMutationCoordinator.commitCompletion` before Barrier B; it must preserve the strict key/nonce/hash/commitment instead of reminting them.
- Lifecycle hazard: private consume/hide/delete cleanup owns plaintext, secure key, and attachment deletion, while v111 owns ciphertext and ACK/expiry. The shared lifecycle lock and current unhanded-off private retention rules must serialize the two without upgrading an attachment lock to the message-wide lock. At prepared/stored pre-v108 crash cuts, terminal cleanup must first retain the complete attachment/key/plaintext/ciphertext projection; the existing global blob drain may then terminalize v111, and a later private cleanup pass may remove the private assets. It may never leave an unreopenable live generation.
- Receiver terminal replay hazard: View Once consumption can legitimately remove the attachment/key while a no-FK v111 obligation survives. An authenticated replay after a durable consumed/hidden/deleted parent must never recreate the parent, attachment, display marker, or notification. Full descriptor/key equality is provable only while that attachment authority exists; a zero-effect terminal replay instead requires the durable same-author/private-policy parent and, when v111 survives, the exact attachment ID plus public custody commitment. A physically absent parent with only v111 cannot prove original author/policy and therefore fails closed with no receipt until v111 expiry.
- Recovery-download hazard: the network drain currently calls the strict download owner directly for every nonexpired `incomingCommitted` row, bypassing private explicit-intent policy. The ordinary strict download also writes timestamped ciphertext/decrypt candidates outside the private cleanup inventory. Plan 354 must retain private committed rows without automatic network work and use deterministic private-owned staging siblings for an explicit download.
- Refuted alternatives: a separate protected and View-Once plan, v110 expansion, a new private blob table, a second lifecycle lock, a private retry queue, a new relay custody kind, and a second strict network caller are all unnecessary. Simply removing `privateTransferLease == null` is also insufficient because the repository, DB, send, retry, receive, and download predicates remain ordinary-only.
- Expected production surface: existing Dart seams only: `media_attachments_db_helpers.dart`, `messages_db_helpers.dart`, `media_attachment_repository.dart`, `message_repository.dart`, their two implementations, `prepared_direct_media_blob_custody_coordinator.dart`, `conversation_wired.dart`, `send_chat_message_use_case.dart`, failed/incomplete retry, `delete_message_use_case.dart` for lock-owned private hide, `handle_incoming_chat_message_use_case.dart`, `chat_message_listener.dart` for a terminal-supersession disposition that cannot trigger global display retry, `download_media_use_case.dart`, `strict_direct_media_blob_download_ack_owner.dart`, `direct_private_media_lifecycle.dart`, `private_media_lifecycle_engine.dart` only if lock orchestration must move, `drain_direct_media_blob_custody_use_case.dart`, and production bootstrap closures. `retry_unacked_messages_use_case.dart` is preservation-only. Stop and re-review if this requires a new durable type or native/protocol surface.

## Scope Contract And Guard

In scope:

- Newly authored direct one-to-one private-media initials only: v1 Protected with exactly one image or video, and v1 View Once with exactly one image. Preserve current no-text/caption, no-edit, no-forward eligibility and all current contact/identity/path/size/key checks. Disappearing, GIF, View-Once video, audio/voice, file, multiple attachments, and malformed/unsupported policy refuse before encryption, durable strict publication, or network.
- Keep the durable private parent plus exact convention-pending attachment as the sole pre-v111 preparation authority. Do not mint or infer a v110 intent. Requalify the current parent, contact, attachment identity/path/status, private policy, lifecycle state, transfer ownership, and raw key projection under the existing shared media lifecycle lock.
- Add one narrow private entry to the existing prepared blob coordinator and one private-specific repository/DB staging capability over physical v111. It accepts only the exact current private pending projection, writes the prepared attachment encryption metadata/secure-key reference and one exact v111 row atomically, compensates any losing raw-key write, and preserves every private parent/lifecycle column. Exact winner adoption precedes shared capacity checks; crossed key/hash/path/policy/state/custody bytes refuse all-or-zero.
- Barrier A: the complete v111 generation and encrypted artifact must be durable before the first LAN callback or strict relay upload. Reuse `PreparedDirectMediaBlobCustodyCoordinator` and its sole strict network owner; do not add a feature-layer bridge caller. LAN remains acceleration only and never cancels strict relay custody.
- Preserve the strict upload result's `blobCustody` commitment through the existing private completion coordinator. On its durable-success arm, first reuse the private owner's no-network plaintext promotion/copy from the exact convention-pending source to the canonical path under the existing transfer/lifecycle claim; preserve the strict result's key, nonce, hashes, ciphertext commitment, and artifact byte-for-byte. A stored generation whose private completion already won adopts the exact canonical `done` row. Opening/viewing/consumed races continue to return the existing process-owned `deferredActiveLease` or `transportOnlyTerminalCustody` authorization instead of being forced into `done`; no ordinary full-row save may launder a losing private lifecycle state.
- Barrier B: after strict upload supplies exact expiry/proof, the private completion coordinator has authorized the handoff—either an exact durable canonical `done` projection or the existing exact process-owned deferred/terminal authority—and encryption produces the final private message envelope, atomically re-read the corresponding private lifecycle/attachment authorization, commit the envelope, insert/adopt one v108 row, and bind the complete v111 generation to that v108 incarnation/recipient/manifest/earliest blob expiry. Do not accept an unauthorised generic pending row. The stored proof must expire strictly after the inherited `now + 3000 ms` floor; an exact existing v108 winner is adopted before shared capacity is checked. This transaction replaces the protected/View-Once envelope-only handoff for strict attempts and must commit before any direct/LAN/chat-inbox egress. Its typed result carries the exact committed/adopted v108 projection (or an equivalent immutable authority token) back to the caller; do not perform a racy post-commit lookup that can misclassify a concurrently completed row as unstaged.
- v108 continues to use the existing `direct_text_v108` custody kind because it is the initial direct-chat envelope owner, not a plaintext-content label. Existing Plan 344 ACK-or-expiry proof, capacity, mixed-version shadow, default-off admission, fair drain, expiry ceiling, and exact completion semantics remain unchanged.
- A live direct/LAN delivery is transport truth only: it must not cancel the scheduled/non-awaited v108 hedge. Generic or legacy `stored` cannot retire strict ownership. Only exact `stored|duplicate` plus `ack_or_expiry_v1` acceptance may complete v108 and advance its bound v111 rows to cleanup. Rejected-full, disabled admission, old relay, missing proof, throw, timeout, or local completion ambiguity retains exact v108/v111. The existing private settlement branch must not bypass this exact v108 completion/failure owner once strict private custody is staged.
- Define sender crash cuts explicitly: (1) private parent/pending attachment only; (2) v111 `outgoingPrepared`; (3) v111 `outgoingStored` but no private completion authorization/v108; (4) durable completion or current-process deferred/terminal authorization but no v108; (5) exact envelope+v108+bound-v111; and (6) accepted v108/cleanup. Failed/incomplete retry must resume from the highest exact durable authority. Cuts 2/3 claim the existing private transfer/lifecycle owner, reopen byte-identical v111 ciphertext, perform the same no-network canonicalization and `commitCompletion` when the durable state permits, then attempt Barrier B without legacy upload, key rotation, envelope invalidation, or a second artifact. Cut 4 adopts an exact canonical completion or uses only a still-live exact process authorization; after process loss it requalifies the durable lifecycle state and cannot trust the vanished token. Cut 5 drains v108, while the unchanged generic unacked path suppresses any exact v108 owner. Cut 1 is deliberately pre-selection and indistinguishable from an exact pre-354 pending row without inventing provenance; it retains the unchanged legacy private retry. Partial/crossed strict state fails closed.
- Serialize sender open/consume/local-hide with cuts 2-4 under the existing media lifecycle lock. Opening/viewing retain the incumbent send through the exact `deferredActiveLease` authorization; consumed retains only the existing `transportOnlyTerminalCustody` handoff and then converges through cleanup. Move the current destructive delete-for-me/local-hide plus cleanup transition under that existing repository lifecycle authority (or an exactly equivalent existing lock-owned capability), because persisting hide before the lock can otherwise win after strict preflight but before blob/chat egress. Only local-hide winning before the transfer claim means zero later egress; if the authorized upload/handoff wins, hide waits and then converges. Private delete-for-everyone transport remains out of scope.
- Terminal cleanup uses a retention-first state machine; it must not attempt a forbidden per-attachment-to-message-wide lock upgrade. Hidden/deleted/consumed parents with `outgoingPrepared` or `outgoingStored` v111 retain the exact attachment, secure key, pending/canonical plaintext, and ciphertext artifact. The existing global blob drain later terminalizes that v111 authority, and a subsequent private cleanup pass removes the private assets. Cover both v111 states and process restart; do not add a journal, scanner, lock, cleanup owner, or a nested lock upgrade.
- Generalize strict incoming parsing only for the exact Plan-354 initial shapes. Atomically insert the incoming private parent with the full v1/mode, incoming author/contact/status, `receivedAtMs`, equal clock high-water, and null reveal/terminal/expiry/cleanup projection; its one secure-key-backed pending attachment; and one `incomingCommitted` v111 row before display staging, publication, notification, delivery receipt, or inbox ACK. Reopen/hydration must preserve that lifecycle authority exactly. Exact replay is idempotent; crossed policy/descriptor/key/commitment/sender/target/state refuses without generic fallback. After successful stage but before marker/publication, re-read terminal authority: if hide or author-delete won, return a nonthrowing durable supersession, retire/refuse any message display marker through the existing parent-conditional owner, suppress stream/notification, and still emit the exact initial receipt. A terminal replay must never route through the generic duplicate/display-promotion branch. For Protected photos, preserve the existing bounded inline thumbnail only as a best-effort guarded sibling write after atomic custody; it never becomes authority or blocks the receipt, and existing private cleanup still owns its removal.
- Incoming terminal precedence is monotonic. An authenticated initial encountering a durable consumed/hidden/author-tombstoned parent is `durablySuperseded` only when the parent proves the same author/private policy and any surviving v111 row in `incomingCommitted` or `incomingAckPending` matches the incoming attachment ID and exact public custody commitment. Source/retry metadata on an ACK-pending survivor is not replay input and must not be compared. No descriptor/key is reconstructed after legitimate cleanup, and the branch has zero attachment/key writes, display staging or promotion, publication, stream, or notification effects; its initial receipt may be emitted only after that durable winner is re-read. A crossed survivor or physically absent parent refuses with no receipt and cannot be restaged. A terminal parent with no surviving v111 uses this explicitly reduced durable parent equivalence; a parentless surviving v111 expires independently and cannot authorize a receipt.
- Route strict private download only for explicit-user intent and an exact visible incoming `available` protected/View-Once parent with one matching attachment and `incomingCommitted`/`incomingAckPending` v111. Before the first network callback, the exact attachment-scoped private transfer token must be active and the DB projection must carry the existing private `downloading` claim. Contact deletion, hide, and consume therefore either win before the claim with zero network, or wait/lose safely under the existing owners. Automatic download remains forbidden. Production bootstrap currently calls the strict owner directly for every `incomingCommitted` row, bypassing `downloadMedia` intent checks; its policy callback must behaviorally retain private rows without network. `incomingAckPending` source ACK and exact expiry may still converge automatically. Reuse the strict ciphertext verifier/decryptor and private transfer/lifecycle claim; atomically commit the canonical local path plus source-pinned ACK state under the same lock.
- Download/consume/hide/delete races must converge in both orders. A private terminal winner scrubs only the losing attempt's plaintext candidate, emits no false source ACK, and leaves v111 to exact ACK/expiry. A download commit winner may then be consumed by the existing private cleanup; parent/attachment/key removal cannot delete or recreate the independent v111 obligation. The ordinary strict owner's timestamped relay candidate decrypts to a dynamic `.dec` path that private cleanup cannot enumerate; the private strict entry must instead use one deterministic convention-owned ciphertext/decrypt staging pair under the existing single-flight/lifecycle lock. Before bridge/network/decrypt work, reuse `DirectPrivateMediaPathGuard.authorizeTarget` for the canonical target, exact ciphertext sibling, and exact `.dec` sibling; an unsafe symlink refuses with zero target mutation, network, DB, or ACK. Existing private cleanup/restart recovery must remove those exact staging siblings after a crash, including decrypt-before-DB-commit, without a wildcard scanner.
- Production bootstrap must provide the same repository/capability instances to composer, send, retries, receive, strict download, and lifecycle drain. Capability absence for a newly selected strict private attempt fails closed before network; it must not silently fall back after strict selection.

Must preserve:

- Plans 342/344 direct initial-envelope custody, exact ACK-or-expiry proof, capacity, mixed-version shadow, and one fair lifecycle drain.
- Plans 347/352 ordinary direct-media v110/v111/v108 publication, exact artifact reopen, receiver stage, source-pinned ACK/expiry, post-drain lineage, and cleanup.
- Existing protected/View-Once private lifecycle semantics: pending preparation, sender-open completion deferral, available/opening/viewing/consumed ordering, reveal limits, terminal cleanup, path guard, secure-key cleanup, and transport settlement.
