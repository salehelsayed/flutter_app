## Problem And Evidence
- Behavior to improve: a 1:1 "Protected view" photo renders with no pixels on both sides — receiver gets the plan-270 no-pixel 150px open tile, sender gets `DirectPrivateMediaOutgoingPlaceholder` (the "Protected photo … Open private media" card in the user's screenshot). The user wants the real image thumbnail in both bubbles, looking like a normal photo message, with all egress restrictions and in-app-open-only behavior intact.
- Impact: protected photos currently read as "hidden content" rather than "a photo with restrictions"; both parties lose the at-a-glance context a normal chat thumbnail provides.
- Confirmed current mechanism (modification — not a bug; no root cause fabricated):
  - Render fork: `isPrivatePresentation = !message.isDeleted && message.privateMediaPolicy.requiresRedaction` (`lib/features/conversation/presentation/screens/conversation_screen.dart:796-798`); `requiresRedaction => isPrivate || isUnsupported`, `isPrivate = protected||viewOnce||disappearing` (`lib/core/media/private_media_policy.dart:227-234`). A non-null `privateContentSlot` replaces `MediaGrid` entirely (`lib/features/conversation/presentation/widgets/letter_card.dart:127, 430-435`); slot factory picks the placeholder by state (`conversation_screen.dart:907-1074`): Terminal `:911-913`, Unsupported `:942-949`, OpenFailure `:988-989`, Outgoing `:1014-1031`, incoming default OpenPlaceholder `:1048`.
  - Receiver has ZERO image bytes before tapping Open, by design: incoming attachment persists metadata-only (`localPath: null`, `downloadStatus: 'pending'`, `lib/features/conversation/domain/models/media_attachment.dart:233-234`); auto-download policy-refused (`lib/features/conversation/application/chat_message_listener.dart:222, 712` via `allowsAutomaticDownload => !requiresRedaction`, `private_media_policy.dart:242`); download lane fails closed except `explicitUser` intent + `allows(explicitDownload)` + exact-row fingerprint (`lib/features/conversation/application/download_media_use_case.dart:578-630`).

## Scope Contract And Guard
In scope:
- Wire (additive, optional): protected-photo sends embed `thumbnailInlineBase64` — a sender-generated JPEG thumbnail (longest side ≤ 320 px, quality ≈ 60, hard cap 49,152 raw bytes; generation failure or over-cap ⇒ field omitted) — inside the already-E2E-encrypted direct-lane attachment JSON, sibling of the existing optional `thumbnailHash` (`media_attachment.dart:240, 259`). Generation is pure Dart via `package:image` (already imported, `image_processor.dart:3`) — exact longest-side bound, no platform channel, no hang risk (review corrected the original `flutter_image_compress` reuse claim: `CompressFileFn` is file-output and the plugin's min semantics bound the SHORT side). Photos only; `mode == protected` only; **gif excluded via the repo's dual check** (`mime == 'image/gif' || mediaType == 'gif'`, mirroring `send_chat_message_use_case.dart:227`) on the send, receive, and render branches — protected GIFs are representable at this seam (`allowsPrivateMedia` includes gif; only the composer excludes new ones) and must carry no thumbnail. Budget is bound by the 128 KB transport frame cap (see Problem And Evidence).
- Send seam: generation + embedding live entirely inside `SendChatMessageUseCase` (single seam; 7 external callers today — computed census, never a fixed list). `isEdit` flows do not generate, drop, or mutate the field.
- Receive seam: `HandleIncomingChatMessageUseCase` reads the field from the RAW media map the payload parser already preserves (`message_payload.dart:209-212`; raw attachment JSON available at `handle_incoming_chat_message_use_case.dart:571-577`) — the `MediaAttachment` model file is untouched. It validates (protected mode, image-and-not-gif mime, base64-decodes, ≤ cap) and persists the thumbnail to the deterministic guarded sibling path `media/<contactPeerId>/<blobId>.thumb.jpg` (new `MediaFilePathConvention.relativeThumbnailPathForAttachment`, authorized per-callsite via `DirectPrivateMediaPathGuard.identifiersAreSafe`/`authorizeTarget` exactly like the existing FS sites at `:919/:939`), write-once/idempotent on replay, placed AFTER the existing dedup/deleted-row/replay checks so a replay of a deleted message cannot resurrect it, and NEVER stored in the DB (no schema change; base64 is dropped after the file write).
- Render seam: `privateContentSlotFactory` gains two branches routed to a new `ProtectedPhotoThumbnailTile` — incoming: `mode == protected && image && state available/non-terminal && thumb file exists`; outgoing: `mode == protected && image && local bytes exist && non-terminal` (sender renders the full local file with `cacheWidth`, no artifact needed). Missing file/bytes ⇒ exact current presentations (fail-closed; also the old-sender-build path).
- Tile behavior: lock badge + reuse of existing protected copy for semantics (button + label co-located on ONE Semantics node); tap invokes the exact existing protected open flow (`_openPrivateMediaFromConversation`); ancestor long-press/swipe-to-quote preserved; no new l10n keys expected (reuse `private_media_card_title_protected_photo` family).
- Screenshot posture (platform-split, review-corrected): **Android only** — the conversation route acquires the existing `PrivateMediaProtectionCoordinator` owner while ≥1 protected thumbnail is rendered in the loaded message list, released when none remain or on dispose (window `FLAG_SECURE` via the existing handler — no native change). The route-level `enter()` MUST NOT run on iOS: iOS natively emits `inactive`/`background`/`screenshot` as critical protection events (`ios/Runner/PrivateMediaProtectionCoordinator.swift:21-31`), the coordinator latches them while any owner is held and clears only when ALL owners release (`private_media_protection_coordinator.dart:268, 308-315`), and both viewer controllers refuse to open on a latch (`direct_private_media_viewer_controller.dart:429-435`) — a long-lived route owner would make protected media unopenable on iOS after a single app-switch. iOS pixels are protected per-view instead: the tile renders through the promoted shared `IosCaptureProtectedImage` platform-view wrapper (pixels excluded from screenshots/recordings; mechanism already shipped for the viewer). **Enter-failure fails closed**: if the Android route `enter()` yields null (the coordinator's channel-failure state is permanent for the session, `private_media_protection_coordinator.dart:110-111, 274-275`), the slot factory keeps today's no-pixel presentations — protected pixels never render in an unprotected Android window.
- Wipe/delete: every code path that wipes protected media bytes or deletes the message/attachment also removes the thumbnail sibling file.
- Budget invariant: bubble rendering performs zero lifecycle-engine calls; sender reopen budget and receiver open flow semantics unchanged.

## Risks And Blind Spots
- Receiver renders a thumbnail the sender's old build never sent → guarded by TC-02 (fail-closed) — this is also the mixed-version rollout story.
- Payload growth rides the E2E message against a HARD 128 KB frame cap on both transport legs (`go-relay-server/inbox.go:28, 1911, 1922, 2024`; `go-mknoon/node/config.go:77`, `node/node.go:2222`): 49,152 raw → ≈91 KB worst-case frame (≈1.78× raw→frame after double base64), ≈37 KB headroom → bounded by the raw cap in TC-07; an over-cap message is not merely heavy, it becomes PERMANENTLY UNDELIVERABLE (retrieve_pending errors forever) — never raise the raw cap without recomputing against `maxFrameLen`. Inbox memory (100 msgs/peer, `inbox.go:29`) is the secondary bound.
- Lifecycle / derived-state durability: thumbnail presence is a FILE, not an in-memory latch — cold-mount render proven by TC-01 (fresh fixture) and writer idempotency by TC-08; no latch to lose across restart.

- Destructive-action side effects: TC-09 asserts what is REMOVED (thumb file) on all THREE destructive paths (delete-for-me, terminalization, incoming delete-for-everyone — the third runs `cleanupDeletedMessageArtifacts`, a different function than the private-lifecycle wipe), reusing the existing wipe sets rather than writing a parallel cleanup.
