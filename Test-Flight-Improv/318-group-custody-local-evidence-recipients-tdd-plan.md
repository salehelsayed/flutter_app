## Problem And Evidence

- Behavior to improve: a group member's device silently drops other members from the custody recipient set of outgoing messages. The dropped member suffers **custody+push loss while online** (live pubsub still delivers — `topic.Publish` carries no recipient restriction, go-mknoon/node/pubsub.go:420-426) and **total loss while offline**: the relay retrieval ACL denies replay AND push fanout iterates only `RecipientPeerIds` (go-relay-server/inbox.go:1655-1683), so no wake either. 309's live repro: Dave, a second admin who joined after Eve, computed `recipientPeerIds: [alice, frank]` — Eve dropped (alice survived via the creator exception, frank via his tracked invite row; no raw log artifact exists — the committed evidence is the 309 plan prose).
- Impact: the most severe known defect in the program — silent, permanent message loss for offline victims, on ordinary chat, media, retries, share-batch, and **every announcement send by a later-joined admin** (announcements share the same path and every announcement sender is an admin).
- Confirmed root cause (survived the refute pass, HEAD `846117b63` lineage): `_loadGroupSendMembership` (lib/features/groups/application/send_group_message_use_case.dart:96-176) filters the roster through `_isMissingInviteStatusInTrackedGroup` (:310-329), which on a "tracker" device drops any member with `inviteStatus == null && hasJoinedInviteEvidence && !hasJoinedTimelineEvidence` (:326-328; `unknown` status always drops, :323-325). Two **independent trigger branches** make a device a tracker with incomplete evidence (:120-121 `inviteStatuses.isNotEmpty || senderRole == GroupRole.admin`):
  1. **Admin arm** — any admin is a tracker even with zero invite rows;
  2. **Witness arm (WIDER than 309 recorded)** — `markJoined` fires on ANY device that processes a later `member_joined` transition (group_message_listener_system_transition_processor.dart:1803 → repo impl:140-151, wired at bootstrap:3778), so an ordinary late joiner who witnesses anyone joining after them acquires a `joined` row → `inviteStatuses.isNotEmpty` → tracker. Additionally, one `joined` row suppresses the timeline-evidence load entirely (:122-128), so even a locally-held `sys-member_joined` row for the victim cannot save them in branch 2.
  Invite-attempt rows are written only where evidence was locally acquired: at staging on the staging device (`recordPendingGroupInviteFanoutAttempts:90-113` writes `needsResend` at stage time; send results write sent/queued/cannotSend, record_group_invite_delivery_attempts.dart:50/:76/:101) and at witnessed joins (`markJoined`). A member who joined before this device started observing legitimately reads `null` — the null-inference misclassifies incumbents as pending invitees.
- Loss mechanics (C3, confirmed): one predicate `groupInboxMessageAuthorizedForPeer` (inbox.go:1958-1963, `From==peerId || containsPeer(RecipientPeerIds, peerId)`) is the sole authorization for all three group retrieval verbs — `group_retrieve` (:2294-2304), `group_retrieve_cursor` (:2306-2320, checks :1747/:1763), `group_history_repair_range` (:2322-2352, check :1798). No group ack/delete verb exists (entries leave via TTL prune only); `RecipientPeerIds` additionally drive push targeting (:1655-1683) and gap `CandidateSourcePeerIds` (:1838-1859), and are `json:"-"` (never serialized to clients, :1447). The same client-computed set is durably staged everywhere custody is (re)established: signed replay envelope + `inboxRetryPayload` (:1699-1705), `preserveRecipientPeerIds:true` through the bridge (bridge.go:2145-2150, :2189-2225), pubsub inbox leg (only when non-empty, pubsub.go:391-415), relay `group_store` (empty set rejected, inbox.go:2273-2274/:1500-1503). Retry and pending-broadcast lanes replay the **frozen** staged set byte-identically (envelope byte-identity is load-bearing: duplicate `group_store` MERGES recipient sets only for identical sender + identical envelope bytes, backend_redis.go:633-637 / backend_memory.go:373 — also the enabling mechanism for a future historical-custody remediation).
