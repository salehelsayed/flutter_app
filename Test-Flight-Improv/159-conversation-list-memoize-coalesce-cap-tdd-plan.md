## Exact Problem Statement
Inside a 1:1 or group chat, three compounding structural costs make interactions stutter, especially during a relay drain:

1. **Full-list grouping rebuild on every `setState` (`main-isolate-blocking-1`).** `conversation_screen.dart:447` calls `_buildDisplayItems()` **unconditionally** on every `_buildMessageList`; `_buildDisplayItems` (`:704-801`) does a full O(N) two-pass run-grouping over `widget.messages` (forward run-flag pass `:725-770` + last-in-run pass `:774-791`) with **no cache key/guard**. The group mirror `_buildGroupDisplayItems` (`group_conversation_screen.dart:793`, called from `_buildMessageList` `:560` from `build` `:219`) is identically unmemoized. So any rebuild — a status flip, a banner toggle, an unrelated `setState` — re-runs the entire grouping.

2. **One whole-screen `setState` per message (`rebuild-storms-2`).** During a relay drain, `saveMessage` emits one event per persisted row on the durable `messageChanges` broadcast stream (131 widened the filter at `conversation_wired.dart:1518` to accept incoming inserts). The listener `setState` (`:1555`) and the live `_onIncomingMessage` `setState` (`:1590`) each fire **per event** → M drained rows = M `setState` = M full `ConversationScreen` rebuilds = M full `_buildDisplayItems` passes = **O(M×N)**. Group is identical: `group_conversation_wired.dart` stream listener (`:1418-1422`) → `_applyMessageUpdate` (`:3069`) → one `setState` per message (`:3083`), each preceded by a per-message DB `getMessage` (`:3074`) + unconditional `_loadResolvedAttachmentsForMessage` (`:3075`).

3. **Unbounded in-memory window (`rebuild-storms-3`).** `_upsertMessageById` (`conversation_wired.dart:3602-3617`) rebuilds a new `_messages` list and re-runs the full O(N log N) `_sortMessagesForDisplay` (string-compare on ISO timestamps, `:3706`) on **every** insert, with **no cap/eviction** — the list grows forever on a long-lived screen. Group `_upsertMessage` (`:3279-3288`) is the same (re-runs `orderGroupMessagesForTimeline` per insert, no cap).

A secondary cost (1:1 only): `conversation_message.dart:21` stores `timestamp` as a **String**, re-parsed via `DateTime.tryParse` once per message per grouping pass (`conversation_screen.dart:737`) and string-compared per sort (`:3706`).

What must improve: (a) the grouping pass is **memoized** (recomputed only when run-affecting inputs change); (b) a drain burst of M events produces **one** rebuild, not M; (c) the in-memory window is **capped (~300, newest-first)** with self-healing re-fetch of evicted history; (d) the 1:1 parsed `DateTime` is **cached on the model** at ingest. PLUS a folded 157 follow-up: the **group** incoming media-resolve gate (mirror of 156 QW-9, which was 1:1-only).

What must stay unchanged (→ preserved-green sentinels): the **145** non-blocking notif-tap path — `_isSyncingNewMessages` "catching up…" banner toggle (set at `conversation_wired.dart:1185/1242`, rendered at `conversation_screen.dart:337` keyed on `widget.isSyncingNewMessages` `:145`), the `NOTIFICATION_TAP_TO_LIVE_MESSAGE_TIMING` milestone (`conversation_wired.dart:1217`), `CONV_FL_NOTIF_DRAIN_REFETCH` (`:1227`), and `_reloadLatestPageForRecovery`'s single bulk `setState` (`:1265`) which is **already coalesced**; the **131** stale-window self-heal (every drained message still surfaces, no dropped ids); 1:1 older-page pagination (`_hasMoreOlderMessages`/`_loadOlderMessages`, `conversation_wired.dart:1282-1318`); the 156 row-level slivers (QW-10/11/12) untouched; 146/147 upstream decrypt/receipt mechanics untouched.

- **Unconditional grouping** — `conversation_screen.dart:447` `_buildDisplayItems()` (body `:704-801`) and group `_buildGroupDisplayItems` (`group_conversation_screen.dart:793`) carry **no 156 QW marker** (the only QW hits in conversation_screen.dart are the three row-level slivers at `:449` quote-map, `:455` DateFormat, `:664` entrance — verified by direct Read); the grouping-pass body is untouched structural code with no memo guard.
- **Per-message storm** — `conversation_wired.dart:1555` (messageChanges) + `:1590` (`_onIncomingMessage`) each `setState` per event; group `:3083` per message. The only existing "coalesce" is `_drainAndReloadOnce`'s one-shot `_drainReloadPending` latch (`:1174-1177,1188-1237`), which coalesces **resume triggers into one more bulk reload** — it does **not** batch the per-message stream sinks, which still `setState` individually and run **alongside** the bulk reload (the per-message saveMessage emits fire during the drain).
- **Unbounded window** — `_upsertMessageById` (`:3611` insert branch) appends + full re-sort, **no eviction**; group `_upsertMessage` (`:3285` append + `:3287` reorder) same.
- **String timestamp re-parse (1:1 only)** — `conversation_message.dart:21` is `String`; re-parsed at `conversation_screen.dart:737` per grouping pass and string-compared at `conversation_wired.dart:3706` per sort. **GroupMessage.timestamp is ALREADY `DateTime` (`group_message.dart:26`)** → the cached-DateTime sub-change is **1:1-only** by construction.

**Three structural asymmetries that re-shape the group leg (source-verified, not assumed):**
- `GroupConversationScreen` is a **StatelessWidget** (`group_conversation_screen.dart:41`) taking `messages` as a ctor param → it **cannot** hold a memo cache or a `@visibleForTesting` counter across rebuilds. Group memoization is therefore **hoisted to `group_conversation_wired` State** (which owns `_messages`): the wired State computes the memoized `List<_GroupDisplayItem>`-equivalent (an exposed display-model) once when run-keys change and passes it down; the build-count probe lives on the wired State. The screen keeps a thin fallback compute for direct-construction widget tests.
- The group has **NO incremental older-page pagination** — no `_hasMoreOlderMessages`, no `_loadOlderMessages`, no `_pageSize` in `group_conversation_wired.dart`. `_loadMessages` (`:1272`) calls `getMessagesPage(widget.group.id)` (signature `getMessagesPage(String groupId, {int limit = 50, int offset = 0})`, `group_message_repository.dart:31-35` — offset-paged, no `beforeTimestamp` cursor) and **replaces** `_messages` wholesale (`:1288`). So the group cap's self-heal is a **full `_loadMessages` re-fetch** (re-reads from the repo), NOT a paginated `_loadOlderMessages` call (which does not exist on the group). The cap's job on the group is purely to bound in-RAM growth from the live `_upsertMessage` stream path.

The cached parse MUST be a getter backed by a non-final private cache or a recompute-cheap getter — `late final` is explicitly **forbidden** (see Scope Guard).

## Real Scope
**In scope (BOTH 1:1 + group; structural mirrors with the asymmetries above), sequenced RED-first in dependency order:**
1. **Cache parsed `DateTime` on the model (1:1 only, const-safe).** Add a `DateTime? get parsedTimestamp` to `ConversationMessage`. **Caching-strategy decision (finding #3, source-verified): `ConversationMessage` has a `const` ctor (`:79`) and EVERY instance field is `final` (`:9-77`) — Dart therefore FORBIDS any non-final instance field, so a private `DateTime? _parsedCache` instance cache will NOT compile (this is a hard compile error, not merely "not const-safe"; a `late final` is likewise out).** Pick ONE, explicitly:
   - **(a) DEFAULT — plain non-cached getter** `DateTime? get parsedTimestamp => DateTime.tryParse(timestamp)`. This is the recommended choice: once sub-change (2) memoizes the whole grouping pass, the parse runs **once per recompute** (only when the memo key changes), not once per rebuild — so per-instance caching buys almost nothing and the const-safe non-cached getter is sufficient. Hoist a single parse at the call site (`conversation_screen.dart:737`) so the value is reused within one pass.
   - **(b) ONLY-IF-PROFILED cache — a static `Expando<DateTime>`** keyed on the instance (`final _parseCache = Expando<DateTime>()`; the Expando is a static/library-level final, the *instance* stays const-safe). A static `Map<String,DateTime>` keyed by the timestamp string is **rejected** here — it grows unbounded over a long-lived process with no eviction.
   Consume `parsedTimestamp` in `_buildDisplayItems` (`conversation_screen.dart:737`) and `_sortMessagesForDisplay` (compare by `parsedTimestamp`, falling back identically to the current ISO-string compare on parse failure). NOT a DB column; NOT in `==`/`hashCode` (already id-only, `:216-223`) / `toMap` / `fromMap`. (Group already has `DateTime` — assert in the shared run-grouping test that grouping consumes a real DateTime, no new group model field.) TC-159-01 asserts the chosen strategy concretely: for (a) that `const ConversationMessage(...)` still compiles and malformed → null; for (b) additionally that a second read does NOT re-parse (Expando hit).
2. **Memoize `_buildDisplayItems` (1:1, on State) / group display-items (hoisted to `group_conversation_wired` State).**
   **RECOMMENDED key strategy (`wf_0742feb7-803` + findings #1/#2): list-reference identity + scalars.** Because the `_DisplayItem` holds the **actual `ConversationMessage`** (`conversation_screen.dart:502`) and the row renders `text` (`:556`), `media` (`:536`/`:558`), `editedAt`, and the quote/status glyph, the memo key MUST invalidate on ANY of those. The clean sound key is `identical(messages, _cachedMessages)` (the wired layer reallocates `_messages` on every content change — `_upsertMessageById` `:3604/3611/3614`, `_updateLocalMessageStatus` `:3715`, `_loadOlderMessages` prepend `:1307`; an edit flows through one of these → new ref → invalidates for free) **PLUS the non-message scalars that are NOT captured by the list ref**: `_wasEmpty`, `widget.hasMoreOlderMessages`, `widget.isLoadingMore`, **`locale`**, and a **`todayToken`** (a `YYYY-MM-DD` day stamp). 1:1 caches the `List<_DisplayItem>` on `_ConversationScreenState`; group hoists the memoized display-model into `group_conversation_wired` State (the screen is Stateless) and passes it down (thin recompute fallback on the screen for direct-construction tests).
   **FALLBACK key (only if an in-place `_messages` mutation path is ever introduced): per-message content-fold.** If you cannot rely on reference identity, the fold MUST cover **per-message `status` + `transport` + `timestamp` + `isDeleted` + `senderPeerId` + `text` + `editedAt` + a media-signature (count + each attachment id/downloadStatus)`** — `==` is **id-only** (`:216-223`) so an **edit** (same id/timestamp/status, changed `text`/`editedAt`/`media`) is invisible to a status-only fold and would render a STALE bubble (**finding #1**) — plus `messages.length` + `firstId` + `lastId` + the same scalars (`_wasEmpty`, `hasMoreOlderMessages`, `isLoadingMore`, `locale`, `todayToken`).
   **Locale + day-boundary (finding #2): the 1:1 `_formatDateLabel` (`conversation_screen.dart:956`) reads `AppLocalizations` + `Localizations.localeOf` + `DateTime.now()`** — exactly like the group path — so the 1:1 key MUST fold `locale` (a locale switch must re-label) and a `todayToken` (the day-separator "Today"/"Yesterday" labels roll over at midnight). Folding `todayToken` makes the day rollover correct on the next rebuild; if you instead accept the at-rest rollover staleness, document it as an Accepted Difference for BOTH legs (do not silently fold it for group and drop it for 1:1). Recompute only when the key changes; reuse the cached list otherwise.
3. **Per-frame coalesce of the per-event message-apply `setState`.** A trailing per-frame flush (`SchedulerBinding.instance.addPostFrameCallback` / 16ms scheduling, 157 shared-infra §1 shape) that queues each event's upsert and applies **all** queued upserts in **one** `setState`. **Lands ONLY on** `conversation_wired.dart:1555` (messageChanges) + `:1590` (`_onIncomingMessage`); group `:3083` (`_applyMessageUpdate`). **NEVER** touches `_drainAndReloadOnce`'s banner `setState` (`:1185/1242`), the milestone emit (`:1217`), `CONV_FL_NOTIF_DRAIN_REFETCH` (`:1227`), or `_reloadLatestPageForRecovery`'s bulk `setState` (`:1265`) — those are 145-owned and already coalesced. **The 145/131 preservation lock (sub-change 3a) lands and is GREEN BEFORE the coalesce edit.**
   **Per-event LIVE-STREAM SIDE EFFECTS must survive the batch (finding #4, source-verified).** `_onIncomingMessage` does more than upsert inside the `setState`: after it, it **scrolls to bottom** iff the upserted message is the new live edge (`:1592-1597`), calls **`_markAsRead()`** (`:1598`), and **auto-dismisses the intro banner** once `_messages.length >= 3` (`:1600-1602`). The group `_applyMessageUpdate` captures `previousOffset` + `preserveScrollOffset` **before** its `setState` (`:3078-3081`) and calls `_restoreScrollAfterMessageUpdate(...)` **after** (`:3088-3091`), plus `_markVisibleReadIfAllowed()` (`:3097`). A naive coalescer that just moves the upsert into a post-frame flush will (a) evaluate the "is this the live edge?" scroll predicate against a pre-batch `_messages`, (b) drop or N×-duplicate markAsRead, and (c) on the group, capture/restore the scroll offset M times around one batched setState → wrong offset. The coalescer must therefore run these effects **once per flush, after the batched apply**: compute scroll-to-bottom from the post-batch live edge, call markAsRead once, evaluate the intro-dismiss threshold once, and on the group capture `previousOffset` once before the flush and restore once after. Locked by TC-159-06 (extended) + new TC-159-08b.
4. **In-memory window cap (~300) with self-healing re-fetch.**
   **Cap-scope policy (finding #5, source-verified): the cap bounds the LIVE-DRAIN growth vector ONLY (`_upsertMessageById` / `_upsertMessage`); the manual back-scroll path `_loadOlderMessages` (`conversation_wired.dart:1291`, prepend `:1307`) is INTENTIONALLY EXEMPT.** Rationale: (a) back-scroll growth is user-driven and self-limiting (the user stops scrolling), unlike the unbounded relay-drain append that motivates this epic; (b) **newest-first eviction is fundamentally incompatible with capping during an older-page load** — `_loadOlderMessages` prepends the OLDEST page, which is exactly what a newest-first trim would immediately evict, producing a load→evict→load-again loop (the user sits at `minScrollExtent`, `_maybeLoadMore` `:1286` re-fires forever). So the trim runs in the live-append branch and is **skipped** on the prepend branch. This makes the "in-memory window cap" framing precise: it caps the live edge's forward growth, not the user's deliberate history excursion.
   1:1: in `_upsertMessageById` (`conversation_wired.dart:3611` insert branch) after sort, trim to the newest `kMaxInMemoryMessages` (cap **newest-first** — never evict the live edge), and when an eviction happens set `_hasMoreOlderMessages = true` so `_loadOlderMessages` (`:1291`) re-fetches the dropped tail. Group: in `_upsertMessage` (`group_conversation_wired.dart:3285/3287`) after reorder, trim newest-first to `kMaxInMemoryMessages`; the group's only self-heal is a full `_loadMessages` re-read (`:1272`, re-fetches up to the repo page limit) — there is no `_hasMoreOlderMessages` flag to set (the group has no incremental older-page UI), so the group cap test asserts trim-newest-first + that a subsequent `_loadMessages` re-populates the evicted rows. Extract the trim to a pure helper for plain unit testing (shared shape across both legs); call it from the live-append branch only.
**Folded 157 follow-up (additive, small):** add the 156 QW-9 media-resolve gate to the **group** `_applyMessageUpdate` (`group_conversation_wired.dart:3069-3075`) — skip `_loadResolvedAttachmentsForMessage` (`:3075`) when the message is already shown AND declares no unresolved attachment id (mirror the 1:1 `shouldResolveMedia` logic at `conversation_wired.dart:1538-1546`), preserving the group media-integrity verify.
