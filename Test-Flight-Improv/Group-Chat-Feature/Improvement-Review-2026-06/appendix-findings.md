## Send path (`send-path`)

**Score:** reliability 3/5 · UX 2/5

**Current state:** The group send path is a sophisticated optimistic-send pipeline: the UI mints a messageId, shows an optimistic row, then sendGroupMessage() pre-persists a 'sending' row (with wireEnvelope + inboxRetryPayload for retry), invokes a native group:sendReliable that does GossipSub publish + relay-inbox custody in one call, and applies a multi-way result matrix to set the final status ('sent' / 'pending'(in-doubt) / 'failed'). A separate legacy path (callGroupPublish + concurrent inbox store) remains for older native nodes. Background retriers (on reconnect, every 5 min, plus app-resume) re-drive failed rows and failed inbox stores, and incoming self-echo reconciliation can heal in-doubt rows. The design correctly recognizes that publish is fire-and-forget and treats topicPeers as live-fanout evidence rather than delivery proof. The main reliability/UX gaps are at the boundaries: the open conversation screen does not observe background status changes, failed text messages have no in-place retry, restored-composer text resends are not id-stable, in-doubt 'pending' rows lack a dedicated recovery sweep, and reactions have no offline custody fallback — together these reproduce the duplicate-delivery / stuck-failed cascade documented in doc 102.

**Strengths to preserve:**
- sendGroupMessage() centralizes optimistic persistence and a clear result matrix; it correctly distinguishes live fanout (topicPeers) from delivery, and treats topicPeers as evidence-only rather than a delivery ACK (send_group_message_use_case.dart:30-43, 68-97).
- BRIDGE_TIMEOUT and publish-without-custody are explicitly classified as in-doubt ('pending') rather than false 'failed', preserving wireEnvelope for self-echo reconciliation (send_group_message_use_case.dart:888-947) — directly addresses the doc-102 false-failure root cause for the reliable path.
- messageId stability under dedicated retry is well designed: _resolveOutgoingMessageId reuses a caller-supplied id only when group/sender/text/timestamp/quote all match an existing sending/failed row, with collision fallback (send_group_message_use_case.dart:208-279); dedicated failed-card retry reuses the original id (retry_failed_group_messages_use_case.dart:284).
- Self-echo reconciliation can repair an already-'failed' row (not just sending/pending) when it still carries wireEnvelope/inboxRetryPayload, preventing a permanent false-failed card after a late own-message replay (handle_incoming_group_message_use_case.dart:893-902).
- Concurrent composer sends from the same screen are guarded by _isSending (group_conversation_wired.dart:307-324), and background tasks are wrapped so uploads/sends survive brief backgrounding.
- Media attachment send is robust: EXIF/MIME/size/content-hash validation and durable-storage staging happen before publish, with stale upload_pending cleanup to avoid orphaned attachments (send_group_message_use_case.dart:310-436, _persistOutgoingMedia).

### `send-path:no-text-message-retry-affordance` — Failed text-only group messages have no in-place retry button

`high` (raised: high) · ux · verdict: **confirmed** · effort: small · reviewer-confidence: high

- **User impact:** When a group text send fails, the user sees a red error icon but no way to retry that exact message. Their only options are to wait (silently) for a background sweep or to retype the text, which mints a NEW messageId and can produce a duplicate for recipients if the original actually went through. This makes group chat feel unreliable and is a primary driver of the doc-102 duplicate cascade for text.
- **Evidence:** group_conversation_screen.dart:543-589 only computes showFailedMediaActions (requires messageMedia.isNotEmpty) and only passes onRetryFailedMedia/onDeleteFailedMedia to LetterCard; onRetryFailedMessage is never supplied for groups. LetterCard supports onRetryFailedMessage (letter_card.dart:294-314) but it is left null, so a failed text row renders Icons.error_outline_rounded (letter_card.dart:530) with no retry control. retryFailedGroupMessage() exists and is id-stable but is only invoked for media (group_conversation_wired.dart:2071).
- **Proposal:** Wire an onRetryFailedMessage callback for group conversations: in group_conversation_screen.dart show it whenever isSent && message.status == 'failed' (regardless of media), and in group_conversation_wired.dart call retryFailedGroupMessage(messageId: ...) which already reuses the original id. This gives users an explicit, id-stable retry for text and removes the incentive to retype (which duplicates).
- **Affected files:** `lib/features/groups/presentation/screens/group_conversation_screen.dart`, `lib/features/groups/presentation/screens/group_conversation_wired.dart`, `lib/features/conversation/presentation/widgets/letter_card.dart`
- **Verifier:** group_conversation_screen.dart:543-547 computes only showFailedMediaActions (requires messageMedia.isNotEmpty) and the LetterCard built at 555-595 wires only onRetryFailedMedia/onDeleteFailedMedia (582-589); it never sets onRetryFailedMessage. The group screen has no onRetryFailedMessage field at all (only onRetryFailedMedia/onDeleteFailedMedia at lines 75-76). LetterCard fully supports onRetryFailedMessage (letter_card.dart:294,303-314) but it stays null for groups, so a failed text row renders only Icons.error_outline_rounded (letter_card.dart:530) with no retry control. By contrast the 1:1 conversation_screen.dart:470-476,538-539 wires onRetryFailedMessage for failed text-only messages, proving the pattern exists and groups are the gap. The id-stable retryFailedGroupMessage() (retry_failed_group_messages_use_case.dart:94) is only invoked from media retry (group_conversation_wired.dart:2071). Evidence and proposal hold.

### `send-path:open-screen-no-refresh-on-background-status-change` — Open conversation does not reflect background retry status changes

`high` (raised: high) · reliability · verdict: **confirmed** · effort: medium · reviewer-confidence: high

- **User impact:** If a send shows 'failed' (or stays 'pending'/in-doubt) and then a background retrier flips it to 'sent' while the user is still looking at the group, the screen keeps showing the failed/clock card. The user believes it failed and resends, creating duplicates — exactly the cascade described in doc 102.
- **Evidence:** group_conversation_wired.dart subscribes only to groupMessageListener.groupMessageStream (incoming messages) at lines 1201-1202 and reloads messages only on AppLifecycleState.resumed (588-595). PendingMessageRetrier runs retryFailedGroupMessages and retryFailedGroupInboxStores on reconnect and every 5 minutes while foregrounded (pending_message_retrier.dart:163-178, 374-384, 469-479), updating rows via the repository, but there is no repository change-stream the open screen listens to. The repo writes status directly (group_message_repository_impl.dart updateMessageStatus) with no broadcast.
- **Proposal:** Add a lightweight outgoing-status change notifier: have GroupMessageRepository (or a small status event bus) emit (messageId,status) on updateMessageStatus/saveMessage for outgoing rows, and subscribe in group_conversation_wired to upsert the affected row. Minimal alternative: after each PendingMessageRetrier sweep that changes >0 group rows, emit an event the active screen listens to and triggers a scoped _loadMessages().
- **Affected files:** `lib/features/groups/presentation/screens/group_conversation_wired.dart`, `lib/features/groups/domain/repositories/group_message_repository_impl.dart`, `lib/core/services/pending_message_retrier.dart`
- **Verifier:** group_conversation_wired only subscribes to incoming/removed/reaction/media-progress/recorder streams (1201-1222, 3717-3718, 366); none carry outgoing status changes. It reloads messages only on AppLifecycleState.resumed (588-595). PendingMessageRetrier runs retryFailedGroupMessagesFn and retryFailedGroupInboxStoresFn every periodicRetryInterval=5min while foregrounded (pending_message_retrier.dart:168-171,374-384,469-479), and GroupMessageRepositoryImpl.updateMessageStatus just calls dbUpdateGroupMessageStatus with no broadcast (group_message_repository_impl.dart:295-297). So a background failed->sent (or pending->sent) flip is not reflected on the open screen until resume/reopen. Confirmed.

### `send-path:restored-composer-text-resend-not-id-stable` — Restored-composer text resend mints a fresh messageId (duplicate risk)

`high` (raised: high) · correctness · verdict: **confirmed** · effort: medium · reviewer-confidence: high

- **User impact:** After a failed text send, the composer is restored. If the user re-sends, a brand-new messageId is generated, so recipients cannot dedupe it against the original — and because the original may actually have been delivered (flood-publish/relay custody completed after a BRIDGE_TIMEOUT), members can receive two copies of one intended message.
- **Evidence:** _onSend always uses restoredContinuation?.messageId ?? _uuid.v4() (group_conversation_wired.dart:1590). _trackRestoredMediaContinuation, which would make the resend reuse the original id+timestamp, is only invoked from _restoreComposerSnapshot when snapshot.pendingAttachments.isNotEmpty (group_conversation_wired.dart:2158-2166); a text-only failed send falls into the else branch (2164) that clears continuation tracking. _resolveOutgoingMessageId can reuse an id for a matching failed row (send_group_message_use_case.dart:208-279), but only if the caller passes that id — which the text resend never does.
- **Proposal:** Track a restored continuation for text-only failed sends too (not just media): in _restoreComposerSnapshot always record draftText/quote/timestamp/messageId for the failed row so a matching resend reuses the original messageId. Alternatively, steer users to the in-place retry (finding no-text-message-retry-affordance) so retyping is unnecessary. Either way the same intended send must keep one stable id.
- **Affected files:** `lib/features/groups/presentation/screens/group_conversation_wired.dart`
- **Verifier:** _onSend uses messageId = restoredContinuation?.messageId ?? _uuid.v4() and now = restoredContinuation?.timestamp ?? DateTime.now() (group_conversation_wired.dart:1590-1591). The continuation is only ever set by _trackRestoredMediaContinuation (the sole writer of _restoredMediaContinuation, 873-882), which is invoked only from the snapshot.pendingAttachments.isNotEmpty branch (2158-2163); text-only failed sends hit the else at 2164-2165 that clears tracking. _resolveOutgoingMessageId can reuse an id but only via _canReuseOutgoingMessageId which requires matching text AND identical timestamp (send_group_message_use_case.dart:217-227); a retype passes a fresh uuid with a fresh DateTime.now(), so the reuse predicate fails and a new id is minted. Recipients dedupe on id, so a previously-delivered original plus the resend yields two copies. Confirmed.

### `send-path:orphaned-in-doubt-pending-rows` — In-doubt 'pending' rows can get stuck forever with no recovery sweep

`medium` (raised: medium) · reliability · verdict: **confirmed** · effort: medium · reviewer-confidence: medium

- **User impact:** A message left in the in-doubt 'pending' state (reliable-send timed out, or published without custody) shows a perpetual clock icon and has no retry button. If it is never healed by a self-echo and has no usable retry payload, the user is left with a message that looks permanently un-sent even though it may have been delivered — eroding trust and prompting a duplicate resend.
- **Evidence:** On BRIDGE_TIMEOUT / publish-without-custody the row is saved status:'pending' with inboxStored:false and retryPayload from _nativeReliableInboxRetryPayload, whose fallback is prePersistMessage.inboxRetryPayload (send_group_message_use_case.dart:881-904, 156-169). That fallback is null when buildGroupOfflineReplayEnvelope threw earlier (786-817). retryFailedGroupInboxStores only loads rows where inbox_retry_payload IS NOT NULL (group_messages_db_helpers.dart:731). recoverStuckSendingGroupMessages only transitions status='sending' (group_messages_db_helpers.dart:742-757). getFailedOutgoingMessages only loads status='failed'. So a 'pending' row with null retry payload and no self-echo is picked up by nothing. The UI renders 'pending' as a non-actionable clock (letter_card.dart:531, 567) with no retry affordance.
- **Proposal:** Add a stuck-'pending' recovery: either (a) a sweep that, after a timeout, re-drives 'pending' rows that still have a wireEnvelope via sendGroupMessage with the same id, or (b) transition long-stale in-doubt 'pending' rows (no retry payload, older than N minutes, no echo) to 'failed' so they surface the (newly added) retry button. Also ensure a retry payload is always persisted for in-doubt rows by falling back to the locally built inboxPayload before giving up.
- **Affected files:** `lib/features/groups/application/send_group_message_use_case.dart`, `lib/core/database/helpers/group_messages_db_helpers.dart`, `lib/features/groups/application/retry_failed_group_inbox_stores_use_case.dart`
- **Verifier:** On reliableTimedOut/publishWithoutCustody the row is saved status:'pending' with inboxRetryPayload=retryPayload (send_group_message_use_case.dart:897-904), where retryPayload (881-887) falls back to prePersistMessage.inboxRetryPayload, which is null when buildGroupOfflineReplayEnvelope threw at 786-817 (inboxRetryPayload declared null at 785, only set in the try). The DB sweeps confirm no recovery for such a row: dbLoadGroupMessagesWithFailedInboxStore requires inbox_retry_payload IS NOT NULL (group_messages_db_helpers.dart:731), dbLoadStuckSendingGroupMessages only status='sending' (700), dbLoadFailedOutgoingGroupMessages only status='failed' (713), dbTransitionGroupSendingToFailed only transitions 'sending' (748,754). A self-echo CAN heal it (_canReconcileOutgoingSelfEchoStatus returns true for 'pending', handle_incoming...:894), but the finding correctly scopes to the case where no echo arrives (message not actually delivered) AND payload is null. UI renders 'pending' as a non-actionable clock (letter_card.dart:531) with no retry. Genuine but narrow edge case; medium is right.
- **Verifier correction:** Narrow scope worth stating explicitly: only the subset where buildGroupOfflineReplayEnvelope threw (null payload) AND no self-echo arrives is truly orphaned; when the replay envelope builds successfully the 'pending' row IS picked up by the inbox-store sweep (db helper line 731 includes status='pending').

### `send-path:reaction-no-offline-fallback` — Group reactions are silently dropped on publish failure (no relay custody, no retry)

`medium` (raised: medium) · reliability · verdict: **confirmed** · effort: small · reviewer-confidence: medium

- **User impact:** If a reaction's live publish fails (e.g. topic not yet joined, transient bridge error), the optimistic emoji is reverted and the reaction is lost with no fallback and no retry. Unlike messages, the reaction is never staged to the relay inbox, so offline group members never see it and the sender gets no feedback that it failed. Reactions feel flaky compared to messages.
- **Evidence:** sendGroupReaction returns publishFailed immediately when callGroupPublishReaction is not ok or throws (send_group_reaction_use_case.dart:168-183), returning BEFORE _stageReactionInboxStore (line 186). The wired layer then reverts the optimistic reaction with no message (group_conversation_wired.dart:3841-3843). By contrast, messages stage relay-inbox custody even at zero peers. (Note: with GossipSub flood-publish, topic.Publish returns nil at zero peers — pubsub.go:710 — so the zero-peers case is usually covered; the gap is the genuine publish-error path.)
- **Proposal:** Stage the reaction replay-outbox entry BEFORE the live publish (or unconditionally after building it), so a publish failure still leaves a retryable, durable reaction that retryFailedGroupInboxStores will re-drive. Treat publish failure as queued-with-retry rather than a hard drop, mirroring the message path.
- **Affected files:** `lib/features/groups/application/send_group_reaction_use_case.dart`
- **Verifier:** sendGroupReaction returns publishFailed immediately on result['ok'] != true (send_group_reaction_use_case.dart:174) or on exception (182), both BEFORE _stageReactionInboxStore (186) and reactionRepo.saveReaction (199). The wired layer's else branch reverts the optimistic reaction with no message (group_conversation_wired.dart:3841-3843). The pubsub.go note is accurate: with flood-publish, topic.Publish only errors on a real publish failure (pubsub.go:710-712), so the zero-peers path generally returns ok and is covered; the gap is the genuine publish-error/throw path, exactly as claimed. Confirmed.

### `send-path:reliable-send-timeout-budget-mismatch` — Flutter reliable-send timeout (10s) is shorter than native budget (15s inbox + 30s pubsub)

`medium` (raised: medium) · reliability · verdict: **confirmed** · effort: small · reviewer-confidence: medium

- **User impact:** Under slow networks the Flutter side gives up after 10s and reports BRIDGE_TIMEOUT while native group:sendReliable is still working (and often succeeds), pushing the message into the in-doubt 'pending' limbo more often than necessary. This increases the rate of stuck/ambiguous sends and the duplicate-resend behavior that follows.
- **Evidence:** callGroupSendReliable defaults to Duration(seconds: 10) (bridge_group_helpers.dart:410-411, 445-456) and returns BRIDGE_TIMEOUT on TimeoutException. Native budgets are InboxTimeout=15s and PubSubTimeout=30s (config.go:33, 45), and native pubsub.go performs inbox store + publish before returning the reliable result. So the foreground caller frequently abandons a call that the node completes successfully.
- **Proposal:** Raise the reliable-send Flutter timeout to comfortably exceed the native worst-case (e.g. ~35-40s, or pass an explicit timeout aligned to the native budget) so the common case resolves to a real 'sent' instead of in-doubt 'pending'. Keep the in-doubt handling for genuinely slow cases. Optionally have native return an early 'accepted-custody' signal so Flutter can mark 'sent' before the full pubsub timeout elapses.
- **Affected files:** `lib/core/bridge/bridge_group_helpers.dart`, `go-mknoon/node/config.go`
- **Verifier:** callGroupSendReliable defaults to Duration(seconds: 10) and maps TimeoutException to BRIDGE_TIMEOUT (bridge_group_helpers.dart:410,448-456); the send use case calls it with no timeout override (send_group_message_use_case.dart:845). Native SendGroupMessageReliable runs inbox store and publish concurrently and only returns after wg.Wait() (pubsub.go:378-399), with publish bounded by PubSubTimeout=30s (394; config.go:45) and inbox by InboxTimeout=15s (config.go:33). So the foreground caller abandons after 10s while native can still be working (worst case ~30s), pushing sends into in-doubt 'pending' more often than necessary. Confirmed.
- **Verifier correction:** Minor: native inbox and publish run CONCURRENTLY (wg.Wait at pubsub.go:399), so the native worst case is ~max(15s,30s)=30s, not the 15s+30s=45s the evidence/proposal implies. The 10s<30s mismatch (and hence the bug) still holds; the proposal's ~35-40s target remains safe.

## Receive path (`receive-path`)

**Score:** reliability 4/5 · UX 3/5

**Current state:** The Dart receive path is mature and heavily defended: Go emits `group_message:received` / `group_reaction:received` / diagnostics, `GoBridgeClient` routes them to broadcast StreamControllers in main.dart, and `GroupMessageListener` validates a schema, short-circuits system messages, buffers membership-dependent messages, then calls `handleIncomingGroupMessage()` which dedups (by messageId, with content fallback), enforces removal/dissolve/epoch boundaries, reconciles self-echoes, persists, and fans out on `groupMessageStream`/`groupRemovedStream`/`groupReactionChangeStream` to Conversation/List/Feed/Orbit. Live messages are serialized via `asyncMap`, the DB insert merges on id-conflict, and UI surfaces also reload from the DB so transient stream misses self-heal. The main reliability gaps are in the decryption-failure repair lifecycle (live placeholders that never resolve), in reaction ordering/early-arrival handling (no buffering, no serialization), and a few correctness/UX divergences between the persisted message and notification/timeline ordering.

**Strengths to preserve:**
- Live message processing is serialized via incomingGroupMessages.asyncMap(_handleLiveMessage), preventing same-stream interleaving and most dedup races on the live path.
- Strong, layered dedup: messageId pre-check before group/member lookups, conflicting-id rejection, self-echo reconciliation, logical media-retry dedup, and a content-based fallback for id-less messages (handle_incoming_group_message_use_case.dart:86-587).
- DB-level insert is hardened: dbInsertGroupMessage catches UNIQUE id conflicts and merges instead of blind-replacing, and respects local tombstones (group_messages_db_helpers.dart:31-37).
- UI surfaces (GroupConversationWired._loadMessages) reload persisted rows from the DB on open, so broadcast-stream events emitted before a subscriber attaches are not permanently lost.
- Empty (no text + no media) events are dropped rather than persisted, avoiding empty bubbles that survive cold restart (group_message_listener.dart:680-694).
- Future-timestamp clamping with a 5-minute skew tolerance keeps clock-skewed senders from jumping to the bottom of the timeline forever (handle_incoming_group_message_use_case.dart:1004-1030).
- Robust per-handler error isolation with flow events, plus dispatcher-overflow and push-loss recovery hooks so dropped Go events trigger catch-up rather than silent loss.

### `receive-path:live-key-repair-placeholder-never-resolves` — Live decryption-failure placeholder can never be repaired and duplicates the real message

`high` (raised: high) · reliability · verdict: **confirmed** · effort: medium · reviewer-confidence: high

- **User impact:** After a key-rotation race, the receiver sees a permanent 'Waiting for a newer group key to decrypt this message.' bubble that never goes away, and once the real message is delivered the user sees BOTH the stuck placeholder and the real message side by side. This looks like a stuck/duplicated message in the group thread and erodes trust that messages eventually arrive.
- **Evidence:** queueLiveGroupDecryptionFailureRepair() persists a placeholder with replayEnvelopeJson:null and a synthetic id 'live:groupId:senderId:keyEpoch:localKeyEpoch' (group_pending_key_repair_service.dart:264-307). The Go event group:decryption_failed carries only groupId/senderId/keyEpoch/error, never the ciphertext (pubsub.go emitGroupDecryptionFailed:1664-1675), so the placeholder has no envelope to replay. _retryOne() therefore always returns at 'waiting for replay envelope' (group_pending_key_repair_service.dart:425-440) and can never decrypt. The only cleanup, _supersedeLiveDiagnosticRepairForDurableReplay(), is invoked solely from the durable OFFLINE replay queue path (line 145) and requires replayEnvelopeJson==null AND a durable replay for the same sender+epoch (_isLiveDiagnosticRepairForSender:235-243); the live _handleMessage path never supersedes it, and the real message (real wire messageId) is not deduped against the synthetic placeholder id.
- **Proposal:** On the live receive path, when handleIncomingGroupMessage successfully persists a real message, call a supersede that deletes any live: pending-key placeholder/repair for the same groupId+senderId+keyEpoch (reuse _supersedeLiveDiagnosticRepairForDurableReplay logic, driven from _handleMessage after _emitGroupMessage). Additionally, either (a) have Go include the encrypted envelope (or messageId) in group:decryption_failed so the live placeholder can be reconciled/replayed by id, or (b) give live pending-key placeholders a TTL after which retryPendingRepairsForKey marks them undecryptable instead of looping 'waiting for replay envelope' forever.
- **Affected files:** `lib/features/groups/application/group_pending_key_repair_service.dart`, `lib/features/groups/application/group_message_listener.dart`, `go-mknoon/node/pubsub.go`
- **Verifier:** Verified end-to-end. Go group:decryption_failed carries only groupId/senderId/keyEpoch/error/decryptMs (+ optional localKeyEpoch) and never ciphertext or messageId (go-mknoon/node/pubsub.go:1664-1675). queueLiveGroupDecryptionFailureRepair persists a placeholder + repair with replayEnvelopeJson:null and a SYNTHETIC id 'live:groupId:senderId:keyEpoch:localKeyEpoch' used as both repair.id and message.id (group_pending_key_repair_service.dart:264-307). _retryOne() short-circuits at 'waiting for replay envelope' whenever replayEnvelopeJson is null/empty, so a live placeholder can NEVER decrypt via retry (group_pending_key_repair_service.dart:424-441). The only supersede call site is line 145 inside queueMissingGroupReplayKeyRepairFromEnvelope (durable OFFLINE replay), gated by _isLiveDiagnosticRepairForSender requiring id.startsWith('live:') AND replayEnvelopeJson==null (lines 199-243). The LIVE receive path _handleMessage calls _emitGroupMessage(result) on success but never supersedes a live placeholder (group_message_listener.dart:736-783), and the real message persists under its real wire messageId via a fresh saveMessage (handle_incoming_group_message_use_case.dart:590-609) — the placeholder dedup at line 477 only matches when existing row id == real messageId, which it never does for the synthetic live id. Placeholder text matches ('Waiting for a newer group key to decrypt this message.', group_pending_key_repair.dart:5-6). IMPORTANT MITIGATION CAVEAT: when repair completes via the durable offline-replay queue, _supersedeLiveDiagnosticRepairForDurableReplay DOES delete the live placeholder and finalize the repair (lines 209-221), so the stuck+duplicate outcome only occurs when the real message is re-delivered via a LIVE/membership-flush/push-loss path (all of which route through _handleMessage, listener:1094-1099, not durable replay) rather than the durable inbox. So 'can never be repaired' is accurate for retry/live paths, and the duplicate is real, but the durable-replay path is an existing partial cleanup that the finding under-credits.
- **Verifier correction:** The finding omits that the durable offline-replay path (queueMissingGroupReplayKeyRepairFromEnvelope -> _supersedeLiveDiagnosticRepairForDurableReplay, line 145) already deletes/finalizes the live placeholder for the same sender+epoch. The stuck-forever + side-by-side duplicate therefore manifests specifically when the real message is repaired/redelivered via the LIVE _handleMessage path (including the durable membership-buffer flush at listener:1094 and push-loss recovery) rather than the durable inbox drain — not 'in all cases'. The proposed fix (supersede live placeholders from _handleMessage after a real persist) is correct and closes the remaining gap.

### `receive-path:reaction-before-message-dropped` — Reactions that arrive before their target message are silently dropped with no retry

`medium` (raised: medium) · reliability · verdict: **confirmed** · effort: medium · reviewer-confidence: high

## Transport / GossipSub (`transport-gossipsub`)

**Score:** reliability 3/5 · UX 3/5

**Current state:** Live group delivery rides GossipSub with WithFloodPublish(true) over libp2p, with a rendezvous register/discover loop (warm 3s cadence, backing off toward 30s/1m) and circuit-relay dialing to form the mesh. A v3 envelope is encrypted (AES-256-GCM under a per-epoch group key) and signed per device; a topic validator authenticates sender->member->device->signature before accept. SendGroupMessageReliable races a live publish against a relay inbox store so offline members can catch up; PublishGroupMessage (the non-reliable GroupSend path) publishes live only. The code is careful about config normalization, device binding, dial cooldowns/backoff, and emits rich group:discovery diagnostics. The main reliability gaps are around publish being fire-and-forget with no per-recipient delivery confirmation, validator behavior during key rotation, and swallowed inbox errors.

**Strengths to preserve:**
- Topic validator (groupTopicValidator, pubsub.go:1436) is rigorous: it binds the claimed senderId to the libp2p transport peer (groupEnvelopeMatchesTransportPeer), resolves the exact active member device (activeMemberDeviceForEnvelope), enforces announcement-group write rules, and verifies the per-device signature before ValidationAccept. This prevents spoofed/forged group messages from reaching the UI.
- WithFloodPublish(true) (pubsub.go:72) is a deliberate, well-justified choice for small groups where mesh formation over relay circuits is slow/partial — it sends to all connected interested peers, not just the mesh subset, materially improving small-group live delivery.
- SendGroupMessageReliable (pubsub.go:338) runs the relay inbox store and the live publish concurrently and reports a structured DeliveryMode (live_and_inbox / inbox_only / live_only / failed), giving the app a real signal to distinguish live vs store-and-forward delivery.
- Discovery cadence is adaptive and bounded: warm 3s retries while partially connected, exponential backoff capped at 1m (nextGroupDiscoveryCadence, pubsub.go:3025), jitter, per-peer dial cooldown/in-flight guards (beginGroupPeerDialWithMode), and a concurrency semaphore — this avoids both fanout storms and multi-minute stalls.
- connectGroupPeerPreferDirect (pubsub.go:1873) prefers direct/LAN addresses and only falls back to relay circuit, then verifies the peer actually became a live *topic* peer (waitForLiveGroupTopicPeer) rather than trusting a bare host connection — a correct distinction for GossipSub.
- Validation-reject feedback (group_validation_feedback.go) sends a back-channel to the original sender so the sender can learn its message was rejected (e.g., stale config), enabling sender-side recovery instead of a silent black hole.
- Reject diagnostics are rate-limited and privacy-preserving (hashed peer/group ids, 1-minute dedup window) in logPubSubValidationReject (pubsub.go:1362), keeping observability without log spam or PII leakage.

## Recovery & reliability (`recovery-reliability`)

**Score:** reliability 3/5 · UX 3/5

**Current state:** Group recovery is orchestrated from three entry points: cold-start (StartupRouter._doStartP2P fire-and-forget), foreground resume (handleAppResumed), and PendingMessageRetrier (a debounced retry pass plus a 30s continuity sweep). Each runs a documented ordered pipeline: rejoinGroupTopics -> drainGroupOfflineInbox -> conditional acknowledgeRecovery -> recoverStuckSendingGroupMessages -> retryIncompleteGroupUploads -> retryFailedGroupMessages -> retryFailedGroupInboxStores. The drain is cursor-paginated with idempotent message handling and a two/three-phase write split to avoid holding the SQLCipher lock across bridge hops. GroupRecoveryGate is an advisory re-entrant counter (not a lock); cross-entry-point mutual exclusion relies on a patchwork of separate boolean flags (_isResuming, _isRetrying, _isGroupContinuitySweeping) that do not all guard each other. Reliability of catch-up itself is generally solid (dedupe-on-messageId, retention cutoffs, stale-cursor/max-page guards), but the orchestration layer has overlap and timing hazards that can flap message status and waste work.

**Strengths to preserve:**
- Offline-inbox drain is genuinely robust: cursor-based pagination with a seenCursors stale-cursor guard, a maxPages ceiling, a synthetic since-cursor fallback, and per-page idempotent persistence so a crash between phases re-drains and dedupes naturally (drain_group_offline_inbox_use_case.dart:292-1007).
- The three-phase drain (process outside txn, tiny atomic cursor+receipt commit, then independent gap repair) deliberately avoids holding the SQLCipher write lock across native bridge round-trips, which directly prevents the 10s 'database locked' starvation that froze concurrent readers (drain_group_offline_inbox_use_case.dart:767-860).
- Groups are drained in parallel via a bounded worker pool (maxConcurrentGroupDrains, default 4) so one slow relay group does not serially stall startup/resume catch-up (drain_group_offline_inbox_use_case.dart:95-157).
- Per-group and per-message fault isolation is consistent: errors are caught, logged via emitFlowEvent, and never abort the whole batch, so one bad group/message does not block the rest of recovery.
- History-gap detection is persisted BEFORE the cursor advances (Phase 2a), so a detected gap survives a crash and is independently retryable rather than being lost when the cursor moves past it (drain_group_offline_inbox_use_case.dart:828-842).
- Retry eligibility is carefully tiered: text-only failed rows retry directly while media rows only retry once attachments are downloadStatus=done, with ownership cleanly split between retryFailedGroupMessages and retryIncompleteGroupUploads.
- Recovery acknowledgement to Go is correctly gated on BOTH a clean rejoin (0 errors, 0 skipped-no-key) AND a successful drain, preventing premature clearing of needsGroupRecovery (handle_app_resumed.dart:200-221, rejoin_group_topics_use_case.dart:36-37).

## Invites (`invites`)

**Score:** reliability 3/5 · UX 2/5

**Current state:** Group invites are sent ML-KEM-encrypted+signed over P2P with a relay store-and-forward fallback, validated by a signed membership-freshness proof and device-binding, then stored as a per-group pending invite and accepted via a multi-stage flow (validate -> materialize group -> bridge join -> drain offline inbox -> commit/consume). The cryptographic authorization and replay/consumption/revocation tombstone model is thorough and defensive. However, the accept flow couples invite-consumption to a best-effort offline-inbox drain, so a single transient relay/bridge failure produces a confusing "Joined X, but recovery is still catching up" message over a stale group snapshot and leaves the invite re-tappable (the known scenario-7 bug). Several reliability/UX gaps remain: a 24h-vs-7d expiry mismatch that silently rejects still-actionable invites, no admin revocation path wired to the UI, no decline notification or delivery-status convergence back to the inviter, no background sweep of expired/lingering invites, and no on-join authoritative-metadata resync.

**Strengths to preserve:**
- Strong cryptographic authorization: every invite carries a signed inviter snapshot + membership-freshness proof that is verified on receive AND again at accept time (group_invite_auth.dart), with sender/transport peer-id cross-checks and recipient device-binding (handle_incoming_group_invite_use_case.dart:147-195).
- Robust replay/abuse defenses: single-use consumption tombstones, welcome-key-package tombstones, revocation tombstones, and stale-snapshot comparison (_incomingInviteIsStaleComparedToExistingPending) prevent double-join and stale-invite resurrection.
- Send path degrades gracefully: direct P2P send falls back to relay inbox store-and-forward, returning distinct success/queued results with rich FLOW logging at every step.
- Repairable join-material errors trigger a clean rollback of the half-materialized group (removeAllKeys/removeAllMembers/deleteGroup) rather than leaving corrupt state (handle_incoming_group_invite_use_case.dart:920-937).
- The invite listener serializes message processing into a single Future chain (_messageProcessing), avoiding concurrent-accept races at the listener level, and rejects invites from blocked contacts up front.
- UI double-tap is guarded per-invite via _processingInviteIds set synchronously before any await (group_list_wired.dart:277-282).

## Membership & lifecycle (`membership-lifecycle`)

**Score:** reliability 3/5 · UX 3/5

**Current state:** Membership and lifecycle mutations (add/remove/role/dissolve/metadata) are implemented as top-level use-case functions that mutate the local repo, then re-derive a full authoritative GroupConfig snapshot and push it to the Go validator, then broadcast a signed `__sys` system event over pubsub plus an offline inbox replay envelope. Receivers apply these in `group_message_listener._handleSystemMessage`, which is gated by per-event sender-authorization, device-binding, a signed-transition audit (hash-chained pre/post state), and timestamp watermarks (`lastMembershipEventAt`, `lastMetadataEventAt`). The convergence model is "last-writer-wins by event timestamp" with snapshot reconciliation, which is robust for serial admin actions and replay/idempotency but fragile under concurrency, clock skew, and cross-event ordering. Add/remove use cases are serialized and stale-gated; role-update is notably not, and full-config snapshots carried by membership events can overwrite independently-versioned metadata.

**Strengths to preserve:**
- Strong inbound authorization model: `_isAuthorizedMembershipEventSender`, `_isBoundSystemEventSenderDevice`, and `verifyGroupTransitionAudit` (Ed25519 signature + canonical payload + pre/post state-hash chaining) prevent forged or non-admin membership events from being applied, closing the SC-001/SC-015 trust gap described in doc 57.
- Solid idempotency/replay handling: signed-audit hash dedupe (`_acceptedSignedTransitionAuditHashesBySourceId`), deterministic timeline message IDs, `_isDuplicateMembersAddedReplayAlreadyApplied`, and watermark equal-version replay tolerance mean duplicate authorized events do not produce duplicate UI side effects.
- Local-then-broadcast mutations have explicit rollback on bridge/publish failure (add/remove/role use cases revert the repo write; remove restores the snapshot and deletes the cutoff timeline; leave captures a rollback snapshot), reducing the window for divergent local state.
- Removal correctness across rejoin is carefully handled: removed-member snapshots, `member_removed` cutoff timestamps, and epoch/rejoin window checks in `handleIncomingGroupMessage` prevent removed members from re-injecting traffic and handle re-add ordering.
- Dissolve is treated as a frozen terminal state with a graceful recovery-gap UX (`DissolveGroupResult.bridgeError` still commits locally and shows a recovery snackbar rather than failing hard), and post-dissolve events are ignored except `group_dissolved`.
- Mutations are blocked during recovery via `isGroupRecoveryInProgress()` and add/remove serialize through `runGroupMembershipMutationLocked`, avoiding interleaved partial commits.

## Crypto & key management (`crypto-keys`)

**Score:** reliability 2/5 · UX 2/5

**Current state:** Group messaging uses a per-group symmetric AES-256-GCM key with an integer epoch. New members receive the current key+epoch directly inside the encrypted invite payload; existing members receive rotated keys via signed, ML-KEM-encrypted 1:1 "group_key_update" messages with an inbox store-and-forward fallback. Rotation is admin-only, serialized per group, and uses a pending-draft so an interrupted rotation can be resumed idempotently. The Go node keeps current+previous key with a 30-second grace window so in-flight previous-epoch messages still validate/decrypt. When a member cannot decrypt (offline-missing-key or live decryption failure), a pending-key-repair row + placeholder message is created and retried when a newer key arrives. The cryptographic primitives and the signed-transition/audit verification on key updates are solid; the main reliability gaps are in how undecryptable messages are recovered (passive, no active key pull), the very short grace window, and an all-or-nothing rotation gate.

**Strengths to preserve:**
- Key-update messages are strongly authenticated: canonical signed payload + Ed25519 signature + signed transition audit + recipient device binding + sender rotate-keys permission check, all verified before the key is applied (group_key_update_listener.dart:203-401). This prevents a malicious member from injecting a forged group key.
- Rotation is serialized per group via _withSerializedGroupRotation and uses a persisted pending-draft (rotate_and_distribute_group_key_use_case.dart:204-270, 477-511), so a crash mid-rotation resumes the same epoch/key instead of minting divergent keys.
- Rotation promotes the admin's own key LAST, only after every required recipient confirms delivery (rotate_and_distribute_group_key_use_case.dart:317-358), avoiding the admin getting ahead of the group.
- DB key insert is idempotent on identical material and hard-fails on same-epoch-different-material conflict (group_keys_db_helpers.dart:20-61), surfacing key divergence instead of silently corrupting state.
- The Go grace window correctly accepts AND decrypts only the immediately-previous epoch during grace, rejects removed senders even during grace, and rejects unknown future epochs (pubsub.go:1221-1261; covered by extensive GK016-GK020 tests).
- Bounded key retention (8 generations) with stale-historical-key rejection prevents unbounded key growth and replay of very old epochs (group_key_retention_policy.dart; group_key_update_listener.dart:441-454).

## Relay server inbox (`relay-inbox`)

**Score:** reliability 3/5 · UX 3/5

**Current state:** The relay group inbox is a store-and-forward backlog for offline members, fronted by a libp2p stream protocol (`group_store`, `group_retrieve`, `group_retrieve_cursor`, `group_history_repair_range`) in inbox.go, behind a `GroupInboxBackend` interface with memory and Redis implementations. Storage is per-group FIFO capped at 500 messages with a 7-day TTL, deduped by `extractMessageId`, with per-message recipient ACLs and authorized retrieval. The production cursor path (`RetrieveWithCursorAuthorized`) loads the entire group via `RetrieveSince(groupId, 0)` and paginates in the store layer; gaps detected at a missing cursor are surfaced as history-gap repair metadata. Reliability posture is reasonable for a single instance under light load, but several cross-instance, cap-eviction, and cursor-continuation behaviors can silently drop or stall an offline member's backlog.

**Strengths to preserve:**
- Per-message recipient ACL is enforced on every read path (RetrieveAuthorized / RetrieveWithCursorAuthorized / RetrieveHistoryRepairRangeAuthorized) and group_store rejects from != remotePeer, so a member only sees messages addressed to them.
- Dedup is content-aware: a duplicate messageId merges recipient sets (mergePeerIds) rather than creating a second copy, and conflicting same-id/different-body is rejected, keeping a single canonical copy per message.
- Cursor pagination is covered by strong exact-once tests (TestGroupInboxStore_CursorPaginationExactOnceAcrossPages, GI-017 120-message authorized pagination) including cross-instance Redis failover tests.
- Client drain is resilient: idempotent on messageId, Phase1/Phase2 split keeps the SQLCipher write lock short, stale-cursor and max-pages guards prevent infinite loops, and a synthetic since-cursor provides a durable fallback when the relay returns no opaque cursor.
- TTL handling is defense-in-depth: read paths filter by cutoff in addition to the periodic Prune(), so expired messages are never served even before a prune cycle runs.
- Redis store/ack/retrieve use WATCH/MULTI optimistic transactions with retry, avoiding lost updates under concurrent writers across relay instances.

**Findings (7):**

### `relay-inbox:cursor-id-space-cross-instance` — Cursor IDs are not portable across backends/restarts: memory uses a per-process counter, Redis a global INCR, so failover/restart can break continuation

`high` (raised: high) · reliability · verdict: **confirmed** · effort: medium · reviewer-confidence: high

- **User impact:** If the relay restarts with the memory backend (or a deployment ever mixes memory and Redis, or two Redis-backed relays share a group but a key is recreated), a client resuming with a previously-issued opaque cursor will not find it. Pagination silently restarts from the head, so the offline member re-downloads/re-processes the whole backlog (slow, jittery catch-up) or, combined with eviction, skips messages. - **Verifier:** Memory backend uses in-process b.idCounter (backend_memory.go:313 field, :372 b.idCounter++) which is never persisted nor seeded from max existing ID on load (newMemoryGroupInboxBackend backend_memory.go:318-324 starts it at zero). ## Multi-device convergence (`multi-device`)

**Score:** reliability 1/5 · UX 1/5

**Current state:** The repo has a first-class device-identity data model (GroupMemberDeviceIdentity, devices_json column via migration 062) and a declared shared-vs-device-local policy (group_multi_device_policy.dart). The receive path is "self-aware": handleIncomingGroupMessage can recognize a same-account sibling delivery and persist it as outgoing 'sent' history rather than unread incoming, and send/receive both resolve a sender device binding before admitting traffic. However, the actual machinery to make two devices of one user CONVERGE in production is largely absent: there is no flow that materializes a group, its members, or its keys onto a second device, and there is no flow that admits/persists a newly-seen sibling device into any member's device roster. The accepted convergence "proof" depends on a test-only helper (mirrorJoinedGroupState) and a device-aware fake pubsub, neither of which exists at runtime. The net posture is that the contract is documented and unit-modeled, but a real second device cannot join, decrypt, or send without manual data copying.

**Strengths to preserve:**
- Receive path is genuinely self-delivery aware: _isLocalSelfDelivery + _reconcileOutgoingSelfEchoDuplicate let a sibling device persist the user's own message as status 'sent'/isIncoming:false instead of a spurious unread incoming row (handle_incoming_group_message_use_case.dart:861-872, 927-989).
- GroupMemberDeviceIdentity is a clean, forward-compatible model with robust JSON alias handling, status/revocation, and a legacy single-device fallback (legacyDeviceIdentity / activeDevicesWithLegacyFallback) so pre-062 members keep working (group_member.dart:79-227, 388-413).
- Key rotation already fans out per-device (distributionTargets expands member -> deliverable devices, each with its own ML-KEM encryption + signed audit), so the distribution plumbing is ready for true multi-device once rosters are populated (rotate_and_distribute_group_key_use_case.dart:170-176, 746-758).
- The shared-vs-device-local policy is encoded once in a typed seam (group_multi_device_policy.dart) rather than scattered as stringly-typed assumptions, giving a single place to enforce the contract.
- Sender-device binding is validated symmetrically on both the Dart send/receive paths and the Go publish path, so the security envelope (no impersonation by unbound transport peers) is consistent.

## Media (`media`)

**Score:** reliability 3/5 · UX 3/5

**Current state:** Group media is an encrypted blob pipeline: the composer pre-persists durable upload_pending rows + content hashes, uploadMedia() keygens/encrypts/uploads to the relay with a member-derived AllowedPeers ACL, sendGroupMessage publishes descriptors over pubsub v3, and receivers auto-download, verify SHA-256 + MIME signature + size, decrypt, and only then mark done. Tie the shown notification's messageId into the dedupe gate so a later successful drain doesn't double-notify.
- **Affected files:** `lib/features/push/application/handle_foreground_remote_message_use_case.dart`, `lib/features/push/application/background_push_notification_fallback.dart`, `lib/main.dart`
- **Verifier:** handle_foreground_remote_message_use_case.dart:68-78 returns notificationNeeded only for group drain errors (:74-75), drained otherwise. main.dart:3185 calls showForegroundPushFallbackNotificationIfNeeded which (background_push_notification_fallback.dart:48-68) builds buildBackgroundPushFallbackNotification — _resolvedTitle/_resolvedBody force the generic 'New Message'/'You have a new message' via _usesProtectedMessagePreview for group/new_message types (:124-143) and perform no decrypt and no isMuted check. So the degraded foreground path is both contentless and mute-blind, and a later dead tap is possible (per the dead-tap finding). Confirmed; severity low/ux is appropriate since it is a degraded error path.

## Dropped as false-positives

Findings the adversarial verifier refuted (kept here for transparency):

- **`invites:partial-commit-on-bridgeerror-keeps-invite-actionable`** — Accept couples invite-consumption to best-effort drain: one transient failure leaves a re-tappable invite over a stale group with a success-flavored error
  - _Why dropped:_ The central claim is refuted by the actual code and a pinning test. In acceptPendingGroupInvite, the success-but-drain-failed branch (accept_pending_group_invite_use_case.dart:321-332) and the join-bridgeError branch (:341-366) BOTH call _commitAcceptedPendingInvite when group != null, which deletes the pending invite and records the consumption/welcome tombstone (:563-583). Since materializeAcceptedGroupInvitePayload always saves the group (handle_incoming_group_invite_use_case.dart:872) before the join attempt, group is non-null on every bridgeError exit, so the invite IS consumed. The finding's evidence 'Both bridgeError exits return before _commitAcceptedPendingInvite' is a misread. Test GCA-004 (accept_pending_group_invite_use_case_test.dart:581-664 and :1179+) confirms: after a RELAY_UNAVAILABLE drain failure and a JOIN_FAILED join failure, getPendingInvite returns null, getConsumedInvite is non-null, the retry returns notFound, and group:publish is logged exactly once across both attempts (no re-fan of member_joined). So the card does NOT re-render actionable and does NOT re-fan duplicates. The only accurate sub-point is cosmetic: the snackbar text group_invite_joined_recovery ('Joined {name}, but recovery is still catching up', app_en.arb:1180) is shown while GroupRecoveryGate is not engaged on this path (gate only used in handle_app_resumed.dart:148, pending_message_retrier.dart:254, startup_router.dart:580) -- a label-accuracy nit, not a reliability bug.
- **`membership-lifecycle:role-update-self-echo-joinedat-reset`** — Receiver role-update apply can reset member joinedAt to event time, corrupting removal/rejoin windows
  - _Why dropped:_ Refuted. (1) _handleMemberRoleUpdated calls _applyAuthoritativeGroupConfigSnapshot(groupId, groupConfig, eventAt: eventAt) WITHOUT eventMemberPeerIds (group_message_listener.dart:3541-3545), so eventMemberPeerIds defaults to null. (2) _resolveAuthoritativeSnapshotJoinedAt (:4685-4710) only advances joinedAt for an existing member when eventAt != null AND eventMemberPeerIds != null AND it contains the peer (:4694-4696); with eventMemberPeerIds null this branch is skipped and it returns existingJoinedAt unchanged (:4702). (3) Even that is moot: GroupMember.fromConfigMap resolves joinedAt as configJoinedAt ?? existing?.joinedAt ?? joinedAt ?? now (group_member.dart:530-534), and toConfigJson() always emits joinedAt (:558), so every member in the role event payload and in buildGroupConfigPayload snapshots carries the sender's real joinedAt; configJoinedAt takes precedence over the passed eventAt in both the first saveMember (:3505-3520) and the snapshot saveMember (:4562-4576). A role change therefore does not move an existing member's joinedAt to event time. The proposed fix (pass eventMemberPeerIds: null) is already the current behavior.
- **`relay-inbox:authorized-page-all-unauthorized-stop`** — A full page where every message is unauthorized returns an empty result with no nextCursor, stalling catch-up before reaching the member's own messages
  - _Why dropped:_ The scan is NOT bounded by `limit` raw rows. RetrieveWithCursorAuthorized (inbox.go:999-1009) iterates from startIdx over ALL remaining messages, appending only authorized ones, breaking only when len(result)==limit. A long unauthorized prefix or interleaved unauthorized block is therefore fully traversed within a single call; the function returns empty only if there are ZERO authorized messages in the entire remaining range (correct end-of-backlog). The next-cursor lookahead (inbox.go:1015-1021) scans to end-of-list for any further authorized message before clearing the cursor, so an all-unauthorized tail correctly terminates. Test TestHandleInboxStream_GroupRetrieveCursorSkipsUnauthorizedMessages (inbox_test.go:1452-1519) proves the exact scenario: recipient-1 / intruder-only / recipient-2 stored, limit=1 returns recipient-1 + nextCursor, next page skips the sandwiched intruder and returns recipient-2 with empty cursor. The finding's own evidence already concedes the scan is len(result)==limit bound, not raw-row bound. No premature stall exists.
- **`multi-device:sibling-self-delivery-depends-on-roster`** — Sibling self-delivery recognition silently fails when the sibling device isn't in the roster
  - _Why dropped:_ _isLocalSelfDelivery (handle_incoming_group_message_use_case.dart:861-872) has a PRIMARY roster-independent path at line 868: 'if (senderId == localRecipientPeerId) return true'. On the wire senderId is the account peerId (group_message_listener.dart:605) and localRecipientPeerId is the local account peerId (handle:64-67 from selfPeerId, resolved via _resolveSelfPeerId/_getSelfPeerId, group_message_listener.dart:207-225,699). A true same-identity sibling shares the account peerId (libp2p ID derives from the identity key, node.go:239,368), so senderId==localRecipientPeerId is TRUE and self-delivery is recognized WITHOUT any roster/device-transport resolution. The roster-dependent path (lines 869-871 via _findLocalRecipientMemberByDeviceTransport) is only a secondary fallback for the case senderId != localRecipientPeerId, which does not arise for genuine same-identity siblings. The convergence integration test confirms this works with the tablet's own device NOT registered in the mirrored roster yet still recording the phone's message as isIncoming:false/status 'sent' (convergence_test:107-112). The claim that self-delivery 'hinges on resolving the sibling's transport peer back to the account' is incorrect.
- **`media:in-doubt-pending-media-stranded-on-retry`** — In-doubt (pending) media sends are stranded: retry uploads the blobs but aborts the re-publish, so recipients never get the message
  - _Why dropped:_ The cascade is not reachable in real flows because its premise (in-doubt message with media still in 'upload_pending') does not occur. In ALL composer send paths, media is uploaded to downloadStatus 'done' BEFORE sendGroupMessage is called: durable image path sets 'done' in _buildStableUploadedAttachmentFromPlan (group_conversation_wired.dart:1502,1524,1539+), legacy image path sets 'done' (group_conversation_wired.dart:1767), voice path sets 'done' in _buildStableVoiceAttachment (group_conversation_wired.dart:3260). The in-doubt branch then persists those same 'done' attachments via _persistOutgoingMedia, which saves attachments as-is (send_group_message_use_case.dart:340-342) — it does NOT set 'upload_pending'. The finding's key evidence ('media is persisted as upload_pending at 897-912') is factually wrong. Crucially, the retry sweep only loads attachments via getUploadPendingAttachments() → dbLoadUploadPendingAttachments which queries WHERE download_status='upload_pending' (media_attachments_db_helpers.dart:315-320). An in-doubt message whose media is 'done' is therefore never even enumerated by the sweep, so _lateGroupSendAbortReason and the 'message_status_pending' abort (retry_incomplete_group_uploads_use_case.dart:622-624) are never reached for it. _lateGroupSendAbortReason rejecting 'pending' is dead/defensive code on the live path. The existing tests exercise 'failed'/'sending' rows with upload_pending media, never the 'pending'+upload_pending combination, consistent with it not arising.
- **`media:silent-drop-of-rejected-gallery-media`** — Gallery picks that fail MIME/signature validation are silently dropped with no user feedback
  - _Why dropped:_ Misreads the code paths. In _pickFromGallery the per-pick loop calls _preparePendingMedia (group_conversation_wired.dart:2599), which throws _RejectedPendingGroupMediaException ONLY for the GIF-too-large case (lines 936-941) — and that case DOES show a user-visible snackbar via _showGifTooLargeMessage() before throwing. There is NO MIME/signature validation in _preparePendingMedia at pick time. The MIME/signature throw the finding cites (lines 1276-1300) lives in _prepareDurableGroupMediaUploads, which runs at SEND time (invoked from the send flow at line 1672), not in the gallery pick loop; lines 3009-3030 are the voice-record path. So a MIME/signature-invalid gallery file is NOT dropped at pick time — it is added to the composer, then rejected at send, where the exception is caught at the generic send catch (line 1893) and _restoreComposerSnapshot (line 1899) restores the attachments into the composer and marks the row 'failed' (lines 2140-2149). The media therefore does not silently 'vanish'; it returns to the composer with a failed row. The finding's bare-'continue'-only-FLOW-log description of line 2604 is also inaccurate: that catch is a bare continue with no log, and it only ever fires for GIF-too-large (already snackbar'd).
