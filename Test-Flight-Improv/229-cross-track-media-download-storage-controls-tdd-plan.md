## Problem And Evidence

- Behavior to improve: users need per-lane and per-media-type automatic-download controls, a storage inventory, and a safe “remove local copy but keep message” action.
- Impact: HEAD consumes data/storage automatically and conflates an app-private downloaded copy with a user-exported file or a deleted message.
- Confirmed current mechanism: direct receipt calls `_autoDownloadMedia` without a user policy at `lib/features/conversation/application/chat_message_listener.dart:180` and triggers it at `:631`.
- Confirmed bypass: `ConversationWired._recoverVisibleMedia` independently invokes `downloadMediaFn` for pending/downloading/retryable-failed direct attachments after initial load, staged drain and older-page load (`lib/features/conversation/presentation/screens/conversation_wired.dart:1178`, `:1343`, `:1381`, `:1393`). Listener-only policy wiring can therefore pass while mounted recovery still transfers denied media.
- Confirmed current mechanism: group load calls `_downloadPendingMedia` at `lib/features/groups/presentation/screens/group_conversation_wired.dart:1344`; discussions and announcements share this wired screen.
- Confirmed current model gap: `MediaAttachment.downloadStatus` documents pending/downloading/done/failed at `lib/features/conversation/domain/models/media_attachment.dart:42` and has no user-evicted state.
- Confirmed file boundary: app-owned media lives under Documents `media/<scope>/<blob>` and `MediaFileManager.deleteFile` routes through ownership telemetry (`lib/core/media/media_file_manager.dart:273`).
- Confirmed destructive/concurrency gap: download promotion renames the staged file to the canonical path and then unconditionally writes `local_path`/`done` by attachment ID (`lib/features/conversation/application/download_media_use_case.dart:1940`, `:1945`; `lib/features/conversation/domain/repositories/media_attachment_repository_impl.dart:223`). `MediaFileManager.deleteFile` delegates to telemetry rather than enforcing scope/path ownership, and group retry contains a raw `File.delete` (`lib/features/groups/presentation/screens/group_conversation_wired.dart:2414`).
- Confirmed inventory/UI gap: plan 228 pages only image/video library kinds (`lib/features/conversation/domain/models/media_library.dart:10`) with a 100-row ceiling; one page cannot be an exact total. `MediaGridCell` renders any non-done image/video as loading and only exposes Retry for retryable integrity failures (`lib/shared/widgets/media/media_grid_cell.dart:199`, `:216`), so a new `evicted` state would be neither truthful nor actionable.
- Confirmed product constraint: relay media expires after seven days (`go-relay-server/media.go:21`), so an evicted old copy may be permanently unavailable; UI must not promise cloud-style re-download.
- Confirmed settings mechanism: image/video preferences already use SecureKeyStore load/save and focused settings sheets (`lib/features/settings/application/image_quality_preference_use_cases.dart:6`, `lib/features/settings/presentation/screens/settings_wired.dart:215`).
- Confirmed dependency seam: plan 228 makes every message-scoped attachment read/write/delete owner-aware, reserves `unresolved` for fail-closed legacy rows, binds cursors to scope/filter, and caps pages at 100. Plan 229 must consume those contracts rather than infer storage ownership from `message_id` or conversation kind.
- Existing coverage: direct/group download retry and media file manager tests cover transfer integrity and deletion primitives, not user policy or storage management.
- Missing coverage: policy decisions, direct listener plus mounted-recovery gating, three-lane wiring, visible manual retry, owner-isolated/concurrency-safe eviction, exact canonical-path authorization, failure/restart reconciliation, unresolved-row exclusion, all-media multi-page totals, eviction durability through ordinary replay, arbitrary-path preservation, settings restart, and no-retry-loop behavior.
- Refuted findings: “clear cache can always re-download later” is refuted by the seven-day relay TTL.
- Unresolved findings: precise roaming detection is not exposed by current dependencies. This plan treats roaming as cellular and labels that accepted difference; a future native network-context owner is required before a distinct roaming toggle is claimed.
- Affected production, test, and gate files: new settings domain/application models; `ChatMessageListener`; direct/group conversation wired recovery and retry surfaces; `MediaAttachment`; media repository conditional transitions; download use case; media storage manager/path validator; all-media storage query/page types; grid rendering; settings screen/wired/l10n; focused tests. No schema migration.

## Scope Contract And Guard

In scope:
- Add `MediaConversationKind {oneToOne, discussion, announcement}`, `MediaDownloadNetwork {wifi, cellular}`, versioned `MediaDownloadPreferences`, and pure `MediaDownloadPolicy.shouldAutoDownload`.
- Preserve HEAD defaults on upgrade: normal supported image/video/audio/file types remain enabled until the user changes a setting.
- Inject one policy/network decision capability into direct listener, direct mounted/paged visible-media recovery, and shared group wired download entry points; derive discussion vs announcement from the existing group type. Every automatic entry point checks policy immediately before transfer, while explicit Retry is separately marked user-initiated.
- Add `kMediaDownloadStatusEvicted`; auto-download/recovery and ordinary attachment replay ignore/preserve it, while an explicit user retry may transition it to pending/downloading through an owner-aware state API.
- Add `MediaStorageManager.inventory` and `clearLocalCopy`: require a complete `MediaLibraryScope` plus attachment ID/MIME. Derive the one expected relative path `media/<scope.id>/<attachmentId><extensionFromMime(mime)>`; authorize deletion only when the stored value is that exact relative path or the normalized current-container absolute equivalent, the resolved target equals the normalized expected target, and containment remains inside the exact scope directory. Substring-remapped/misleading legacy absolute paths, wrong scope, wrong MIME/extension, symlinks, exports and arbitrary paths fail closed before file mutation. Legacy absolute rows that are not the current exact canonical absolute path require a separate path-repair write before Clear; `resolveStoredPath` is not an authorization decision.
- Coordinate eviction and download with owner/scope/path/status compare-and-set transitions. Download may claim only an allowed state into `downloading` and may commit canonical `local_path`/`done` only from its own `downloading` claim. Clear returns `busy` with zero mutation for `downloading`; otherwise it atomically claims the exact `(owner, attachmentId, expected canonical localPath, done)` row as `evicted` while retaining `localPath`, then deletes the exact canonical file, then conditionally nulls `localPath`. A late download commit after another state change fails closed and removes only the exact canonical artifact it promoted.
- Eviction failure semantics are durable and truthful: if the initial DB claim fails, no file is touched; if file deletion fails, keep `evicted` plus the expected path and return `cleanupFailed` so Clear is retryable; if the final path-null write fails after successful deletion, keep `evicted` with a stale path and reconcile it to null on fresh manager/inventory after proving the canonical file is absent. Auto recovery never treats either durable `evicted` form as pending. No transaction or DB write is held across file I/O.
- Add a separate owner-scoped `MediaStoragePage` query for `image`, `video`, `audio`, `file`, and `all`. It reuses plan 228 direct/group visibility and tombstone rules but does not broaden the visual `MediaLibraryRepository` contract. Direct inventory uses `MediaLibraryScope.direct(contactPeerId)`; discussion and announcement use `MediaLibraryScope.group(groupId)`. Inventory follows opaque cursors with literal pages of 100 until `nextCursor == null` and reports exact aggregate counts/bytes across all pages; it never reuses a cursor after scope/type changes.
- Add a Settings “Media & storage” route with lane/type/network controls and scoped storage totals/actions.

Must preserve:
- Direct/group content-hash, encryption, retry budget, terminal failure, and relay-ack behavior -> existing download tests; `GREEN sentinels`.
- Manual unavailable/evicted-media Retry remains visible and user-authoritative in direct, discussion and announcement surfaces even when auto-download is disabled -> TC-229-04/09V.
- Message and sibling attachment persistence during local-copy eviction -> TC-229-06.
- Plan 228 owner/bookmark/playback/completed-path state survives the new `evicted` transition and all ordinary direct/group replays -> TC-229-12.

Hard `Do not`:
- Do not change upload quality, relay TTL, relay ack/delete, message delivery, group publish/auth, go-libp2p, or notification behavior.
- Do not interpret “Save to Photos/Files” as app-cache download; native egress is plan 227.
- Do not delete gallery/exported/arbitrary absolute files.
- Do not mark an evicted attachment `done`, auto-recover it on mount, or promise re-download availability.
- Do not add unbounded filesystem scans on startup or conversation build.
- Do not authorize deletion merely because `resolveStoredPath` finds a `/media/` substring, hold a DB transaction across file I/O, delete before the durable evicted claim, or let an unconditional download completion overwrite `evicted`.
- Do not infer attachment owner from `message_id`, default an omitted owner to direct/group, expose or mutate `owner_lane='unresolved'`, reuse a cursor across a different scope/filter, or request a page outside `1..100`.

Deferred / accepted difference:
- Separate roaming detection/toggle -> future native network-context plan; cellular policy applies while roaming on HEAD-supported platforms.
- Per-chat exceptions -> lane library plans may add them after global/per-lane controls prove stable.
- Batch export -> plans 233/237/241; private-media forced download rules -> plans 234/238/242.

Dependencies:
- Plan 228 must land first. Its DB v96 `MediaOwnerLane`, owner-aware repository transitions, fail-closed `unresolved` rows, signed scope/filter cursor, and `kMediaLibraryMaxPageSize = 100` are hard prerequisites; plan 229 adds no DB version.
- Existing SecureKeyStore, `connectivity_plus`, media download use case, and file ownership guards.

### Test Notes

- TC-229-09 contains separate named 1:1 and group/announcement cases in one shared integration file and is registered in both owning arrays. If implementation must split the file, both replacement paths remain mandatory and keep the same lane registrations.
- TC-229-03R distinguishes automatic recovery from explicit retry: the same row/policy fixture must observe zero transfer during mount/reload/page recovery, then exactly one transfer only after the explicit action owned by TC-229-09V.
- TC-229-06/06F use a file gateway so DB-claim, delete and final-path-clear failures are injected independently. `evicted + non-null canonical path` is a deliberate cleanup-pending state, not successful byte reclamation; storage totals continue counting the existing bytes until deletion succeeds.
- TC-229-06C requires conditional row-count assertions. An update that reports zero affected rows is a lost claim, never success. The download path may delete only the exact artifact it promoted after a failed final commit.
- TC-229-07 does not grandfather arbitrary legacy absolute paths. A path-repair operation may first prove/canonicalize a legitimate current app-owned copy and write the exact relative path; Clear itself never treats `/media/` substring extraction as authority.
- Storage inventory is user-invoked and pages the dedicated all-media query to exhaustion. Its strict 205-row fixture rejects the wrong scope/type/cursor/limit and asserts more than the first 100 rows contribute to exact totals. This is bounded per page and user-triggered; no timer/startup filesystem scan is permitted.
- TC-229-12 extends plan 228 TC-228-08 after `evicted` exists; it must not weaken explicit bookmark/playback clears or the completed-local-path preservation already owned there.

## Risks And Blind Spots

- Default changes or a bypassed mount path could strand/transfer unexpected media -> TC-229-01/03/03R preserve defaults and gate every direct automatic seam.
- Group/announcement discriminator could collapse -> TC-229-04.
- Eviction can become data loss after relay expiry -> UI/result copy and TC-229-09 are truthful; no cloud guarantee.
- Lifecycle / derived-state durability: TC-229-05/06/06F/09 reopen fresh settings/repositories/managers and reconcile cleanup-pending paths.
- Sibling-surface consistency: TC-229-03/03R/04/09V cover automatic and explicit actions in all three lane kinds.
- Destructive-action side effects: TC-229-06/06F/06C/07 assert transition ordering, files, rows, keys, bookmarks, messages and siblings under concurrency/failure.
- First-page totals masquerade as aggregate storage -> TC-229-08 requires all four media types and 101+ eligible rows across opaque pages.
- Invariant re-verification under new transitions: ordinary replay rechecks and preserves local owner/state in TC-229-12; evicted->manual downloading re-enters integrity/size/auth checks in TC-229-02/09.
- Local state must not become transport policy -> TC-229-11 pins DB-only serialization.
