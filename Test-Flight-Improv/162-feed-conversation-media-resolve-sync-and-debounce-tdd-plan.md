## Exact Problem Statement
On feed mount and on every per-contact feed refresh, the media-resolve loop **awaits** `MediaFileManager.resolveStoredPath` once per attachment. Each `await` re-invokes `getApplicationDocumentsDirectory()` (`media_file_manager.dart:225-259`, no memoization — the async path never reads the static cache), yielding the event loop on a `path_provider` platform-channel hop. With N attachments this serializes into N sequential awaits on the UI isolate — a startup/mount and refresh CPU spike. The fix is already half-built: a synchronous twin `resolveStoredPathSync` (`media_file_manager.dart:56-95`) does the identical string work over a startup-seeded static `_cachedDocumentsDir` (seeded at `main.dart:401`, after `getApplicationDocumentsDirectory()` at `:395`, before any feed/conversation load), and it is **already the production render-boundary resolver** (`media_thumbnail_image.dart`, `media_grid_cell.dart`). Three loaders still await the async twin instead.

Separately, `feed_wired.dart` has **zero** debounce (grep `Timer|debounce` = 0): the outgoing-repo-change listener (`_startListeningForOutgoingMessageChanges`, `feed_wired.dart:1226-1265`) fires a full per-contact materialization (`unawaited(_applyIncomingContactMessageToFeed)` at `:1250-1255` for live messages, `unawaited(_refreshContactFeedItem)` at `:1241-1247` for deleted/hidden) on **every** `sent`/`delivered`/`failed`/delete event; `_onIncomingChatMessage` (`:1275-1279`) calls `unawaited(_applyIncomingContactMessageToFeed(message))` at `:1278`. During a drain burst (131/145/146/147 land N rows → N repo-change emits), this re-materializes N times back-to-back.

What must improve: (A) the per-attachment media resolve drops its `path_provider` platform-channel hop. The two **1:1** loops (`load_conversation_use_case`, `load_feed_use_case`) become **synchronous** string maps (zero event-loop yields). For the **group** path the hop is removed too, but `_resolveGroupFeedAttachmentForDisplay` stays `async` (it still awaits `GroupMediaMimePolicy.validateFile`, `group_feed_media_verification.dart:144`) and the serial loop in `resolveGroupFeedMediaForDisplay` (`:15-22`) is untouched — so the group win is **the channel hop only**, not "zero yields"; (B) a burst of repo-change/incoming-message events that target the **same contact** collapses into **one** trailing materialization pass.

What must stay unchanged (→ preserved-green sentinels): the 127/128 null-cache passthrough (`MEDIA_RESOLVE_SYNC_NO_CACHE`) and on-iOS stale-container re-rooting; the group `existsSync`/`lengthSync` integrity verify + the full `GROUP_FEED_MEDIA_*` flow-event sequence (134/135 group); the 134/135 incremental snapshot semantics (last-write-wins per contact, delete/hide not swallowed, unread-count refresh); and the 145/131 conversation-screen drain path (`conversation_wired` `_drainAndReloadOnce`, the "catching up" banner, `NOTIFICATION_TAP_TO_LIVE_MESSAGE_TIMING`) which must stay **independent** of the feed debounce.

**In scope (Phase B — debounce, host-widget locked, land SECOND):**

Add a trailing per-contact coalescer in `feed_wired.dart` around the repo-change/incoming-message reload triggers (the `_startListeningForOutgoingMessageChanges` listener body `:1239-1256` and `_onIncomingChatMessage` `:1278`). A short trailing `Timer` (≈16-50ms) keyed by `contactPeerId` collapses a same-contact burst into one materialization, cancelled in `dispose` (`:2303`).
   - **Correctness rule (do NOT "enqueue the latest event and replay its branch").** `_applyIncomingContactMessageToFeed` (`:944-1010`) is an **incremental, in-memory single-message upsert** (`_mergeThreadMessages` `:852-865`, upsert core `:857-861`) — it reads only the current in-memory snapshot (`_threadForContact` `:973`), never re-reads the DB, and never touches any other message. So a coalescer that keeps only the latest event for a contact and replays its branch silently drops earlier messages in two ways, **both of which must escalate to a full refresh**:
     - **delete-then-send:** `delete(X)` then `sent(Y)` (latest = Y → `apply(Y)` leaves X in the thread — the delete is lost).
     - **distinct-id burst (F1, pass 2):** two **distinct non-delete** ids `sent(X)` then `sent(Y)` for the same contact, where X is not already in the in-memory snapshot (latest = Y → `apply(Y)` upserts only Y; X was never applied → X silently vanishes from the rendered feed). This is the exact drain-burst pattern the plan cites as the debounce motivation (§Exact Problem Statement, 131/145/146/147 land N rows).
     The robust rule: **per contact, escalate that contact's single flush to a full `_refreshContactFeedItem(contactPeerId)`** (`:630-673`, a `loadContactFeedSnapshot`→`replaceContactSnapshot` — inherently last-write-wins from DB, subsumes delete+edit+send and surfaces every persisted id) **if the burst contained ANY `isDeleted`/`isHidden` event (`sawDestructive`) OR more than one distinct message id (`sawDistinctIds`)**. Both flags are **sticky** (a later event must NOT clear them). The incremental apply may stay ONLY for the hot **all-same-single-id, no-delete** burst (repeated status flips on one id).
   - **Full-refresh escalation is SAFE for both sources (F1 correction, pass 2):** the earlier draft argued "do not blanket always-full-refresh because `_onIncomingChatMessage`'s message may not be persisted yet." That premise is **refuted** — `chat_message_listener` emits on `incomingMessageStream` only **after** persistence (primary emit `chat_message_listener.dart:572` follows the `stored` state, `:533` "message is already persisted", `:59` class doc "broadcasts persisted"; the media re-emit `:224` re-emits an already-stored message). So a full `_refreshContactFeedItem` **does** surface a live incoming message. Keep the incremental apply purely as a CPU optimization for the single-id status-flip burst, **not** because a full refresh would miss data. (If execution ever uncovers a genuinely not-yet-persisted incoming emit, the documented fallback is a per-`contactPeerId` pending **id→message map** flushed by applying ALL pending ids — heavier, used only if the persistence guarantee breaks.)
   - **Preserve two side-effects the single funnel hides:** (1) the `refreshUnreadCount` asymmetry (the listener passes `false` at `:1245`/`:1253`; `_onIncomingChatMessage` passes the default `true` at `:1278`, default `:946`; the recompute is `_loadTotalUnreadCount` `:495-508`, gated at `:662`/`:735`/`:993`). Because Phase B funnels BOTH sources into one per-contact queue, the coalesced flush must honor the asymmetry as an **OR-accumulated sticky `sawRefreshUnread` flag** — set true if ANY enqueued event for the contact would have passed `true` (the incoming source) — and flush with `refreshUnreadCount: sawRefreshUnread`, NOT the latest event's value. A "false-wins / latest-event-wins" coalescer would silently drop the unread-badge recompute when a same-contact burst mixed an incoming live message with outgoing status events (F3, pass 2). (2) the **eager** `_sessionReplies.clear(message.contactPeerId)` at `:1277` (must run on event arrival, NOT be deferred behind the timer).
   - Independent of `conversation_wired` drain (145).
