## Exact Problem Statement

The self-removal B3 path deliberately keeps the group row and old messages as a read-only shell, but removes the local self-member row and all keys. Every active-group exit path then attempts voluntary-leave prework. That prework requires the self member that B3 removed, so it returns `skippedMemberNotFound`; the wrapper turns that into `preworkFailed`, and the UI reports “Failed to leave group.” Repeating the action cannot repair the state.

What must improve: a shell produced by a verified self-removal must expose a confirmed, local-only delete from Orbit, Group Info, and both stuck-row callbacks. It must remove the visible shell, live membership/crypto state, and membership-instance pending work while making zero native leave, publish, or inbox calls.

What must stay unchanged: ordinary voluntary leave and its signed broadcast/key-rotation/native sequence; last-admin blocking and sole-admin recovery; pending-role synchronization; dissolved-group local deletion; accepted re-invite materialization; read-only retained history before the user confirms deletion; pending invitations themselves; wire, bridge, Go, relay, and native-handler contracts.

## Root Cause (Verify → Refute Confirmed)

### Confirmed mechanism

1. `lib/features/groups/application/group_message_listener.dart:3591-3617` selects B3 for self-removal. `_retainSelfRemovedLocalHistory` at `:3809-3874` awaits native `group:leave`, removes the self member at `:3840`, removes every group key at `:3841`, writes the removal timeline at `:3845-3858`, and intentionally retains the group row.
2. `lib/features/groups/application/group_exit_policy.dart:11-17,73-104` has no removed-shell disposition. After dissolved and pending-role checks, a non-admin shell maps to `leave`; a removed admin can retain stale `myRole == admin` and map to another non-delete branch.
3. `lib/features/groups/application/broadcast_voluntary_leave_use_case.dart:87-92` returns `skippedMemberNotFound` when the self member is absent. `leave_group_and_delete_local_history_use_case.dart:193-202,252-269` converts that non-broadcast result to `preworkFailed`.
4. Orbit’s primary path maps that failure to `group_info_leave_failed` (`orbit_wired.dart:3025-3031`). Group Info calls the same leave wrapper directly (`group_info_wired.dart:456-489`). The two stuck-row callbacks call raw `leaveGroup` (`orbit_wired.dart:3324-3347`, `group_list_wired.dart:857-876`) and therefore also need explicit removed-shell routing if that state reaches them.

### Refuted / do not re-introduce

- Do not infer delete authority from `member_removed` timeline history plus a missing key. `materializeAcceptedGroupInvitePayload` saves the replacement group first (`handle_incoming_group_invite_use_case.dart:909-928`), members second (`:930-960`), and the key third (`:963-970`). A same-group re-invite retains the old removal timeline, so its transient post-group/pre-member window satisfies the original predicate and could delete a newly accepted membership.
- Do not claim a fresh invite has no old removal event. Same-group B3 re-entry explicitly retains that history and permits re-materialization at `handle_incoming_group_invite_use_case.dart:824-860`.
- Do not use `LeaveGroupAndDeleteLocalHistoryStatus.notAMember` as delete authorization. Missing membership is documented as ambiguous during invite materialization at `leave_group_and_delete_local_history_use_case.dart:103-121`; pending-role rows can block before broadcast, and a removed admin can hit last-admin logic before the missing-self check.
- Do not re-issue native `group:leave` on this delete path merely because the Go topic leave is currently idempotent. A re-invite can win between confirmation and commit; local deletion must be incapable of leaving the newly accepted topic.
- Do not duplicate `_cleanupAfterConfirmedLeave` in widgets. It is private and currently deletes message evidence before later best-effort failures; a message-derived classifier would make retries unclassifiable.
- Do not present the stuck-row generic snackbar as proof of the same failure mechanism. Those rows are rendered only for given-up rejoin state; their raw-leave bypass is a sibling-surface consistency risk, not part of the confirmed primary-path chain.

Unresolved root-cause items: none. The previous review's concurrency stop-if is resolved below by holding the membership lock and repository coordinator across native leave plus one atomic authority commit, then using the committed marker and retained row addresses for terminal retry.

## Critical Review Reassessment

Accepted and corrected:

- The original marker-first sequence could strand a marker/self/key contradiction because redelivery was rejected by the stale-event and missing-self guards. A first attempted correction moved external-key cleanup before SQL, which let a concurrent self restoration commit before the final recheck after its keys had already been destroyed. A durable marker+self phase would instead leave ordinary compose/reaction/system-publish authority live unless many outbound paths learned a new pending state. The final minimal design keeps the existing native-first semantics but moves native leave inside the membership lock and one repository-coordinated mutation unit: revalidate, call native leave, then atomically set marker/watermark and delete only the exact self while retaining key rows. Accepted re-entry and every repository DB+projection mutation are serialized against that unit. Native or SQL failure leaves no marker and unchanged local rows; if native already succeeded, convergence still needs restart, voluntary action, or another authenticated delivery. Terminal failure leaves marker+self-absent+row addresses, and the visible local-delete path revalidates that exact marker and resumes terminal cleanup without native leave. No event receipt or durable pending phase is added.
- `GroupModel.toMap()` plus ordinary full-row group writes can erase a newly stored marker. The marker is now protected state: ordinary saves/updates preserve it, B3 owns the only set operation, and accepted membership materialization owns the clear operation.
- `removeAllKeys` currently deletes SQL references before fallible primary secure-key deletion. The new terminal-key path retains committed/draft rows as retry addresses until strict authorization-projection, primary, and generation/mute-mirror deletion succeeds; no new journal is needed.
- B3's late-readd check currently occurs before the proposed lock. The revised contract repeats the self/joined-at/watermark decision inside the lock and again inside the SQL transaction.
- The existing tables do not cascade from `groups`, and the reaction notification projection is an external authorization projection rather than a harmless cache. The plan now names exactly what is deleted or preserved, makes marked/absent group writes suppress stale projection upserts, and removes authorization before the final SQL commit.
- Preparing every retained message one transaction at a time while holding the authority lock was unnecessarily open-ended. Only media-bearing parents use the canonical v98 prepare seam, with a fixed per-attempt cap; non-media parents are tombstoned and deleted set-wise in the final SQL transaction.
- Retaining key rows as terminal retry addresses exposed a startup rejoin/broadcast hole. Ordinary key reads now hide marked rows; B3/backfill atomically neutralize old executable work; future writes/dequeues and loaded runners recheck authority; and the five bounded lifecycle/network consumers skip markers without hiding shells from UI.
- A marker re-read immediately before join/publish/retrieve still left a check/use race with B3. Candidate snapshots are now shortlist-only: the same per-group membership lock covers the final authoritative read and one bounded external leaf action. Batch loops and listener callbacks stay outside so replayed B3 cannot deadlock the non-reentrant lock.
- Database-first accepted re-entry initially trusted a locally advanced time and left the outer accept use case free to generic-delete committed state. The final predicate derives authority only from signed watermark/issued-at values, keeps the canonical event id null, and stages a deterministic SQL key address before primary material. Lock ownership is phase-specific and non-nested. A deterministic shape origin precedes destructive work; every accepted commit atomically inserts a phase-unique binding containing a separate authorization id and accepted-state fingerprint, and restart chooses the newest state match regardless of authorization before checking the pending proof. Thus rollback ownership survives restart and repeated invite cycles without misusing membership ordering or adding a column.
- Physically deleting the shell while preserving an invite originally erased the only removal cutoff, allowing an older invite to enter the fresh-group path. Final cleanup now persists a compact local freshness-floor entry in the already-retained `group_event_log`; absent-row materialization must honor it, but it never authorizes deletion.
- Existing terminal `send_failed` rows are manually rearmable. The membership-end helper now keeps that established UI status but atomically scrubs wire/inbox payloads and backoff eligibility, terminalizes pending uploads, and makes loaded completion writes exact-CAS. Repairable rollback applies the same helper to native-window work, so later acceptance cannot revive old transport.

Rejected or narrowed:

- Do not route every roster writer through the application lock. Only marker set/clear/delete and existing-row accepted-membership transitions require the membership lock. One repository-owned per-group coordinator makes each group/member/key/draft DB+projection mutation indivisible relative to the B3 commit and terminal purge; the in-lock transaction recheck arbitrates the pre-marker self-write window, and late child inserts fail closed once the marker exists.
- Do not add a bespoke key/projection/avatar cleanup journal. The durable marker plus retained key/draft row addresses provide retry authority across partially completed idempotent external deletion, and received-media cleanup reuses the existing v98 journal/reconciler.
- Do not add a removal-tombstone/origin-pointer table or new message-status state machine. The preserved append-only event log carries compact floor/origin/binding facts without mutable progress state, while existing `send_failed` plus scrubbed retry evidence and existing upload terminal states make old transport non-rearmable.
- Do not turn the currently unused `joinGroup` helper into a second post-removal acceptance engine. Its own short phase stays fresh-only/native-first and refuses any existing row, retained/malformed floor, or missing floor capability before bridge; authenticated post-removal acceptance remains in the two verified materialization callers.
- Do not delete every table containing `group_id`. Event logs, security snapshots, invite tombstones, local-deletion tombstones, receipts, and active media journals have independent retention or replay purposes and are preserved explicitly.
- UI cancellation/failure coverage and localization RED precision are worthwhile tightenings, not reasons by themselves to redesign the persistence model.

## Durable Authority And Commit Contract

1. **v102 marker and ownership.** Add nullable ISO-8601 UTC `groups.self_removed_at`. `null` means no durable local proof that the current membership was terminated by a received self-removal event. `GroupModel` reads/round-trips it, but ordinary group insert/update helpers preserve the stored marker and stored membership watermark/id rather than trusting a precomputed model. Dedicated monotonic membership-event helpers own normal watermark advancement; the B3 authority commit may set marker+watermark/id, and the atomic accepted-membership transaction is the only production path allowed to clear the marker while strictly advancing accepted authority. While marked, every ordinary write freezes all three authority fields. Before any accepted transition clears a marker, or final cleanup physically deletes its group, persist/replay a deterministic `local_self_removed_freshness_floor` in the preserved `group_event_log`, carrying the exact marker, membership watermark/id, and self id. Before each post-removal accepted DB commit, persist/replay a shape-specific origin `O` whose deterministic source id binds `(group, authenticated authorization/invite id, exact floor entry id, prior shape marked|absent)`. Generate one cryptographically random, phase-stable nonce under the membership lock for each accepted commit attempt. In the same SQL transaction that materializes accepted group+self+key state, insert exactly one new phase-unique `local_self_removed_accept_binding` `B` whose source id binds `(O id, nonce)` and whose payload records the authorization id separately from the non-secret exact accepted-state fingerprint: derived accepted-authority instant with canonical nullable source-event id, signed proof watermark/issued-at, self id/join tuple, key generation/reference, signed config/state hash and version fields, and metadata/dissolution authority fields used by rollback CAS. A reused/colliding binding source id aborts the accepted transaction rather than exact-replaying an old sequence. All semantic fields come from the authenticated tuple or exact floor; the nonce is correlation only, carries no authority, and is never derived from wall-clock time. Define the stored accepted-authority instant as the later of the parseable signed membership watermark and signed `issuedAt`; because today's proof carries no source-event id canonical for that derived instant, accepted materialization stores `last_membership_event_id = NULL`. Neither invite id nor `O`/`B` may occupy that protocol tie-break field; adding a canonical accepted-transition id is wire scope, not Plan 263. On restart, scan binding facts newest-sequence-first—not merely the last log row—and choose the first well-formed `B` whose accepted-state fingerprint exactly matches current DB state, without first filtering authorization; only then require its separate authorization id to match the still-authenticated pending payload and validate its referenced `O`/floor. Missing/malformed/no exact binding or authorization mismatch fails closed. An orphan `O` changes nothing, and a rolled-back `B` cannot shadow a later recommit because every committed transition has a later unique binding sequence. Marked and absent attempts for the same preserved invite have distinct origins/bindings; same-shape origin replay still receives a new binding per committed transition. These facts restore prior shape and reject stale materialization, but never authorize deletion or act as a cleanup journal. Ordinary key reads return no authority for marked/absent parents; only privileged terminal/accepted helpers load raw addresses. Repository projections derive from authoritative post-write state: marked/absent removes or suppresses, never upserts. Launch replacement excludes marked shells. Inject `SelfRemovedGroupShellRepository` separately from the base repository; production wiring and any path that must decide marker/floor state fail closed when it is absent, while unrelated repository fakes need not implement the capability.

## Risks And Edge Cases

- A member/group/key write or accepted re-entry can race B3. The repository coordinator makes each DB+projection mutation wholly before or after native/authority commit, while phase-owned membership locking orders accepted re-entry without nesting the non-reentrant public seam → TC-04/06/11.
- Native leave or the following SQL commit may fail. Both keep marker unset and local rows unchanged. If native already succeeded, the pre-existing unmarked/local-active degradation remains: ordinary exit works, while convergence needs restart, voluntary action, or another authenticated delivery. Only a committed marker+self deletion authorizes redelivery-independent native-free local terminal retry → TC-04/05.
- Projection, primary, generation/mute-mirror, or SQL-finalize deletion may fail after an earlier idempotent step succeeds. The marker and retained row addresses permit deterministic resume; fail-closed projection removal runs first, so a later primary failure cannot leave live notification authorization → TC-05/10.
- An accepted invite can race B3, confirmation, final cleanup, repeated invite cycles, or process death before pending-invite finalization/native retry. Its signed tuple is rechecked in one phase; floor + shape/floor/authorization-bound origin precede floor-bound key staging, and a phase-unique atomic binding correlates each committed transition without polluting the canonical nullable membership-event id. Restart chooses the newest accepted-state-fingerprint match regardless of authorization before checking the binding's separate authorization id against the pending proof, so a rolled-back I2 cannot shadow a later I1 recommit; marked rollback → physical deletion → same-invite absent retry also gets a distinct origin/binding. Timeout/transient retains accepted authority + one fresh rejoin, and metadata/config/dissolution or other newer state makes outer recovery refuse rather than generic-delete → TC-06/11.
- Physical shell deletion can race a preserved or later-delivered pre-removal invite. The deterministic event-log floor must exist before group-last; every post-removal materializer consults it even with no group row, while deletion still requires the live marker → TC-06/09.
- A final marker read can race a native/network call. Each bounded leaf holds the same membership lock across read + one action + exact completion; batches/listener callbacks remain outside to avoid replay deadlock → TC-11.
- A terminal failure can leave readable key addresses or old transport rows on a marked shell. Ordinary key APIs hide addresses; text/repush payloads are scrubbed, pending uploads are terminal, manual reset requires surviving evidence, loaded completion writes CAS exact state, and later reaccept cannot revive them → TC-01/04/05/06/11.
- A legacy broken row may have lost timeline evidence. Structural v102 backfill deliberately recovers it only when identity id=1 exists, self/key are absent, and the row is active; a pending invite is preserved rather than excluding the shell → TC-01/02.
- A removed admin can retain stale `myRole=admin`, and old pending-role broadcasts can survive B3. Marker classification deliberately precedes those stale branches → TC-07.
- A received-media file/key cleanup may outlive the UI action. At most 100 stable media candidates are attempted per call (both advancing typed outcomes consume the cap); overflow is retryable, and the existing journal lets reconciliation complete after authority locks and the group row are gone → TC-09/10.
- Projection removal may succeed before the final SQL transaction fails. This is fail-closed: the retained marker permits retry, launch replacement excludes the marked shell, and delayed ordinary group writes remove/suppress rather than restore authorization → TC-10/11.
- Existing-row replacement clears the marker only through the dedicated accepted-membership path. Ordinary stale full-row saves/updates preserve it and project from the authoritative stored row → TC-03/06/11.
- Group IDs are reusable. Explicit marker clear plus restored self membership prevents destructive authority leaking across re-entry; the historical event-log floor only imposes a lower bound that any legitimately newer signed invite satisfies, and stale key residue alone cannot block dismissal → TC-06/08/09/11.
- v102 must remain the direct successor of v101; hard-coded v101 terminal assertions in the v100, v101, and full-chain tests must be updated without weakening their predecessor checks.

## Reviewer Findings

The read-only review correctly returned `not-ready` for the first revision: sequential marker-first retry could not resume, the proposed application lock did not own relevant transitions, full-row writes could erase authority, key cleanup lost retry enumeration, and “all group-owned artifacts” was false. Later passes refuted secure-first deletion, a durable marker+self phase, native-first accepted re-entry, unaddressed key staging, locally synthesized freshness, generic rollback, and global UI filtering. The final concurrency audit then found five concrete execution gaps: nested non-reentrant lock ownership, final-check TOCTOU at external leaves, restart-unsafe rollback classification, loss of the removal cutoff after group deletion, and manually rearmable outgoing state. The bounded corrections use phase-specific locking, one-action critical sections, compact deterministic floor/origin facts plus phase-unique accepted bindings in the already-retained event log, and established `send_failed`/`upload_failed` states with retry evidence scrubbed. A further counterexample showed that an origin keyed only by invite collides when the same preserved invite moves through marked rollback → physical deletion → absent retry. A first correction then tried to store a shape-derived binding in `last_membership_event_id`; source review rejected that because the field is the canonical equal-time ordering and prepared-broadcast proof id, while today's invite proof signs watermark/issued-at values but carries no source-event id canonical for the derived accepted-authority instant. The final correction keeps that id `null`, creates authorization+floor+shape origins, and atomically commits a nonce-distinct binding carrying a separate authorization id and accepted-state fingerprint with each group+self+key transition. Newest state-match selection occurs regardless of authorization before pending-proof comparison, preventing an older binding from shadowing a recommit. Source census also showed `joinGroup` has no production caller, so its proposed second accepted-reentry engine was removed: it stays fresh-only/native-first and refuses existing/floor/unknown-capability state before bridge. Existing TC-04/06 prove absent optional capabilities fail closed, and TC-12–TC-15 table-drive every typed UI result in each distinct handler. B3 remains native-first inside one membership/coordinator unit; marker-owned cleanup stays strict projection → primary → mirrors → SQL; media work stays capped.
