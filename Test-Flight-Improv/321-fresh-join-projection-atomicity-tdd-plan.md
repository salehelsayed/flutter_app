## Problem And Evidence

- **Behavior to improve:** a freshly ACCEPTED group join publishes the group into the iOS NSE notification projection **without `keyEpoch`** from the moment `saveGroup` returns until `saveKey`'s `upsertKeyEpoch` commits. During that window BOTH parsers drop the group — `OrdinaryNotificationProjectionSnapshot.init` and `GroupReactionProjectionSnapshot.init` each skip a group doc whose `keyEpoch` is missing/non-integer — so every push for the new group renders as the fully-sanitized silent passive fallback (messages: `suppressOrdinary(title: "Mknoon", body: "New message")`; reactions: `groupReactionFallback(reason: "group_reaction_unknown_group")`). The user who just joined sees contentless notifications (or effectively none) for their newest group.
- **Confirmed mechanism (all file:line current HEAD, workflow-verified):**
  - Fresh path `materializeAcceptedGroupInvitePayload`: `saveGroup` (handle_incoming_group_invite_use_case.dart:1081) → roster loop with per-member `saveMember` (:1089) and awaited `triggerDeferredDistributionDrainForPeer` (:1097) → `saveKey` (:1105).
  - `saveGroup` → `_projectAuthoritativeGroup` (group_repository_impl.dart:335-337, :1781-1790) → `upsertGroup`, which carries `keyEpoch` ONLY from a previous doc (`group_reaction_notification_projection.dart:173-174`) — a fresh join has none, and `GroupModel`/`toMap` carries **no** epoch field at all (group_model.dart:49-225), so the first document **structurally cannot** contain the epoch. Members are also empty on that first doc (`:175`, `_copyMembers(null)`).
  - The epoch lands only at `saveKey` → `upsertKeyEpoch` (group_repository_impl.dart:1324; projection :272-281).
  - A fresh join issues **N+2 queued projection writes** (1 `upsertGroup` + N `upsertMember` + 1 `upsertKeyEpoch`); each queued write is a wipe opportunity: any queued-action failure triggers `_deleteAllDocuments()` — contexts + authored-targets + latest-states for **every** group (`_enqueue` :650-678 → :848-866).
- **Why this is the "lead suspect" plan:** the 309 v1 build carrying the C3 edit (an appended unguarded strict publish) was on the device that broke on 2026-07-31 — recorded shape: **Android, app backgrounded → reopened, "unable to load anything"** (user-report wording; no device logs survive; no commit ever contained the v1 edits; root cause never established). The hardened design's non-negotiables follow directly: the projection call must never throw into the join flow, never add queued-write wipe surface, and never hold state that breaks app load.
- **Impact:** every fresh joiner's first minutes in a group have blanked notification content (both message and reaction pushes); a projection failure mid-join can leave the group blanked until next launch; and the N+2 queued writes multiply the global wipe surface.
- **Existing coverage:** reentry atomicity — `group_notification_projection_lifecycle_test.dart:222-293` (strict one-document replacement, driven at the projection layer); use-case persistence — `handle_incoming_group_invite_use_case_test.dart:489` (`InMemoryGroupRepository` + `FakeBridge`, never reads projection state); launch heal — lifecycle `replaceContexts` tests (:295-343). **No existing test drives the fresh-join materialize path against an instrumented projection store** (workflow-refuted existence), no dedicated projection unit-test file exists, and **309's TC-11 Swift test does not exist on HEAD** (`ordinaryGroupContextsJSON` always seeds `keyEpoch`; no omission path).

## Scope Contract And Guard

**In scope (the amended design — all three refute-mandated amendments are requirements, not options):**
1. **Capability interface** (new, small — e.g. `FreshJoinProjectionAtomicity`), implemented by `GroupRepositoryImpl` only, discovered in the use case via the precedented `is`-check (`groupRepo is SelfRemovedGroupShellRepository`, handle_incoming_group_invite_use_case.dart:860). No `GroupRepository` interface change (large fake population).
2. **Refcounted, per-groupId, MIRROR-UPSERT-ONLY suppression** — `runWithSuppressedGroupProjectionMirrors(groupId, action)`: a depth-counted set consulted at **ALL FIVE** mirror-upsert sites (review-corrected census — v1 said three): `_projectAuthoritativeGroup`'s `upsertGroup` (:1788 — covers BOTH `saveGroup` and `updateGroup`, closing KILL 1), `saveMember`'s `upsertMember` (:1127), **`updateMemberRole`'s `upsertMember` (:1167 — v1 missed it; its no-op-without-doc property (:219-222) makes it harmless mid-scope today, but uniform consult is the drift-proof shape)**, `saveKey`'s `upsertKeyEpoch` (:1324), and **`_mirrorGroupContextForPush`'s local-variable `projection.upsertGroup` (:1693 — reached from `archiveGroup`/`unarchiveGroup` :404-419; invisible to the v1 census grep; an archive landing mid-scope would create the first doc epoch-less — the exact KILL-1 class)**. **Removal calls are NEVER suppressed** — the failure-branch `removeGroup` in saveMember/saveKey (:1123/:1321), `removeGroupStrict`, `clearKeyEpoch`, `removeAllMembers`, `deleteGroup`, and the repairable-rollback path (`_rollbackMaterializedInviteState` :1389-1396) all pass through (closes the refuter's worse-corners 1 and 3). Refcount released in `finally`.
3. **Atomic publish `projectCommittedFreshJoin(groupId)`** — runs **inside `_runGroupMutation(groupId)`** (every `_projectAcceptedReentry` call site is wrapped; an unwrapped read-back could resurrect a concurrently-removed member — refuter UNRESOLVED-2, made explicit here). Body: load authoritative group (null/selfRemoved → log-and-return, no throw); **unsupported type (`qa`) → clean no-op** (parity with today's no-context-for-qa; never let `replaceAcceptedGroupContextStrict`'s ArgumentError fire for it — closes the qa kill); load ALL member rows; **load the LATEST committed key (`dbLoadLatestGroupKey`), never the join's pinned generation** (closes KILL 2 — a mid-scope rotation's suppressed mirror is recovered because its committed row IS the latest at read-back, and any later rotation's `upsertKeyEpoch` is monotonic and queues behind the publish under `_runGroupMutation`); hydrate; `replaceAcceptedGroupContextStrict`; then the same best-effort `_mirrorGroupKeyForPush`/`_mirrorGroupMutedForPush` as reentry.
4. **Use-case wiring** in `materializeAcceptedGroupInvitePayload`'s fresh path: define the save sequence once; capability present → run it inside the suppression scope, then `try { await projectCommittedFreshJoin(groupId); } catch (e) { emitFlowEvent('GROUP_FRESH_JOIN_PROJECTION_DEFERRED', …) }` (**log-and-no-op; the join NEVER fails because of the projection** — the 07-31 non-negotiable); capability absent (test fakes only — every production root constructs `GroupRepositoryImpl`, sole construction production_application_bootstrap.dart:1752; the fresh path already hard-requires the SHELL capability at :919 — review precision: `InMemoryGroupRepository` also implements `SelfRemovedGroupShellRepository` (in_memory_group_repository.dart:15-25), which is exactly why the :489 fresh-join test passes with the fake, and it will NOT implement the new `FreshJoinProjectionAtomicity`, so "capability-less" = lacks the NEW interface while still shell-capable) → today's sequence unchanged.
5. **Drain reorder (scope shrink):** collect regained-key members during the roster loop; run `triggerDeferredDistributionDrainForPeer` AFTER the save scope + publish (matches the reentry precedent, which drains post-commit at :1060-1067). Removes all await-driven interleave surface from the scope; drains are DB-owed sends, order-independent of the publish.
6. Flow-event discriminators: `GROUP_FRESH_JOIN_PROJECTION_PUBLISHED` (success) / `GROUP_FRESH_JOIN_PROJECTION_DEFERRED` (caught failure) — distinct from the projection's own `GROUP_REACTION_PUSH_PROJECTION_ERROR`.

**Must preserve:**
- Reentry path byte-for-byte (`commitAcceptedReentry`/`_projectAcceptedReentry` untouched; it correctly pins the reentry generation) → TC-321-07.
- Today's qa end-state (no context, no error) → TC-321-05.
- Capability-less fallback = today's exact sequence → TC-321-08.
- Failure-branch and rollback removals fire under suppression → TC-321-04.
- The projection's fail-closed wipe posture (`_enqueue` → `_deleteAllDocuments`) — UNTOUCHED; this plan only reduces queued writes per join from N+2 to 1.
- Launch heal (`mirrorAllGroupReactionNotificationContexts`, production_application_bootstrap.dart:2046) → TC-321-11.
- Drain semantics: exactly one drain per regained-key member → TC-321-09.

**Hard `Do not`:**
- Do not add a `GroupRepository` interface method (fake population; capability `is`-check only).
- Do not add a monotonic guard to `replaceAcceptedGroupContextStrict` or otherwise change its semantics — reentry DEPENDS on unconditional replacement; the fresh path gets safety from latest-key read-back + `_runGroupMutation`, not from changing the shared primitive.
- Do not hold `runGroupMembershipMutationLocked` across the save scope — the scope contains awaits and the drain chain can acquire rotation-side locks; the reentry precedent holds it only around its own commit, and this plan's safety does not depend on it.
- Do not suppress ANY removal path (the exact refuted worse-corner).
- Do not touch `_enqueue`/`_deleteAllDocuments` or the NSE parsers' drop guards.
- Do not "fix" the window by relaxing the NSE epoch guard — the guard is the privacy/correctness boundary (TC-321-10 locks it).

**Deferred / accepted difference:**
- Same-group concurrent double-accept single-flight (beyond refcount convergence) — no production trigger (sequential UI retry loop; debug-only second caller); owner: future hardening if a second production entry appears.
- **Failed-publish honesty (accepted, documented):** after a queued-storage publish failure the wipe has already blanked all docs (pre-existing fail-closed class), and the NEXT `updateGroup` (avatar/config/mute/drain-retention) re-publishes the joining group epoch-less until relaunch — the SAME recovery class HEAD has after any wipe today. Not new exposure; measurable via `GROUP_FRESH_JOIN_PROJECTION_DEFERRED`; healed at next launch. (The refuter's correction of the earlier "deferred until heal" phrasing is adopted verbatim.)
- Stale App-Group projection across uninstall/restore — pre-existing, noted in 309 (:131), separate hardening item.
- 1:1/direct-reaction projection lanes — untouched.

**Dependencies:** none upstream; client-only. Rollout follows the staged protocol (below) because this seam is the 07-31 breakage suspect.
