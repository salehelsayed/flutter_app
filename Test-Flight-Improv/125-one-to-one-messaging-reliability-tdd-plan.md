## Problem statement

- **F3 (confirmed, medium):** No drain-level mutex/in-flight guard anywhere in `P2PServiceImpl` — both public entry points `drainOfflineInbox()` (`p2p_service_impl.dart:3661`) and `drainOfflineInboxFully()` (`:3675`) plus the warm-background drain (`:577`) and the health-check drain (`:2872`) run unguarded relative to each other. The root amplifier: `InboxStagingRepositoryImpl.stageEntries` unconditionally `ackableEntryIds.add(entry.entryId)` at `inbox_staging_repository_impl.dart:63` regardless of whether `dbInsertInboxStagingEntry` (`ConflictAlgorithm.ignore`, `inbox_staging_db_helpers.dart:25`) actually inserted a fresh row. Two drains fetching the same not-yet-acked relay page both ack and both replay the same entries → double `maybeShowNotification` / double delivery-receipt re-mint when both clear the non-atomic `getMessage(payload.id)` gate at `handle_incoming_chat_message_use_case.dart:283` before either durably saves. (No data corruption — `dbInsertMessage` uses `ConflictAlgorithm.replace`.)
- **F7-reactions (confirmed, medium):** The stage-before-ack/commit durability machinery is gated on envelope type `'chat_message'` (+ `'introduction'`); `'message_reaction'` and `'message_deletion'` never enter it. Go `shouldDeferDirectAck` returns false for non-chat (`node.go:1514`) → immediate `{"ack":true}` to sender (`node.go:1661-1668`); Dart `_shouldDurablyStageDeferredDirectChat` (`p2p_service_impl.dart:805-815`) is false → `_emitIncomingMessage` fire-and-forget (`:3091`); relay-inbox replay deletes the staged row at `_replayStagedInboxEntries:1068` immediately after a bare emit. A kill in the window between Go ack/relay-delete and the listener's `saveReaction`/`saveMessage(tombstone)` loses the reaction/deletion permanently. (Deletions emit a receipt only AFTER commit, so the window is uncovered; reactions have no receipt at all → strictly more exposed.)
- **F8 (confirmed; ACTIVE per OQ-8 — forward/share is planned, medium):** 1:1 incoming dedup is keyed entirely on `getMessage(payload.id)` (`handle_incoming_chat_message_use_case.dart:283`); `MessageRepository` has no `existsByContent` (`message_repository.dart`), and the `messages` table has `id TEXT PRIMARY KEY` with only non-unique indexes (`002_messages_table.dart:7-27`). Same logical content arriving under two different ids persists two rows — the 1:1 mirror of the group double-card flaw. Latent ONLY while every 1:1 sender keeps the id stable; **OQ-8 confirms a forward/share-to-contact path IS planned (audit finding #4), which mints a fresh id (and likely a fresh timestamp) per recipient/resend → F8 becomes ACTIVE the moment that path ships.** F8 is therefore a **HARD prerequisite of the forward/share feature** and the receiver dedup key must NOT be timestamp-exact only (see F8 GREEN tier-2).
- **F5-text-residue (narrowed, low-medium):** `callP2PMessageSend` (`p2p_bridge_client.dart:1035`) awaits `bridge.send(...)` with NO Dart-side `.timeout`, forwarding `timeoutMs` only into the Go payload. Two 1:1 legs — the connection-reuse fast path (`send_chat_message_use_case.dart:453`, inside `try{}catch(_){}` with no outer wrapper) and the relay-probe leg (`:1582`) — await this uncapped. Go self-bounds via `s.SetDeadline` so the common case returns within ~2s; the residual exposure is a MethodChannel/gomobile-boundary stall or iOS suspension freezing the deadline, which leaves `_isSending` stuck-true (cleared only in the `finally` at `conversation_wired.dart:2118-2124`) → composer locked until screen reopen. Group path is fully defended via `BRIDGE_TIMEOUT` (`bridge_group_helpers.dart:76-101`).
- **F6-residue (narrowed, low):** F6 is otherwise owned by 115/114, but `retryFailedMessages` still conflates relay custody with delivery at TWO sites: `retry_failed_messages_use_case.dart:273` (`RETRY_FAILED_MESSAGE_SUCCESS`: `storeInInbox`→`status:'delivered'` + `wireEnvelope:null`) and `:249` (`RETRY_FAILED_MESSAGE_ALREADY_INBOX`: flips to `'delivered'` with NO send). Both clear the envelope, making the false `'delivered'` terminal (`handle_delivery_receipt` idempotent-skips `'delivered'` at `:63-66`; `verify_inbox_custody` only touches `'inboxed'`). The guard test `delivered_status_minting_sites_test.dart` WHITELISTS these as "PROGRAM-TEMPORARY (removed by 116)" — but 116's removal never landed, and ownership of the removal is now reassigned to 125 (OQ-6).

## F3: No mutex / no idempotent stage across concurrent inbox drains

**Root cause (confirmed, `124-harness-refactor`):** `InboxStagingRepositoryImpl.stageEntries` (`lib/core/inbox/inbox_staging_repository_impl.dart:48-67`) does `await dbInsertInboxStagingEntry(entry.toMap())` then unconditionally `ackableEntryIds.add(entry.entryId)` at `:63`, never inspecting the insert result. `dbInsertInboxStagingEntry` uses `ConflictAlgorithm.ignore` (`inbox_staging_db_helpers.dart:22-26`) returning `Future<void>` — a re-stage of an already-present `entry_id` is a silent no-op yet still reported ackable. No drain serialization exists: `drainOfflineInbox()`/`drainOfflineInboxFully()` (`p2p_service_impl.dart:3661/3675`) → `_drainOfflineInbox`/`_drainOfflineInboxDurably` (`:1392/:1458`) carry only the `_allowsAccountNetworkSideEffects` gate; the only `Completer` in the class is `_recoveryInProgress` (`:133`), which coalesces health-check RECOVERY, not drains. `main.dart`'s `_runAccountRuntimeNetworkVoidAction` is a pure gate-check + await (no Completer/queue), so it does not serialize the two wired call sites and cannot cover the internal warm-background/health-check drains. Net live harm: double `maybeShowNotification` (`chat_message_listener.dart:559`, in the `state==stored` block) and double delivery-receipt re-mint when two replays both observe a null `getMessage(payload.id)` at `handle_incoming_chat_message_use_case.dart:283` across the decrypt-bridge awaits.
