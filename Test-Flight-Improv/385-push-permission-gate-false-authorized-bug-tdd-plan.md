## Problem And Evidence
- Behavior to improve: a user who revokes/declines notification permission gets zero feedback — the app records `authorized`, registers its token, posts blind, and the OS discards every card. The in-app "Open notification settings" banner that exists for exactly this state never appears.
- Impact: silent total notification loss with a healthy-looking health surface; wasted relay delivery; the support path ("notifications aren't working") is structurally defeated. Blocks Plan 380 `tc_g7_permission_denied` and the three G7 legs queued behind it.
- Confirmed root cause: `requestPushPermission` at `lib/features/push/application/request_push_permission_use_case.dart:25-27` derives `granted` solely from the request result. On Android SDK≥33, firebase_messaging 15.2.10 `requestPermissions()` short-circuits to `authorizationStatus=1` (authorized) whenever `Context.checkSelfPermission(POST_NOTIFICATIONS) == GRANTED` (`FlutterFirebaseMessagingPlugin.java:358-383`, `checkPermissions()` :389-393), **never consulting `NotificationManagerCompat.areNotificationsEnabled()`**. Device-measured (emulator-5554, Android 17/SDK 37, 2026-08-18): with the grant verified `granted=false` at pm level (campaign leg gate `notification_android_payload_campaign.dart:1256-1261`), the process fully terminated (`:2355-2359` waits for empty pidof) and relaunched fresh, the coordinator still logged `PUSH_PERMISSION_REQUEST_RESULT {"status":"authorized","granted":true}`. The plugin's request-callback path is honest (`FlutterFirebasePermissionManager.java`: `grantResults[0]==GRANTED` mapping; USER_FIXED auto-rejects), so the only route to `authorized` is the checkSelfPermission short-circuit — i.e. the OS's permission-check layer diverged from its NotificationManager state (`importance=NONE`). The NM layer was truthful throughout (posts were really discarded), which is why the fix reads NM-backed truth.
- Consequence at `lib/features/push/application/push_registration_coordinator.dart:205-226`: the `!granted` branch — durable `PushRegistrationHealthRecord.permissionDenied`, `PUSH_REGISTER_COORDINATOR_PERMISSION_DENIED`, early return — is dead code on Android.
- Existing coverage: coordinator denied branch host-proven under injected `false` (`test/features/push/application/push_registration_coordinator_test.dart:18-50` no-retry/no-register; `:226-266` permissionDenied phase + warningVisible + openNotificationSettings action + persisted reason). Banner rendering + settings deep-link host-proven (`test/features/push/presentation/push_registration_health_surface_test.dart:66-109`, en/de/ar; FEED_TESTS `run_test_gates.sh:427`). Device tier: the G7 leg hard-fails without the typed event (`notification_android_payload_campaign.dart:1295-1307`) — red today, exactly this bug.
- Missing coverage: nothing exercises "request says authorized but the OS says notifications are off" — the use case exposes no OS-state seam (`request_push_permission_use_case.dart:5-7`), so the scenario is untestable on HEAD; no host test asserts the coordinator's denied flow event; no code in lib/ reads `Permission.notification` or `areNotificationsEnabled` today (census).

## Scope Contract And Guard
In scope:
- `requestPushPermission` returns an honest verdict: after a granted-looking request result (authorized/provisional), verify the real OS notification state via a new injectable `osNotificationsEnabledFn` (default: Android-only NM-side read via flutter_local_notifications 18.0.1, already a direct dependency and the very poster whose cards were dropped — `AndroidFlutterLocalNotificationsPlugin.areNotificationsEnabled()`, an UNCONDITIONAL `NotificationManagerCompat.areNotificationsEnabled()` on every SDK, `FlutterLocalNotificationsPlugin.java:2211-2214` — i.e. the NotificationManager layer that was measured truthful in the bug state); on OS-off, return `false` and emit a distinct `PUSH_PERMISSION_OS_STATE_OVERRIDE` flow event; whenever the check ran, stamp the raw `osEnabled` value into the RESULT event details (makes a wrong-`true` visible in device logcat); on check failure or a null platform resolve, fail-open (keep the request verdict) and, on failure, emit `PUSH_PERMISSION_OS_CHECK_FAILED`.

Must preserve:
- authorized/provisional → `true` when the OS agrees → TC-385-05/06 (existing tests, default path).
- denied/notDetermined → `false`, with the OS check never consulted → TC-385-07 + TC-385-03.
- Coordinator denied semantics under honest `false` (typed health, no register, no retry) → TC-385-08 (existing tests, unmodified).
- Banner copy + "Open notification settings" action → TC-385-09 (existing widget test, unmodified).
- iOS behavior byte-identical: the default check short-circuits `true` off-Android; the plugin read is never invoked off-Android (and `resolvePlatformSpecificImplementation` additionally null-safes any non-Android resolve).

Hard `Do not`:
- Do not edit `push_registration_coordinator.dart`, `production_application_bootstrap.dart` (its coordinator block is source-frozen by `test/core/lifecycle/main_deferred_push_rearm_wiring_test.dart:67-110`), `background_message_handler.dart`, `MknoonFirebaseMessagingService.kt`, or `push_notification_settings_gateway.dart`.
- Do not replace the settings deep-link with permission_handler's `openAppSettings` (gateway comment `:12-16` deliberately targets the notification-specific OS page).
- Do not use ANY checkSelfPermission-backed API as the OS-truth backend — that includes `FirebaseMessaging.getNotificationSettings()` AND permission_handler `Permission.notification.status` (both refuted above). The default must be the side-effect-free NM read `areNotificationsEnabled()` (never a permission request — a request would double-prompt).
- Gate the default with `kIsWeb || !Platform.isAndroid` short-circuit → `true` (dart:io `Platform`, mirroring `push_notification_settings_gateway.dart:33`) — a consistency rule, not a test-locked hazard under this backend: `resolvePlatformSpecificImplementation` itself null-resolves on hosts without a registered Android platform instance (`flutter_local_notifications_plugin.dart:40-56`), so host tests never reach a channel under either idiom. Keep dart:io `Platform` anyway (flutter_test forces `defaultTargetPlatform == android`; relying on resolve-null as the only host guard is accidental safety).
- Do not let the OS-verify throw out of `requestPushPermission` — an uncaught throw becomes the coordinator's 15s exception-retry loop that re-fires the OS permission dialog every cycle (Hazard B above). The catch must be a BROAD `catch (e)` — `on Exception` misses Error-type throws (FlutterError/StateError extend Error) and re-opens Hazard B. The try/catch fail-open is part of the contract (TC-385-04 pins breadth via a StateError-throwing fake).
- Do not upgrade firebase_messaging or add a new health reason / coordinator state in this plan.
