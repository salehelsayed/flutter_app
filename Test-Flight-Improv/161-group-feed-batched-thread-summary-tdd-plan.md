> ## ⚠ CRITICAL DESIGN CORRECTION  (2026-06-24 second grounding `wf_e66b5771-c4f`, 4 agents — SUPERSEDES the fixed-K=8 window below)
>
> The group feed shares the **exact** base class (`CardThreadFeedItem`), the **exact** pending projection (`projectPendingFeed`, `feed_store.dart:75`), and an **uncapped** card render (`LetterCardGroup`, explicit "no N-more fold") with the 1:1 feed — so it inherits **160-original's hazards**. This plan was written before 160's correction; it must mirror the **corrected** 160. The structural scaffold (NEW `dbLoadGroupThreadPreviews` helper / repo method / interface / injection, orbit preservation, navigation decoupling, real-DB test, `total_message_count`) is **sound and kept**; the **window shape + count-sourcing + the incremental merge path** change. RED tests **TC-161-10..13** lock it.
>
> **Why the fixed-K=8 window is wrong (all source-confirmed):**
> 1. The group card renders the **UNCAPPED** unread set: `GroupLetter.fromThread` → `groupSenderRuns(item.unreadMessages)` (`feed_letter.dart:66-73`, no cap `group_sender_runs.dart:28`); `LetterCardGroup` renders every line ("no N more fold", `letter_card_group.dart:15-16`). K=8 → a 20-unread group shows 8 lines.
> 2. Card **VISIBILITY** is the SHARED `projectPendingFeed` (`feed_store.dart:69-75` merges groups into one list); `isPendingFeedItem` (`feed_pending_projection.dart:55`) drops all-read/answered groups, and `answeredSince` scans the full list for an outgoing **after** `newestIncoming` (`:63-65`). A K-tail that drops the answering outgoing **re-surfaces an answered group as pending**.
> 3. `unreadCount`/`conversationState`/`hasSentMessage` are **re-derived from the message list** in both the initial builder (`group_group_messages_into_threads.dart:40-56`) AND the **incremental** live-message rebuild (`_buildGroupThreadFeedItem` `feed_wired.dart:921-942`: `:939` unread, `:925` state) — under a window they drift.
> 4. The summary lacks the signals: `dbLoadGroupThreadSummaries` (`group_messages_db_helpers.dart:306-356`) returns only `unread_count` + one `latest_*` row — **no `total_message_count`, no `last_outgoing_at`, no `has_sent`**.
>
> **Corrected design (mirrors corrected 160):**
> - **G1 — pending-filter, not a blind cap.** Groups go through the same `projectPendingFeed`; **all-read/answered groups load ZERO messages** (render from the summary row alone). Today `loadGroupFeedItems` (`load_feed_use_case.dart:97-100`) loads `limit:200` for *every* active group — skipping the all-read ones is the biggest win.
> - **G2 — unread-run-sized window, not fixed K=8.** Page `limit = unread_count + context` so `GroupLetter.unreadMessages` is COMPLETE; never a constant 8 (insufficient when `unread_count>8`).
> - **G3 — counts from the summary.** `unreadCount ← summary.unread_count`; `conversationState`/`hasSentMessage` from `summary.has_sent`; `totalMessageCount ← summary.total_message_count`. Add all three (`message_count`, `has_sent`, `last_outgoing_at`) to the NEW `dbLoadGroupThreadPreviews` aggregate.
> - **G4 — add `last_outgoing_at` (timestamp), not just `has_sent` (boolean).** The SHARED pending-projection `answeredSince` (`feed_pending_projection.dart:63-65`) needs whether an outgoing exists **after** `newestIncoming` — a boolean cannot answer that. (`has_sent` is still correct for the 4-state `conversationState`; `last_outgoing_at` is the *additional* signal the projection needs.)
> - **G5 — plumb summary counts into the INCREMENTAL merge path (`feed_wired.dart` IS in scope).** `_applyIncomingGroupMessageToFeed` (`:1040-1071`) → `_buildGroupThreadFeedItem` (`:921-942`) rebuilds the card from the in-memory list on every live group message; it MUST carry the summary-derived counts (and increment `total_message_count` on a genuinely-new id), or the first live message after load drifts the counts back to the windowed list. **This corrects the plan's "feed_wired.dart is NOT an in-scope edit" claim — the incremental group merge IS in scope.**
>
> **Genuine group simplification (DROP from the 160 port):** `GroupMessage` has **no `isDeleted`/`isHidden`** (`group_message.dart`, 0 hits); `_toGroupThreadMessage` never sets it (`feed_wired.dart:836-850`). So 160's soft-delete count reconciliation + its deleted/hidden full-reload branch are **N/A** — `total_message_count := message_count` is safe with no `!isDeleted` filter; do not invent a group per-message delete path. And `lastRepliedAt` is hardcoded null for groups (`feed_item.dart:318-319`), so `last_outgoing_at` is needed ONLY for the projection `answeredSince`, not for group card chrome/sort (group sort/divider use the latest-message timestamp + state booleans, `group_group_messages_into_threads.dart:95-114` — unchanged).

## Exact Problem Statement
On every (re)load of the home feed, group threads are materialized by a per-group loop. `loadGroupFeedItems` (`load_feed_use_case.dart:96-100`, the call at `:98`) iterates active groups and calls `groupMsgRepo.getMessagesPage(group.id, limit: 200)` once per group; the per-group refresh path `loadGroupFeedSnapshot` (`load_group_feed_snapshot_use_case.dart:21-24`) does the same `getMessagesPage(groupId, limit: 200)`. Both flow through `dbLoadGroupMessagesPage` (`group_messages_db_helpers.dart:150-192`), whose `WHERE group_id = ? AND id NOT LIKE 'sys-member_removed_cutoff:%'` (`:170-171`) carries a **non-sargable** residual `NOT LIKE`, and whose **up to 200 returned rows per group are SQLCipher-decrypted + `GroupMessage.fromMap`'d on the UI (root) isolate** (`group_message_repository_impl.dart:326`). At N active groups × up to 200 messages, the entire group working set is decrypted on the UI isolate on every feed mount/refresh — a startup/scroll-in smoothness stall (the `db-persistence-5` symptom). 156 already shipped migration **094** (`idx_group_messages_group_ts`, 3-col, reverse-scanned for `ORDER BY timestamp DESC, id DESC`), which makes the per-query ORDER BY cheap but does **not** eliminate the N-query loop, the non-sargable `NOT LIKE`, or the UI-isolate full-page decrypt.

What must improve: the initial feed load (and the per-group refresh) must materialize group preview cards from a **bounded windowed** query — enough rows to reproduce the card's preview/exchange affordances and exact unread/state derivation — instead of decrypting up to 200 rows per group up front.

What must stay unchanged (→ preserved-green sentinels):
- The **orbit** group unread-badge path (`load_orbit_groups_use_case.dart:187` → `getGroupThreadSummaries` → `dbLoadGroupThreadSummaries`) — byte-for-byte unaffected (we add a NEW helper, never reshape the existing one).
- The `GroupThreadFeedItem` semantics from `groupGroupMessagesIntoThreads` (`group_group_messages_into_threads.dart:40-56`): `hasUnreadIncoming`/`hasSentMessages`/`unreadIncomingCount`, `ConversationState` (active/unread/replied/read), above/below-divider sort (`:104-107`, 134/135).
- The card preview getters (`feed_item.dart:138-210`): `previewMessages` (`:156-161`), `recentInteractionMessages` (`:186-195`), `exchangePreview` (`:143-146`), `hasEarlierHistory` (`:163-169`), `hasEarlierInteractionHistory` (`:199-207`), `hasReply` (`:148-149`), `lastSentMessage` (`:171-177`), `latestMessage` (`:139`), `collapsedPreviewMessage` (`:209-210`).

## Real Scope
**In scope:**
1. NEW DB helper `dbLoadGroupThreadPreviews(db, groupIds, {contextRows = kGroupPreviewContext})` in `group_messages_db_helpers.dart` — one batched aggregate (counts + `last_outgoing_at` + the single `latest_*` row, all per group) **plus a pending-filtered, unread-run-sized window** (NOT a fixed K — **corrected `wf_e66b5771-c4f` / round-3 F2**): per group return `unread_count`, `has_sent` (1 if any `is_incoming = 0`), `total_message_count`, `last_outgoing_at` (`MAX(timestamp) WHERE is_incoming = 0`, round-3 **F3**), the latest row (`latest_message_id/text/timestamp`, round-3 **F5** — for the zero-window card), and a **window** of `min(unread_count + contextRows, hardCap)` newest rows. **All-read/answered groups (`unread_count == 0`) load ZERO window rows** (the card is built from the summary row alone — G1). The `id NOT LIKE '$_groupRemovalCutoffMessageIdLike'` exclusion is preserved in the aggregate, the window, the total, and `last_outgoing_at`. The window is **NEWEST-first (`ORDER BY timestamp DESC, id DESC LIMIT (unread_count + contextRows)`), never oldest; never limit-1; never a constant 8** (a 20-unread group must load all 20 — TC-161-10). `kGroupPreviewContext` is the read-context tail (≈ `maxPreview + 2`), not the whole window.
