## §B — Concurrency correctness  *(blockers 2 & 3 — the highest-severity technical gaps)*

- **B1.** **Resolve the nested-semaphore model (deadlock/amplification).** In **Step 7 (L344–348)** and **Accepted Differences (L488)**, replace "a local worker limit no higher than `GroupDiscoveryConcurrency`" with an explicit global-bound design. Recommended: the inner dial pool caps at **1 when a `groupRecoverySem` cycle slot is already held** (i.e., no nested concurrency inside a cycle that already holds a slot), OR move the semaphore from **per-cycle to per-dial** (drop the `defer release()` around the whole cycle at pubsub.go:3053 and acquire a slot per `host.Connect` instead). *Why: `groupRecoverySem`(=5) is already held across both dial fns in `runGroupDiscoveryCycle` (pubsub.go:3049–3077). Reusing it for the inner pool → up to 5 cycles each hold a slot while their inner workers wait on the same exhausted semaphore → **DEADLOCK** (outer never releases). A fresh size-5 limiter → 5 cycles × 5 = **25 concurrent `host.Connect`**, a 5× regression in the cold-start path the refactor claims to improve.*
- **B2.** Add a **production-path** concurrency assertion. TC-220-07/08 call `dialKnownGroupMembers`/`discoverAndConnectGroupPeers` **directly** (no outer slot held), so they measure inner concurrency in isolation and cannot detect the nested amplification. Add one case (or extend TC-220-08) that drives dialing **via `runGroupDiscoveryCycle`** under N concurrent cycles and asserts the **global** concurrent `host.Connect` count stays ≤ the intended bound (~`GroupDiscoveryConcurrency`). *Why: without it, "green" never proves the production nested behavior.*
- **B3.** **Synchronize the six counters.** In **Step 7**, require `dialed/connected/cooldownSkipped/directConnected/relayFallbackConnected/relayOnlyConnected` (pubsub.go:2444–2555) to be accumulated safely under parallelism (atomics, or per-worker locals summed at a post-loop barrier before the `direct_dial` emit at :2572). *Why: they are plain `int++` inside the loop; goroutine-per-target races them and corrupts the aggregate metrics.*
- **B4.** **Make `-race` a MANDATORY acceptance gate** for the parallelized functions. In **Acceptance Gates (L392–450)** and **Blind-Spot Sweep (L295)**, replace "race is optional evidence" with a required command: `cd go-mknoon && GOTOOLCHAIN=go1.25.0 go test -race ./node -run 'TestGroupDialKnownMembersRunsBoundedParallel|TestDiscoverAndConnectGroupPeersRunsBoundedParallel|TestRelaySelectorFanOutRunsDistinctRelaysInParallel' -count=1`. *Why: the headline win is parallelism over shared maps/counters; `-race` is the only host tool that catches the concurrent-map / data-race class, and B1/B3 defects would otherwise pass every gate.*
- **B5.** Extend **TC-220-07's** GREEN assertions (L230) to match TC-220-08 (L237): dedupe/cooldown honored, non-members filtered — **plus** a concurrent-overlap assertion that two overlapping `dialKnownGroupMembers` cycles issue **at most one in-flight dial per peer**. *Why: TC-220-07 currently asserts only elapsed + maxInFlight; nothing guards that parallelism didn't drop the `beginGroupPeerDial` dedupe the serial code guaranteed.*
- **B6.** **Bound `RelaySelector.FanOut` parallelism** (or explicitly accept unbounded with rationale). TC-220-09 locks `maxInFlight==3` = full parallelism with no cap (relay_selector.go:119; callers inbox.go:797/867/931 fire warm/reserve/register). In **Step 8 (L350–353)** state the intended relay-connection concurrency bound and add a preservation note that today's one-at-a-time profile is intentionally changing. *Why: unbounded relay fan-out grows with relay count; the plan neither bounds nor tests the connection-concurrency profile.*

- **C2.** **Recompute the `Node.Start` shape budget.** Change L139 from `≤ 230` to a value **strictly below the measured HEAD logical-line count** (Start is ~207 → set e.g. `≤ 190`), OR drop the Start budget entirely and rely on **TC-220-02** as the real lock-shortening gate. - **C3.** **Pin one deterministic line-counting algorithm** at **L137**. ## §D — Panic / lifecycle robustness  *(blocker 5)*

- **D1.** In the **Startup Lifecycle Contract (L121–133)** and **Step 5 (L337)**, require a `defer` in `Start` that, on **panic** during the lock-release window, clears `startInProgress`, restores lock invariants (do NOT leave a stray `defer n.mu.Unlock()` that would fire on an unlocked mutex — use explicit unlock/re-lock with panic-safe recovery), and re-panics (or converts to error) safely. *Why: `libp2p.New`/`initPubSub` can panic; today's `defer n.mu.Unlock()` (node.go:249) + a bare `startInProgress` marker means a panic → `fatal: sync: unlock of unlocked mutex` AND a permanently wedged node ("node start in progress" forever). The contract currently handles only error-returns.*
- **D2.** Add a RED test **TC-220-04b**: fake host creation **panics** after the in-progress marker is visible; assert the marker is cleared, no fatal unlock occurs, and a subsequent valid `Start` succeeds. Add it to the RED battery and the ≤230 gate list.
- **D3.** In **Step 5**, require `relaySessionMgr.InitRelayPeer` (node.go:~333) to be **deferred to the commit phase** (not called before host creation). *Why: rollback (L128) restores node **fields** but `relaySessionMgr` is a shared external object set in the constructor — a field snapshot does not undo `InitRelayPeer`'s mutation on a failed start. TC-220-04 asserts "no relay fields published" but not manager-state reset.*

## §G — Timing-test precision (tighten before locking thresholds)  *(define-good)*

- **G1.** Define `maxInFlight` explicitly in **Fixed Test Thresholds (L147–152)**: an `int64` atomic incremented on fake-dial entry, a CAS-tracked peak, decremented on exit. *Why: the plan asserts hard `maxInFlight` bounds but never says "atomic"/"peak" — a naive last-value counter flakes or false-greens.*
- **G2.** Mandate the group-dial worker cap **== `GroupDiscoveryConcurrency`** (single ~100 ms wave → 2.5× margin under the 250 ms ceiling) rather than only `>=2` (which gives ceil(4/2)=2 waves ≈ 200 ms → 1.25× margin, inside scheduler jitter), OR widen the ceiling to ~350 ms. Add an **anti-vacuous lower-bound floor** (elapsed ≥ ~90 ms, or slowest fake dial ≥ 50 ms) and a small best-of-N/median. *Why: the repo's own concurrency-timing convention (benchmark_bridge_concurrency_test.go:107–108, 169–172) uses a 3× ceiling + a "dials actually blocked" floor precisely for loaded-CI robustness; single-shot `-count=1` (L295) at 1.25× will flake, and without a floor a fake that fails to block passes vacuously.*
- **G3.** Pull **TC-220-12** (`TestBridgeGroupPublishContractsPreservedAfterHelperExtraction`, the preserved-green-on-HEAD sentinel) **out of the bundled RED bridge command (L402–403)** into its own GREEN-on-HEAD invocation run before production edits. *Why: bundled under the same `-run` as the RED TC-220-11, the combined `go test ./bridge` exits FAIL and the sentinel's pass is invisible — defeating the point of a preserved-green sentinel.*
- **G4.** State the dequeue matcher precisely at **L145** (AST: no assignment to `messageQueue` whose RHS is a slice expression with low bound `1` on `messageQueue`), not fuzzy "equivalent to." *Why: a literal grep misses an aliased form like `q := d.messageQueue; d.messageQueue = q[1:]` that still retains the backing array.*
