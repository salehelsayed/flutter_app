_Generated 2026-06-25 · branch `new-orbit` · decentralized, P2P, post-quantum-E2E-encrypted messaging app (Flutter client + embedded Go libp2p bridge + single-EC2 Go relay)._

This report grades the app across **14 production stack layers**. ## Bottom line

The **cryptographic and product core is genuinely strong** for a pre-launch app — post-quantum ML-KEM-768 E2E encryption, SQLCipher-at-rest, a canary-verified zero-knowledge relay, RBAC-grade group authorization, and a heavily-tested (>2:1 test:source) client with well-built on-device caching and message-layer self-healing. The weakness is **everything operational around the one relay box**: no CI/CD, single-EC2 SPOF defaulting to a volatile in-memory backend, no horizontal scaling, no client crash reporting, no request-rate limiting, and committed signing secrets. Decentralization legitimately removes a lot of centralized burden (no central auth, no session store, no CDN for E2E ciphertext) — but it does **not** excuse the relay's availability, durability, and deployment gaps, which are the real launch risks.

## Executive Summary

The hard part of this product — the decentralized, post-quantum, end-to-end-encrypted messaging core — is genuinely well-built, and that is the headline. Six layers earned a **B**, and they are exactly the ones that define the product: a maintainable feature-first Flutter client with >2:1 test:source and machine-enforced 741/741/741 localization parity (**L1**); an explicit, frozen-contract-tested protocol with uniform result envelopes and idempotent stores (**L2**); 256-bit device-only SQLCipher encryption-at-rest with disciplined transactional migrations (**L3**); a real self-sovereign crypto identity — BIP39 → Ed25519 + ML-KEM-768, signed QR pairing, safety numbers, a 3-deep rotation ring (**L4**); production-grade RBAC + cryptographically-attested group membership (**L5**); and correct on-device caching with N+1-killing batched summaries (**L11**). For a pre-launch app, the on-device substance is ahead of most startups.

Where it is at startup-MVP level is equally clear, and it clusters in two places. First, **everything that touches the single EC2 relay** drops to **C**: Hosting (**L6**), Cloud/Compute (**L7**), Security (**L9** — dragged down by ops, not crypto), Rate Limiting (**L10**), and Availability/Recovery (**L14**). Second, the **engineering-process and operational-visibility layers are essentially absent (D)**: there is no CI/CD (**L8**), no horizontal scaling or HA for the relay tier (**L12**), and no client crash reporting or production telemetry sink (**L13**). The common thread: the on-device core is mature; the box it falls back to and the pipeline that ships it are not.

The central framing for reading these grades: **decentralization legitimately makes several "centralized" concerns N/A, so the relay-dependent layers must be judged separately from the P2P core.** Heavy compute, routing, message storage, and identity all live on-device; the EC2 relay does one narrow job — offline delivery and NAT-traversal fallback. That means a low grade on "Load Balancing" or "Caching/CDN" is not the same failure it would be for a centralized SaaS, because there is no stateless app tier to balance and no public content to cache. The correct lens is: the **B**s describe a strong product, and the **C/D**s describe a single un-redundant server plus a missing dev/ops pipeline — a smaller, cheaper surface than the grades alone suggest.

That said, two findings are not "hardening later" — they gate launch. A **committed-secrets leak** (Apple `.p8`, Android `.jks`, and two built `.ipa`s tracked in git) compromises store-signing identity for both platforms, and the **relay's default in-memory backend** silently discards every queued offline message, push token, and rendezvous registration on each restart or crash. Both are cheap to fix — the Redis-with-persistence backend is already built and one env flip away — but neither is acceptable in a shipped build. Everything else on the roadmap is genuine hardening of an already-strong core.

## Biggest Risks (ranked)

1. **Committed signing secrets in git** — Apple `AuthKey_*.p8`, Android `upload-keystore.jks`, and two `mknoon.ipa` artifacts are git-tracked and `APPLE/` is not gitignored; anyone with repo access owns the store-signing identity for **both** platforms. Trivially exploitable, irreversible until rotated. — **L6, L9**
2. **Relay defaults to a volatile in-memory backend** — the documented systemd deploy never sets `RELAY_BACKEND=redis`, so every restart/crash (with `Restart=on-failure`) wipes all queued offline 1:1/group messages, push tokens, and rendezvous registrations. Silent, routine data loss on the critical offline-delivery path. — **L3, L7, L12, L14**
3. **Total blindness to client crashes** — no Crashlytics/Sentry and no `FlutterError.onError` / `runZonedGuarded` / `PlatformDispatcher.onError`; the 3,037 well-redacted telemetry events are all `kDebugMode`-gated with no field sink. You will not know if TestFlight users are crashing or why. — **L13**
4. **Single EC2 relay SPOF + hardcoded, pinned relay identity** — one box, one AZ, no LB/standby/backup; relay-down stops all WAN delivery (only same-LAN mDNS survives), and the relay's libp2p key is the committed default whose peer ID the client pins, so rotation forces a client re-release and repo-access enables impersonation. — **L6, L7, L9, L12, L14**
5. **1:1 message forgery / sender spoofing** — 1:1 envelopes carry no sender signature and the 1:1 inbox store does not enforce `from==remotePeer` (the group store does); a holder of the recipient's ML-KEM public key can forge a relay-delivered message attributed to a known contact, and the spoofable `from` misleads push attribution. — **L2, L4, L5, L9**
6. **No request-rate limiting + unauthenticated store + unbounded media disk** — zero token-bucket/throttle anywhere on the relay; unauth 1:1 store enables targeted inbox-fill and FCM-cost amplification, and `handleMediaUpload` allows ~5 GB × distinct recipient IDs to disk on the one box → cheap DoS. — **L9, L10, L12**
7. **No CI enforcement + no account recovery** — no `.github`, no hooks, nothing blocks a gate-failing or analyze-regressing commit; releases are hand-driven. Separately, lost device + lost 12-word mnemonic = permanent unrecoverable account loss (the phrase is an opt-in settings card with no onboarding write-down/verify) — a real retention/support risk at launch. — **L8, L4, L14**

## What Decentralization Makes N/A (do not build this)

- **Public CDN / edge caching tier for media + assets** — blobs are E2E ciphertext, one-shot and delete-on-ack; there is no cacheable public content. The relay media store is an origin/source-of-truth queue, not a cache. (L11 confirms CDN is N/A by design.)
- **Autoscaling a stateless application/compute tier** — message processing, decryption, and routing decisions all run on-device. There is no app-server fleet whose CPU scales with users; the relay does one narrow fallback job. (L7, L12)
- **A central message database (system-of-record) + its sharding, backups, and content search index** — the on-device SQLCipher store is the source of truth. Do not build server-side message storage, replication, or search. _(Caveat: relay queue durability — Redis persistence — is NOT N/A; build that.)_
- **A centralized auth/identity server** — no password store, OAuth, session tokens, server-side MFA, or forced-logout infra; identity is self-sovereign keys. _(Caveat: client-side recovery/escrow IS still needed — see Risk 7.)_
- **Server-side content moderation / message-content compliance scanning** — the relay is zero-knowledge (canary-verified), so it cannot read content to moderate or scan. _(Caveat: metadata — social graph, timing, plaintext usernames in invites — still leaks; that is a real L9 gap, not N/A.)_
- **Application-tier load balancer** — there is no stateless request-handling tier to put behind an LB; only the relay fallback would ever need redundancy, and that is relay-HA (build it), not classic web-tier load balancing.

## 1. Frontend Foundations

**Grade:** B · **Status:** Solid · **Decentralization:** N/A-by-design is minimal — the full frontend-foundation bar applies; decentralization only explains the heavy dependency graph, it does not excuse it.

**Assessment.** This is a real, maintainable, unusually well-tested Flutter client (223,956 LOC of `lib/` against 492,712 LOC of tests across 981 `test/` files plus 116 `integration_test/` files — a >2:1 test-to-source ratio), not a prototype. The feature-first layout, theme-token system, and localization discipline are genuinely strong, and the documented 156–164 perf pass is substantive. The debt is concentrated and visible: a ~53-parameter manual-DI composition root, several 2.5k–5.7k-line "wired"/listener files, a near-empty central widget library, and single-theme / RTL / golden gaps. It is maintainable today but is starting to accrete structural debt in the screen + composition layer faster than it is being refactored. Grade held at **B**: the corrections found during verification (zero golden tests rather than one, ~53 DI params rather than ~60, slightly lower RTL-hazard counts) do not move the overall picture — the foundation is solid and consistently applied, with debt concentrated in the screen/composition tier.

**What exists (and how good)**
- Feature-first structure (19 features under `lib/features/`, cross-cutting under `lib/core/`) — strong — `lib/features/`, `lib/core/`
- Internal layering presentation/application/domain/data — adequate (present per-feature, but not uniform) — `lib/features/feed/data/feed_cleared_repository_impl.dart` (proper `data/`) vs `lib/features/conversation/domain/repositories/message_repository_impl.dart` (impl colocated in `domain/`)
- State management via lightweight `ChangeNotifier`/`ValueNotifier` + injected use-cases, no framework lock-in — adequate — `lib/features/feed/application/app_shell_controller.dart:9` (`AppShellChangeKind` notify-split enum), `:11` (`AppShellController extends ChangeNotifier`); `lib/features/feed/application/feed_store.dart:25` (`ValueNotifier<List<FeedItem>>`)
- Theme tokens as `ThemeExtension`s with proper `lerp`/`copyWith` + context extension + non-null fallback — strong — `lib/core/theme/feed_tokens.dart:14`, `lib/core/theme/background_readable_colors.dart:9`, registered at `lib/core/theme/app_theme.dart:33`, palette in `lib/core/theme/app_colors.dart`
- Localization (en/ar/de) via generated `gen-l10n` (`l10n.yaml`) with **perfect key parity (741/741/741)** — verified by JSON parse: 0 keys missing or extra in any direction; only 1 byte-identical AR value (`account_migration_paste_payload_hint`). - **Later:** Add a golden-test baseline for `letter_card`/feed/orbit (currently zero), a MaterialApp `builder` `textScaler` clamp with large-font tests, an RTL lint pass converting `EdgeInsets.only(left/right)`→`EdgeInsetsDirectional` and `Alignment.centerLeft/Right`→`AlignmentDirectional`, and a light/system theme to unlock `themeMode`. (M)
## 2. APIs & Backend Logic

**Grade:** B · **Status:** Solid · **Decentralization:** relay is a deliberately dumb zero-trust store-and-forward; bridge + use-case layers are fully owned and fully apply

**Assessment.** The protocol surface is genuinely good for a pre-launch P2P app: every relay operation, native-bridge command, and use-case is an explicit, named contract with idempotent stores, consistent result envelopes, and a frozen-contract regression test that fails CI on any rename/removal/retype. The two real liabilities are organizational, not protocol-level — `P2PServiceImpl` (4250 lines, 5 interfaces) and the `send_chat_message_use_case.dart` file (1893 lines) are god-class hotspots where business logic and transport policy entangle. The relay's exact-match, no-negotiation protocol and absent request-rate-limiting are acceptable today but are the items most likely to bite at scale.

**What exists (and how good)**
- Relay inbox API — strong — 10 explicit actions dispatched in one place: `store/retrieve/retrieve_pending/ack/register_token/unregister_token/group_store/group_retrieve/group_retrieve_cursor/group_history_repair_range` (`go-relay-server/inbox.go:1530`); media `upload/download/delete/list/profile_upload/profile_download/profile_delete` (`media.go:411`); rendezvous `REGISTER/UNREGISTER/DISCOVER` (`rendezvous.go:155-159`)
- Frozen wire contract — strong — `protocol_contract_test.go:40/79/151` pins the served protocol IDs, the exact `inboxResponse` JSON key set (17 keys), and the `OK/NO_MESSAGES/ERROR` status strings; renames/removes/retypes fail CI (NET-REL-07, mutation-verified per the test's own header)
- Protocol versioning — adequate — semver-namespaced IDs `/mknoon/{chat,inbox,media}/1.0.0` (`go-mknoon/node/config.go:21-24`, rendezvous is `/canvas/rendezvous/1.0.0`); `protocol_version_test.go:51` proves the chat stream negotiates only the current version (`/mknoon/chat/0.9.0` is refused, `:80`) and `:139` locks the versioned inbox protocol; group-envelope `version` strictness ("3" accepted, "2"/"4" rejected) is enforced in the pubsub path (`pubsub_test.go:2054-2058`)
- Idempotency — strong — relay mints/dedups by messageId (`inbox.go:787` `ensureInboxMessageID`, `:840` `InboxStoreResultDuplicate`), and a duplicate store skips the push (`inbox.go:840-847`); Dart stamps `dedupKey` (defaults to the message id, a forward keeps the propagated source key) so a re-minted forward still dedups (`send_chat_message_use_case.dart:349`)
- Auth on the right operations — adequate — retrieve is keyed on the libp2p-authenticated `remotePeer` (you can only drain your own inbox, `inbox.go:1576`); group retrieve is membership-authorized (`:1656`, `RetrieveAuthorized`); media download/delete authorizes on `AllowedPeers` (group) or `To` (1:1) — `containsPeer(meta.AllowedPeers, remotePeer)` (`media.go:522-531`)

**Gaps / what is missing**
- **[high]** `P2PServiceImpl` god-class — `lib/core/services/p2p_service_impl.dart:64` is 4250 lines implementing `P2PService, DetailedInboxStore, ReadinessProofRecorder, P2PFullInboxDrain, DurableLanSender` with ~20 injected deps and ~90 methods; it conflates node lifecycle, health-check/watchdog recovery (`_performHealthCheck`, `:3029`), inbox drain/replay (`_replayStagedInboxEntries`, `:1137`), sticky-transport learning (`_LearnedTransport`), LAN discovery, and push-token logic. Central change-risk and review-cost concentrator.
- **[medium]** Transport policy buried in a use-case — `send_chat_message_use_case.dart` is 1893 lines, dominated by a single `sendChatMessage` use-case that embeds the full transport race (local/direct/relay), grace window, sticky head-start, low-confidence concurrent-inbox, and relay-probe fallback inline; this transport orchestration arguably belongs behind `P2PService`, leaving the use-case to own only intent/persistence.
- **[medium]** No request-level rate limiting on the relay — `limits.go` only sizes libp2p relay reservations/circuits (`MaxRelayReservations` 512, `MaxConnectionsPerPeer` 8) and per-recipient inbox depth (`maxMessagesPerPeer = 100`, `inbox.go:27`). No token-bucket/throttle on `store`/`group_store`, so an authenticated peer can fan out to fill many victims' inboxes to cap — an abuse/DoS vector for a public box.
- **[medium]** Un-negotiated, stringly-typed relay contract — `protocol_contract_test.go` itself documents (header, `:16-30`) that IDs are exact-match, hard-coded into every shipped binary with no fallback, and clients string-match `status`; a breaking change hits 100% of un-updated clients and the only escape is a manual multi-relay migration. Powerful as a guardrail, fragile as a forward-compat story.
- **[low]** Sender-binding asymmetry — 1:1 `store` accepts a client-supplied `from` and only falls back to `remotePeer` when empty, never rejecting a mismatch (`inbox.go:1535-1538`), whereas `group_store` enforces `from != remotePeer → "not authorized"` (`inbox.go:1638`). E2E encryption makes the relay `from` non-authoritative for content, but it still feeds the push `SendNotification(... entry.From ...)` (`inbox.go:867`), so a peer can forge the apparent sender of a 1:1 notification.
- **[low]** Hand-rolled protobuf for rendezvous — `pb.go` is manual `protowire` encode/decode (`pb.go:12`, wire-compatible with `@canvas-js/libp2p-rendezvous` by hand) even though `proto/rendezvous.proto` exists; no generated `.pb.go`. Correct today but an easy place to drift.

**Decentralization note.** By design the relay is a thin, content-blind store-and-forward + discovery node, so server-side content validation, centralized auth/identity, an OpenAPI/REST gateway, and trusting any sender claim are correctly **N/A** — sender identity and integrity are enforced cryptographically inside the E2E (ML-KEM) envelope by the recipient, not the relay. What is genuinely **owed** regardless of decentralization: relay abuse/rate-limiting hygiene, consistent `from` binding, and a real forward-compat path for the wire protocol; the bridge and Dart use-case layers are fully owned product code where the normal API-quality bar applies in full.

**Recommendations**
- **Now:** Add per-peer request rate limiting (token bucket) to `store`/`group_store` in the inbox handler, and make 1:1 `store` bind `from := remotePeer` (or reject a mismatch) like `group_store` already does, since `from` flows into the push `sender_id` (S).
- **Next:** Carve `P2PServiceImpl` into focused collaborators (lifecycle, health/recovery, inbox-drain/replay, sticky-transport, LAN) behind the existing `P2PService` interface, and lift the `sendChatMessage` race orchestration into a `TransportPolicy`/`P2PService` method so the use-case shrinks to intent + persistence (M-L).
- **Later:** Define an explicit forward-compat strategy beyond the frozen test — additive-only envelope/version negotiation and a documented multi-relay rollout runbook — and generate the rendezvous protobuf from `proto/rendezvous.proto` instead of the hand-rolled `pb.go` (M).
## 3. Database & Storage

**Decentralization note.** Durable server-side storage of message *content* is correctly N/A — the relay is a 7d store-and-forward cache and E2EE means a dropped ciphertext just forces a re-send/self-heal. ## 4. Authentication & Identity

**Grade:** B · **Status:** Solid · **Decentralization:** Self-sovereign cryptographic identity; the classic central-auth surface (passwords, OAuth, sessions, central recovery) is structurally absent — mostly N/A by design

**Assessment.** This is the strongest-conceived layer of the stack, and the claims hold up against the code. Identity is a deterministic BIP39 mnemonic → Ed25519 keypair → libp2p peer ID (the peerId is derived from the public key), augmented with a post-quantum ML-KEM-768 keypair, secrets held in iOS Keychain (`first_unlock_this_device`, excluded from iCloud backup) / Android EncryptedSharedPreferences, signed canonical-JSON QR pairing, Signal-style safety numbers folding peerId+Ed25519+ML-KEM, a 3-deep ML-KEM secret-rotation ring, msgId/timestamp replay + strict anti-rollback on key updates, an introduction key-mismatch guard for already-known contacts, and an AEAD account-move (ML-KEM encap → HKDF-SHA256 → AES-256-GCM with canonical AAD) gated by a 5-minute QR TTL and a 6-digit channel-binding confirmation code. The relay is a true zero-trust dumb relay: reads/acks/token-register are authorized by the libp2p-authenticated peer ID and it never sees plaintext or private keys. The B (not A) reflects maturity/UX gaps appropriate to a pre-launch app: recovery is a single unenforced opt-in mnemonic (no cloud/social fallback), MITM verification is opt-in with no persisted verified-state, the 1:1 relay `store` path lets the cosmetic `from` hint be spoofed (groups don't), and stranger-introductions trust introducer-vouched keys with no end-to-end signature from the introduced party.

**What exists (and how good)**

- Post-quantum KEM keypair (ML-KEM-768 via cloudflare/circl, JS-wire-compatible 2400-byte secret) generated for every identity; keygen failure is fatal (no plaintext-only identities) — strong — `go-mknoon/crypto/mlkem.go:25-47`, `lib/features/identity/application/generate_identity_use_case.dart:93-130`

- **[high]** Recoverability hard floor: lost device **and** lost 12-word mnemonic = permanent, unrecoverable account loss. Central recovery is correctly N/A, but the total absence of any fallback is a real consumer-retention/support risk.
- **[medium]** 1:1 inbox `store` does not enforce `from==remotePeer` (`from := req.From; if from == "" { from = remotePeer }`), unlike `group_store` which rejects `from != remotePeer` — `go-relay-server/inbox.go:1535-1538` vs `1638`. The relay-stored sender hint is therefore spoofable. Impact is cosmetic — the envelope is E2E-signed and reads are peer-authenticated, so it cannot forge message content or identity — but it can mislead push/notification "from" and is an inconsistency between the two store paths.
- **[medium]** MITM verification is opt-in: the safety number is shown/copyable but there is no in-flow comparison prompt, no persisted "verified" flag on the contact model (`contact_model.dart` has no verified field), and no re-key warning surfaced in the conversation UI (the `CONTACT_KEY_ROTATED` event is a flow log, not a user-facing banner). A relayed/substituted QR (attacker presents their own key) goes undetected unless the user voluntarily compares out-of-band.
- **[medium]** Transitive trust — stranger case: introductions carry the introduced party's Ed25519+ML-KEM keys asserted by the introducer with no end-to-end signature from the introduced party at intro time (`handle_incoming_introduction_use_case.dart:198-211`). The accept path *does* guard against a substituted key when the other party is already a known contact (`_hasIntroContactMlKemMismatch`, `accept_introduction_use_case.dart:84-95,217-233`), but for a genuine stranger (no prior contact record) the guard returns false and the vouched keys are trusted as-is — a malicious introducer can substitute keys when bridging two people who don't yet know each other. The later contact request is independently signature-verified, but no reconciliation forcing the signed-request key to equal the introducer-vouched key was found for the stranger path.
- **[medium]** ML-KEM secret is mirrored into a shared Apple app-group keystore (`group.com.mknoon.app.share`) so the push/NSE extension can decrypt previews — `identity_repository_impl.dart:177-195`, `flutter_secure_key_store.dart:5`. Deliberate, but it widens the post-quantum secret's blast radius to the extension sandbox.
- **[low]** Sender-binding check is skipped on the offline path: `peerId != message.from` is bypassed when `message.from == 'unknown'`, falling back to the self-certifying signature only — `handle_incoming_message_use_case.dart:255`.
- **[low]** No app-level abuse throttling on inbox `store` / contact requests; `limits.go` is capacity-only (per-peer inbox cap, per-group cap, reservation/connection caps) with no per-time rate limiting — `go-relay-server/limits.go:40-47`.
- **[low]** Keychain accessibility doc/code drift: the class doc says `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` but the code uses `KeychainAccessibility.first_unlock_this_device` (AfterFirstUnlock) — `flutter_secure_key_store.dart:10,21`. The code choice is correct for background/NSE decryption; only the comment is wrong.

**Decentralization note.** Password reset, OAuth/social login, session tokens/JWT, server-side identity store, central login rate-limiting, and central account recovery are all genuinely N/A by design — libp2p transport auth (authenticated peer IDs) replaces sessions, and self-sovereign keypairs replace accounts. The overwhelming majority of a traditional "Authentication & Identity" checklist is structurally absent here, which is why the stance is *mostly* N/A by design. What is *owed* (and partly missing) is the decentralized equivalent: an enforced/redundant key-backup story and active MITM-verification UX. Those are product-maturity gaps, not violations of the model — and the cryptographic equivalents that do apply (key storage, key rotation, signed pairing, AEAD migration, zero-trust relay) are largely present and well-built.

**Recommendations**
- **Now:** Enforce a mnemonic-backup-and-verify step in onboarding before the account is usable, and align the 1:1 inbox `store` to reject `from != remotePeer` as `group_store` already does. (S/M)
- **Next:** Persist a per-contact "verified" state driven by an in-flow safety-number comparison, surface a re-key warning in the conversation header on `CONTACT_KEY_ROTATED`, and extend the introducer-key reconciliation to the stranger path (compare the later signed contact-request key against the introducer-vouched key; warn/block on mismatch). (M)
- **Later:** Offer an opt-in encrypted-cloud or social/escrow recovery so non-technical users aren't one lost phone from total loss; narrow the NSE's ML-KEM exposure to a dedicated push sub-key; add relay-side per-time rate limiting on contact-request/inbox `store`. (L)

A party holding the recipient's (semi-public) ML-KEM public key who has the spoofed contact as a known contact of the victim can forge a relay-delivered message attributed to that contact. (Direct libp2p delivery is transport-authenticated; the forgery is specific to the relay inbox path.)
- **[medium]** No forward secrecy — 1:1 uses the recipient's *static* long-term ML-KEM key for every message and groups use a long-lived epoch key, so compromise of those keys decrypts all retained history. - **[medium]** Inbox-store DoS — the 1:1 inbox store needs no auth and no `from` verification (above), and there is no per-peer/per-IP request rate limiter — only finite capacity caps (`maxMessagesPerPeer=100`). An attacker can spam-fill a victim's inbox to `INBOX_FULL` while spoofing the sender.
- **[low]** The ML-KEM shared secret is used directly as the AES-256 key with no extra KDF (`encrypt.go:61`); this is acceptable for ML-KEM (the KEM output is already a uniformly-random key), unlike a raw DH output. 1:1 and group AES-GCM pass `nil` AAD (only contact-requests bind `msgId|ts`); group authentication is instead provided by the Ed25519 signature over `groupId|epoch|ciphertext`.

**Decentralization note.** Most of this layer genuinely applies and is well-delivered (E2E crypto, at-rest, transport, zero-knowledge relay). Truly N/A-by-design: there is no server-side account/session/auth to grade (identity is a self-sovereign BIP39/Ed25519 keypair) and no centralized PKI/CA (trust is TOFU via in-person QR + signed contact requests). But "the relay can't read messages" being by-design does NOT excuse the committed relay key or the plaintext username/groupname metadata — relay-identity integrity and metadata minimization are owed and have real, verified gaps.

(S)

## 10. Rate Limiting

**Grade:** C · **Status:** Partial · **Decentralization:** the shared relay is the one chokepoint and genuinely owes DoS throttling; per-account quotas are awkward (self-minted peer IDs)

**Assessment.** What the relay calls "limits" are *capacity / admission* controls — bounded storage with TTLs, eviction, frame caps, an FCM push-data budget — plus libp2p's default (untuned) resource manager and the circuit-relay reservation envelope. Those are real and tested, and they bound *per-victim* damage. But the actual subject of this layer, *request-rate* limiting, is **entirely absent** on the one centralized, publicly-reachable EC2 relay: a non-test grep for `rate.Limiter`/`x/time/rate`/`tollbooth`/`ratelimit`/`throttle` returns **zero** (`golang.org/x/time` appears only as an `// indirect` transitive dep in `go.mod:145`, unused by relay code). There is no token bucket / sliding / fixed window on any action, no per-peer/per-IP/connection throttle, no upload-rate or push-rate cap, and no abuse banning. Combined with an **unauthenticated 1:1 `store`/media `upload`** and **unbounded bucket counts**, an attacker gets cheap targeted DoS, disk/memory exhaustion, and (against registered victims) FCM-cost amplification. The client side is the bright spot (jittered, coalesced, debounced) — but it is cooperative and the relay enforces none of it. Blast radius is bounded by the architecture (E2EE means the relay leaks no plaintext, and online peers talk directly P2P) — the exposed asset is relay *availability* / the offline-delivery path, not confidentiality.

**What exists (and how good)**
- Inbox per-peer capacity cap (100) with reject-new-on-full + structured `INBOX_FULL` (occupancy/capacity) and messageId dedup — strong, and unit-tested — `go-relay-server/inbox.go:27,830-870,1548-1555`, `backend_memory.go:130`, `limits_test.go:19-67`
- Group inbox per-group cap (500) with evict-oldest + 7d TTL — adequate, tested — `inbox.go:31`, `backend_memory.go:327,374-377`, `limits_test.go:71-103`
- Group path is the *more* hardened one: `group_store` binds `from` to the authenticated `remotePeer` (rejects spoofed sender) and `group_retrieve` is ACL-gated — `inbox.go:1638-1639,1656`
- Media size caps: per-blob 5 GB, per-recipient 5 GB + 100 blobs, evict-oldest prune, 7d TTL / 10-min cleanup; download/delete authorized against `To`/`AllowedPeers` — adequate per-recipient, weak globally — `media.go:27-28,160-193,438,522-534`
- FCM push-data budget (`maxPushDataBytes=4000`): oversized media envelope drops ciphertext and sends a visible generic fallback (the 142 fix) — strong — `inbox.go:45-53`
- Frame caps (inbox 128 KB `maxFrameLen` on `readFrame`/`writeFrame`; rendezvous 1 MB varint) and rendezvous clamps (`maxTTL=2h`, `maxDiscoverLimit=64`, `maxNamespaceLen=256`) + signed-peer-record validation on register — adequate — `inbox.go:26,1391-1412`, `rendezvous.go:17-19,171-186,228-234`
- libp2p relay-service envelope: reservations 512, circuits/peer 8, `MaxReservationsPerPeer=1` (circuit-relay v2 only, **not** app inbox/media/rendezvous streams) — adequate for relay-circuit abuse only — `limits.go:40-47,77-84`, `main.go:72-74`
- libp2p default ResourceManager (auto-scaled to host memory) provides an aggregate backstop on total connections/streams/memory — present but untuned to the EC2 box, and it does **not** govern the application-level inbox/group/rendezvous maps — `main.go:62-76`
- Client cooperative throttling: ±20% jittered self-rescheduling retry (5 min) + continuity sweep (30 s), 5 s debounce, single in-flight drain coalescing, reconnect coalescing — strong — `pending_message_retrier.dart:16-19,32-33,245-259`, `p2p_service_impl.dart:1671-1686,2676-2677`

**Gaps / what is missing**
- **[critical]** No request-rate limiting on *any* relay action (store/retrieve/ack, media upload/download, rendezvous register/discover, push-token register). Verified: zero `rate.Limiter`/`x/time/rate`/`tollbooth`/`ratelimit`/`throttle` in non-test source; stream handlers process every stream with no admission gate. Capacity caps bound *how much is stored*, not *how fast an attacker can hammer* — `main.go:109-117`, `inbox.go:1497-1531`.
- **[critical]** Media upload is unauthenticated for the uploader and has no global disk cap: `handleMediaUpload` checks only `id/to/size` + per-blob 5 GB, then `io.CopyN`s up to 5 GB to disk *before* any prune; any peer can upload to any `To`, and recipient buckets are unbounded in count, so total disk on the single EC2 box is `~5 GB × distinct recipient IDs` → disk-exhaustion DoS — `media.go:433-508`.
- **[high]** The 1:1 inbox `store` is unauthenticated and `From` is spoofable — `from := req.From; if from == "" { from = remotePeer }` with no recipient contact check, so any connected peer can write to any `To` (the group path's `from==remotePeer` guard is **not** mirrored here). Enables targeted inbox-fill DoS (fill a victim's 100 slots → legit senders bounce on `INBOX_FULL`) and push/FCM-cost amplification: each `ShouldNotify` store fires `go push.SendNotification` with no per-recipient push-rate cap. Amplification is bounded — it only fires for recipients with a *registered* FCM token, and self-limits at the 100-slot inbox cap per offline victim — but an *online* victim who drains frees slots, so a sustained store-spray yields unbounded pushes over time — `inbox.go:1531-1545,866-867,135-142`.
- **[high]** Unbounded bucket counts + no per-peer/IP application-level throttle: inbox keyed by arbitrary `To`, group inbox by arbitrary `groupId`, rendezvous by arbitrary `ns`, all with no cap on the number of distinct buckets and no `ConnManager`/`ConnectionGater`. These maps are **not** covered by the default ResourceManager (which only bounds libp2p conns/streams/memory), so memory exhaustion via ID-spray (one tiny store to each of millions of random `To` strings, persisted 7d) is open; raw connection/stream floods are partially — not fully — backstopped by the untuned default rcmgr — `main.go:62-76`, `inbox.go:1531-1545`.
- **[medium]** No breach response beyond reject/evict: no 429-style rate signal, no temporary ban / tarpit / blocklist for abusive peers, no per-peer rendezvous-registration cap, no discover-rate cap (discovery pollution + peer-set scraping, 64 regs/call). `/metrics` is served unauthenticated on `:2112` — `main.go:204-211`, `rendezvous.go:166-250`.
- **[low]** Health-check timer is fixed 30 s with no backoff/jitter (`_consecutiveRefreshFailures` is counted and reported to the relay but does **not** lengthen the interval), so on a relay restart all clients reconnect within one 30 s window — a mild reconnection-storm contributor — `p2p_service_impl.dart:247,2156,2739,2747`.

**Decentralization note.** Per-*account* quotas are genuinely awkward here — there are no server accounts and peer IDs are free to mint (Sybil-friendly), so identity-bound rate limits are not the right primitive and are fairly N/A. The decentralized design also *shrinks* the blast radius: E2EE/ML-KEM means a relay attacker leaks no plaintext, and online peers route directly P2P, so the exposed asset is relay availability and the offline-delivery fallback — not confidentiality. But the relay is the single shared, publicly-reachable resource in the system; per-connection / per-source-IP request throttling, upload-rate and push-rate caps, and global disk/memory backpressure are *owed regardless of decentralization* and are the genuinely missing piece, not an N/A.

**Recommendations**
- **Now:** Add a per-connection/per-peer token-bucket in front of the three stream handlers (cheap `golang.org/x/time/rate` keyed by `s.Conn().RemotePeer()` + remote IP — the dep is already vendored) and a global media disk-usage ceiling that rejects uploads under disk pressure; reject over-rate with a structured `RATE_LIMITED` response. (M)
- **Next:** Authorize 1:1 `store`/media `upload` against the recipient's contact/allow set (or require a recipient-issued capability token) to kill targeted inbox-fill and push/FCM-cost amplification; mirror the group path's `from==remotePeer` guard on the 1:1 store; cap distinct inbox/group/rendezvous bucket counts and per-peer rendezvous registrations; firewall or auth-gate `:2112/metrics`. (M)
- **Later:** Configure an explicit libp2p `ResourceManager`/`ConnManager` envelope tuned to the EC2 box, add a temporary blocklist/tarpit for repeat over-rate peers, and add jittered exponential backoff to the client health-check so relay restarts don't trigger a 30 s reconnection wave. (L)

Redis externalizes control-plane only; a blob uploaded to relay A is invisible from relay B, so multi-relay breaks media until storage moves to S3/EFS.
- **[medium]** Per-relay hard ceiling `MaxRelayReservations` default 512 (runbook bumps to 2048) caps the number of NAT'd peers that can hold a circuit reservation on one node — likely saturates before CPU/RAM for a relay-heavy population (`limits.go:40-47,77-84`).
- **[medium]** Unbounded push fan-out: group send spawns one goroutine per recipient with no semaphore/worker-pool (`inbox.go:1071-1098`, `go s.push.SendGroupNotification` at `:1091`); 100-user-group prototypes → N concurrent FCM calls per message. (1:1 also fires one goroutine per message at `inbox.go:867`, but single-recipient so not a fan-out concern.)
- **[low]** No traditional LB is wired — and an L4/L7 ALB can't cleanly front libp2p QUIC/relay-circuit traffic anyway (peer-ID-bound stateful connections). The correct model is client-side multi-relay + DNS, which exists and is flag-enabled by default but ships with a single relay **address**: both default addrs (WSS + QUIC) point at one peer `12D3KooWGMYM…` on `mknoun.xyz` (`go-mknoon/node/config.go:11,15`).
- **[low]** 5GB max blob on a single disk; there is a per-peer 5GB *pending-bytes* eviction cap (`media.go:28`, `maxMediaBytesPerPeer`) but no in-transfer per-peer/global media-**bandwidth** throttle, so one large transfer can dominate the box's NIC/disk.

**Decentralization note.** Classic horizontal app-scaling and an L7 load balancer are *partially* N/A by design: the P2P core moves compute, routing, and most message transport onto clients, so the relay only handles store-and-forward, discovery, media, and push — and libp2p's peer-ID/multiaddr model means "load balancing" should be client-side relay selection (already built), not an ALB. What is *genuinely owed*, and not waivable by decentralization, is relay HA/statelessness: removing the single-box SPOF, deploying the Redis backend so queued state survives restarts, and externalizing media so more than one relay is viable.

**Recommendations**
- **Now:** Flip the deployed relay to `RELAY_BACKEND=redis` + a managed Redis (ElastiCache) and set the bounded limits from the runbook — the code and tests already exist, so a relay restart stops dropping queued messages/tokens. Mostly ops, not code. (S)
- **Next:** Move media + profiles off local disk to shared object storage (S3, or EFS as a stopgap) so the relay tier is truly stateless; ship clients a 2-relay `RelayAddresses` list (selector + routing flag already wired and on) for real failover; bound the group push fan-out with a worker-pool/semaphore. (M)
- **Later:** Run N relay processes (distinct `RELAY_PRIVATE_KEY` each) on shared Redis + shared media, distributed via DNS/anycast with client-side relay selection as the "LB"; add autoscaling driven by `relay_connections_active` / reservation saturation; make Redis itself HA (replica/sentinel) since it becomes the new SPOF. (L)
## 13. Error Tracking & Logging

**Grade:** D · **Status:** Early · **Decentralization:** relay metrics genuinely owed and present; client crash visibility genuinely owed and absent — only per-user server-side log aggregation is N/A by design

**Assessment.** The honest bottom line: if a TestFlight user's app crashes or throws an uncaught error, the team will never find out. There is **no crash reporter on any platform** and **no global Flutter error handler**, so the entire client-side crash surface is invisible in release. The app has an impressively large, well-redacted structured-event vocabulary (3,037 `emitFlowEvent` calls across 355 files), but it is `kDebugMode`-gated with only a `@visibleForTesting` sink, so it is dead weight in release — including the 145 notification-timing milestones and `APP_BUILD_INFO`. The relay is the strong half: comprehensive Prometheus instrumentation and 4 Grafana dashboards, but **dashboards-only with no alerting** and unstructured single-box logging with no panic recovery. The plumbing for good observability exists; the production-facing wiring does not.

**What exists (and how good)**
- Structured flow/telemetry events with genuinely strong PII redaction (sensitive keys, peer-ids, multiaddrs, PEM private/secret blocks, base58 peer IDs) — strong *vocabulary*, dead *delivery* — `lib/core/utils/flow_event_emitter.dart:202` (gate `:6,217`; redaction `:42-200`)
- 145 notification timing + `APP_BUILD_INFO` milestones — well-designed but route through the same gated emitter, so dead in release — `lib/core/utils/notification_tap_timing.dart:15,50`, `lib/core/diagnostics/app_build_info.dart:25`
- Push diagnostics that DO emit in release (raw `print()` + `developer.log`, intentionally un-gated) — narrow (tethered-device console only, no remote sink, no file) — `lib/core/utils/push_diagnostics_logger.dart:33-34`
- Relay Prometheus instrumentation incl. push-failure labels (`invalid_token`/`failed`) — strong — `go-relay-server/metrics.go:10-203` (40+ counters/gauges), `go-relay-server/inbox.go:210,219,254`, served `go-relay-server/main.go:206`
- Privacy-safe business metrics (HyperLogLog DAU/WAU/MAU via `axiomhq/hyperloglog`, peer-ids hashed and never stored) — strong design — `go-relay-server/business_metrics.go:11-45`
- 4 Grafana dashboards + journald via systemd — adequate for manual inspection only — `go-relay-server/grafana-{relay,host,redis,business}-dashboard.json`, `go-relay-server/README.md:36`

**Gaps / what is missing**
- **[critical]** No client crash reporter (Sentry/Crashlytics/Bugsnag) anywhere — `pubspec.yaml:57-58` has only `firebase_core ^3.8.1` + `firebase_messaging ^15.1.6`; `android/app/build.gradle.kts:40` applies only `com.google.gms.google-services` (no Crashlytics plugin); the iOS Podfile has no Crashlytics pod (the `Crashlytics` substrings in `ios/Pods/**` are transitive Firebase README/umbrella-header references, not integration). The team has zero production crash visibility.
- **[critical]** No global error handlers — `lib/main.dart:3141` is a plain `runApp()` with no `runZonedGuarded`, and a whole-`lib/` grep finds no `FlutterError.onError` / `PlatformDispatcher.instance.onError` / `ErrorWidget.builder`. Uncaught framework and async errors are silently lost in release.
- **[high]** All structured telemetry is `kDebugMode`-gated with only a `@visibleForTesting` sink — `flow_event_emitter.dart:6` (`flowEventLoggingEnabled = kDebugMode`), `:215` (test sink), `:217` (early return before the `debugPrint`). 3,037 events across 355 files produce nothing in the field, and no code path ever flips the flag on outside tests — no breadcrumbs, no timing, no crash context.
- **[high]** Relay has no alerting — 4 dashboards but no Prometheus alert rules, no alertmanager, no Grafana alerts (0 case-insensitive "alert" matches across the dashboard JSON). Push-failure spikes (`relay_push_sent_total{...="failed"}`), `relay_inbox_rejected_full_total`, disk fill (`relay_media_disk_bytes`), or `relay_connections_active`→0 are caught only by a human watching Grafana. The `:2112/metrics` endpoint is also served with no auth (`main.go:206`).
- **[medium]** Relay logging is unstructured `log.Printf` (~147 calls) to journald on a single EC2 box — no JSON, no aggregation/retention (no Loki/CloudWatch), and no `recover()` anywhere in the relay, so a panicking spawned goroutine crashes the process (only systemd `Restart=on-failure` mitigates, with no crash report).
- **[medium]** No on-device log persistence (no `writeAsString`/log-file in `lib/core/diagnostics` or `lib/core/utils`) and no SLOs/error budgets — nothing to pull from a user's device after a report, and no delivery/latency target defined on the data the relay already gathers.

**Decentralization note.** Decentralization does **not** excuse this layer. A crash reporter capturing stack traces is fully compatible with the E2E/post-quantum privacy model — especially given the strong redaction helpers already in `flow_event_emitter.dart` — and the relay is centralized infra that genuinely owes metrics + alerting. The only part that is N/A by design is routine *server-side per-user log aggregation*: there is no app-server holding user sessions, and message content/keys must never leave the device. Everything else here is owed and missing.

**Recommendations**
- **Now:** Add a client crash reporter (Sentry recommended — supports `runZonedGuarded` + `FlutterError.onError` + `PlatformDispatcher.onError` in one init) and reuse `sanitizeFlowEventDetails` as the `beforeSend` scrubber so no PII/keys leave the device (S). In parallel, add Prometheus/Grafana alert rules on existing metrics: `relay_inbox_rejected_full_total`, `relay_push_sent_total{...="failed"}` rate, `relay_media_disk_bytes`, `relay_connections_active == 0` (S).
- **Next:** Give `emitFlowEvent` a production path that feeds a sampled subset into the crash reporter as breadcrumbs (or a small on-device ring buffer attached to crash reports), so the 3,037-event vocabulary and the 145 timing milestones finally pay off in the field (M). Ship relay logs off the box as structured JSON to a log store for search/retention (M).
- **Later:** Define SLOs/error budgets (1:1 + group delivery success, push delivery, notif-tap→live-render latency from the 145 events once sunk) and add panic-recovery middleware + per-goroutine `recover()` on the relay (M/L).
## 14. Availability & Recovery

**Grade:** C · **Status:** Partial · **Decentralization:** strong message-layer self-heal; infra HA and recovery partly N/A by E2E design but largely unmitigated

**Assessment.** This layer splits hard in two. The **message layer is genuinely strong** (verified B-grade): direct-send-then-relay-inbox custody, a 30s health-check drain + relay recovery, a ±20%-jittered reconnect retrier, relay-side messageId dedup, and a 7-day store-and-forward buffer combine into resilient at-least-once delivery that tolerates transient relay blips. The **infrastructure and recovery story is weak** (D-grade): a single relay node on a single EC2 box in one AZ with only `systemd Restart=on-failure`, a **default in-memory control-plane backend** that loses every queued offline message on a restart, no automated backups committed in-repo, and **no lost-device recovery** (keys are this-device-only and excluded from backups). Against what a pre-launch decentralized TestFlight app needs, it "works but is risky" — survivable at TestFlight scale, but the relay-restart RPO and total device-loss data loss are real, user-visible, and unmitigated. Net: a blended **C (Partial)** — neither sublayer was over- or under-stated by the draft.

**What exists (and how good)**
- Store-and-forward offline buffer (7d) — adequate — `go-relay-server/inbox.go:27-32` (`maxMessagesPerPeer=100`, `maxMessageAge=7*24h`, group `maxMessagesPerGroup=500`/`groupMessageTTL=7*24h`)
- Direct-then-relay-inbox message custody + relay-side dedup — strong — `lib/features/conversation/application/send_chat_message_use_case.dart:461,650,1086` (sendMessageWithReply + storeInInbox), `go-relay-server/backend_redis.go:263-298` (`redisInboxBackend.Store` returns `InboxStoreResultDuplicate` on matching messageId)
- 30s health-check drain + relay recovery + push re-register — strong — `lib/core/services/p2p_service_impl.dart:247` (`healthCheckInterval=30s`), `:3130` (`_attemptRelayRecovery`), `:3178` (`unawaited(_reregisterStoredPushTokenIfAvailable())`), `:3206` (per-poll `_drainOfflineInbox`)
- Reconnect retrier with ±20% anti-stampede jitter (5s debounce / 5min periodic / 30s group-continuity) — strong — `lib/core/services/pending_message_retrier.dart:18-21` (`jitteredRetryInterval` = ×0.8–1.2), `:31-35`
- Send-path self-heal (re-dial via relay on retryable stream-open error) — adequate — `go-mknoon/node/node.go:1327` (`openChatStreamForSend` → `:1348` `recoverPeerForSend` → `:1223` `dialPeerViaRelayWithTimeout`)
- Relay-independent LAN/mDNS path (on by default) — adequate (LAN-only) — `lib/core/local_discovery/bonsoir_discovery_service.dart`, selected at `lib/main.dart:1893` unless `kDisableLocalDiscovery` (`lib/core/debug/e2e_test_mode.dart:2`, defaults false)
- Redis-backed shared control plane (opt-in) enabling future multi-relay — available, not verifiable as live — `go-relay-server/server_bootstrap.go:84` (redis branch), `redis_failover_integration_test.go` (miniredis + helper subprocess proves cross-process survival). The deploy env (`RELAY_BACKEND`) is gitignored, so whether prod runs redis cannot be confirmed from-repo; the *code default* is memory.
- Multi-relay client plumbing already present (only one relay configured) — latent — `go-mknoon/node/relay_selector.go:22` (`relays []RelayInfo`), `go-mknoon/node/multi_relay_test.go`
- Device-to-device account migration (resumable, checkpointed) incl. full SQLCipher snapshot export + import-staging — solid for its scope — `lib/features/account_migration/application/account_migration_transfer_flow.dart`, `migration_transfer_checkpoint_store.dart`, `migration_transfer_keep_alive.dart`, `migration_database_snapshot_exporter.dart`, `migration_database_import_staging.dart`
- E2E means a down/compromised relay leaks nothing — strong (by design) — `lib/core/secure_storage/flutter_secure_key_store.dart:21` (`KeychainAccessibility.first_unlock_this_device`)

**Gaps / what is missing**
- **[critical]** Code-default control-plane backend is in-memory (`go-relay-server/server_bootstrap.go:36` `loadBackendConfigFromEnv` → `kind=backendKindMemory` when `RELAY_BACKEND` is unset; memory branch at `:60` uses Go-map stores). On that default a `systemd` restart/crash wipes all queued offline messages, push tokens, and rendezvous (RPO ≈ everything queued). There is **no committed deploy config** pinning the box to redis-with-persistence, so the safe path depends entirely on an unversioned env var. Only *partially* self-healed by client re-store, and only while the sender stays online and hasn't treated inbox-store as terminal.
- **[high]** Single relay, single AZ, process-only HA — `go-mknoon/node/config.go:11,15` (one peer ID `12D3KooWGMYM…` at `mknoun.xyz` over WSS:4001/QUIC:4002), `server_config.go:61` (`ServerIP4="13.60.15.36"`), `README.md:19-20` (`Restart=on-failure`/`RestartSec=5`, manual deploy). No standby, no LB; host/AZ/bad-deploy failures need manual SSH recovery → RTO is human-bound (minutes-to-hours).
- **[high]** No automated backups committed in-repo: no Redis persistence (AOF/RDB) config or backup/snapshot script anywhere under `go-relay-server/` or `scripts/`; relay media on unreplicated local `/data/media` (`media.go:21,23`, 7d TTL).
- **[high]** Lost/dead device = permanent loss of identity + SQLCipher history. Keys use `KeychainAccessibility.first_unlock_this_device`, "excluded from iCloud/iTunes backups" (`flutter_secure_key_store.dart:9-11,21`). The only recovery is device-to-device migration requiring the *old* device alive *and* paired to a new one; there is no key escrow, seed phrase, social recovery, or even a forced/nudged-migration UX before device handoff. Note: a full SQLCipher snapshot export + import-staging already exists, but is coupled to that live-old-device migration flow — it is **not** a standalone export-to-file/cloud backup you can restore from later.
- **[medium]** Relay-down WAN delivery effectively stops: rendezvous discovery, circuit dialing, and the offline buffer are all relay-bound. Only same-LAN mDNS peers keep working — so "decentralized P2P survives the relay outage" is true only on-LAN, not for the common cross-network case.
- **[low]** The "failover" test names oversell redundancy: `go-relay-server/failover_test.go:30-37` shares one in-process memory backend object between `rzA`/`rzB` (proves abstraction correctness, not HA); `redis_failover_integration_test.go` proves state survives across *processes* on one shared Redis (proves Redis *can* back multi-relay) but no Redis cluster/sentinel and no second live relay are exercised or deployed.

**Decentralization note.** Server-side message *confidentiality during an outage* and *key escrow* are correctly N/A by E2E design — the relay can never read traffic (post-quantum ML-KEM), and keys intentionally never leave the device, so a leaked/seized relay yields nothing. The keychain-mirror backfill (`lib/main.dart:1332`, `mirrorAllKeysToSecureStore`/`mirrorAllMutedGroups`) is *not* key DR — it only copies group keys into the App-Group keychain for the iOS NSE push-preview decrypt. But *availability* and *a recovery story* are still owed: the single-relay SPOF, the volatile default backend, and the all-or-nothing device-loss outcome are infrastructure/UX choices, not inevitable consequences of decentralization (the `RelaySelector` already fans out over a relay list; only one is deployed).

**Recommendations**
- **Now:** Set `RELAY_BACKEND=redis` with Redis AOF persistence on the EC2 box **and commit it to the deploy runbook/systemd env** so the safe backend isn't an unversioned env var — single highest-leverage fix, converting relay-restart RPO from "everything queued" to near-zero (S). In parallel, add a one-line in-app pre-handoff nudge/warning that keys are device-only and only account migration preserves them (S).
- **Next:** Stand up a second relay peer and seed both in the client `RelayAddresses` (the selector already fans out), and add scheduled backups (Redis snapshot + `/data/media` sync to object storage) plus an uptime/`up{job="relay-server"}` alert off the existing Prometheus/Grafana stack (M). Repurpose the existing migration snapshot exporter into a client-side encrypted DB/key export-to-file as a manual backup escape hatch that does **not** require a live old device (M).
- **Later:** Add managed/replicated Redis (cluster or sentinel) and a documented relay disaster-recovery runbook with measured RTO targets; consider optional encrypted key/seed backup or social-recovery so device loss is no longer terminal (L).

## Methodology & limitations

**How this was produced.** A 29-agent orchestrated workflow: 14 **audit** agents (one per layer, each scoping via the graphify knowledge graph then reading real source/config), 14 **verify** agents (an independent skeptic per layer that re-opened the cited files, corrected counts/line numbers, and flagged unsupported claims), and 1 **synthesis** agent (the cross-layer executive brief). ~2.5M tokens, 814 tool calls, ~18 min wall-clock. All agents were read-only on existing files.

**Verification outcome.** 0 of 14 grades changed during fact-checking — the draft assessments held — but the skeptics caught and corrected numerous count/citation drifts (e.g. golden-test count 1→0, StartupRouter deps ~60→~53, a `media.go` auth line, the multi-relay flag being on-by-default not off, two `.ipa` files not one) and over/understatements (e.g. contact-request pairing is *not* forward-secret; the relay 1:1 `from`-spoof is cosmetic/push-attribution, bounded by E2E signing). Each section ends with the verifier's note so you can see exactly what was confirmed vs corrected.

**Key limitation — the live relay environment is unverifiable from the repo.** The deploy config (`RELAY_BACKEND`, `REDIS_URL`, the production TLS terminator, `RELAY_PRIVATE_KEY`) is gitignored. Several findings — "defaults to in-memory", "no committed backups", "runs the hardcoded key" — describe the **code default and the committed README**, not a confirmed production state. If the live box already sets `RELAY_BACKEND=redis` with AOF/RDB and overrides the relay key, the Database/Cloud/Scaling/Availability grades improve materially. **Confirm the prod env out-of-band** before treating those as live defects.

**Scope notes.** Grades are calibrated to what a *pre-launch / TestFlight-stage decentralized app realistically needs* — not to a hyperscale-SaaS bar. "Decentralization N/A" credit is given only where a concern is structurally absent by design (central auth, session store, CDN for E2E ciphertext), never as an excuse for owed-but-missing relay operations.
