## 1. Problem statement and impact

Posts media has exactly **two** relay-upload code paths, and one of them is the **last unencrypted relay upload** in the app besides the doc-112 1:1 path:

- **Author-attach path (PLAINTEXT).** Composer (`posts_wired.dart:402-414, 467-487` `ComposePostSheet onSubmit` → `createLocalPost` → `_startBackgroundDelivery`; **note:** `PostsWired` is currently **test-only** — zero `lib/` imports outside its own file, the app shell mounts only feed/orbit tabs — so the live production author-attach entries are the `sendPost` callers and the retriers wired in `main.dart:2200-2219`; Caveat 9.7) → `prepareCreatedLocalPostMedia` → `attachPostMedia` → the default `uploadPostMedia` (`attach_post_media_use_case.dart:222-305`), which mints `blobId`/`mediaId` (`:235-236`) and calls `callP2PMediaUpload` with the **raw `localFilePath` and the real mime** (`:246-253`) — no `callBlobKeygen`/`callBlobEncrypt` anywhere in the file. `sendPost` (`send_post_use_case.dart:62-99`) and the restart retrier (`PendingPostMediaUploadRetrier`, `pending_post_media_upload_retrier.dart:154-245`, replay at `:208-222`) funnel into the same plaintext function (production wires no `uploadPostMediaFn` override — `attach_post_media_use_case.dart:92-126`).
- **Pass-along path (ALREADY ENCRYPTED).** `_prepareRepostMedia` (`pass_post_along_use_case.dart:525-648`) runs `callBlobKeygen` (`:578`) + `callBlobEncrypt` (`:580-584`), re-mints a blobId (`:587`), uploads the **ciphertext** (`:589-596`), and ships keys as a mediaId-keyed `media_keys` map inside the ML-KEM-encrypted inner payload, **fail-closed** per recipient (`post_delivery_runner.dart:552-592`; pre-abort at `pass_post_along_use_case.dart:225-242`). The receiver decrypt site is shipped: `downloadPostMedia` stages to `.enc` and calls `callBlobDecrypt` when `isEncrypted && key && nonce` (`download_post_media_use_case.dart:27-64`).

Blobs upload to the **author's own peer** with `allowedPeers` = author + all recipient delivery peers (group-mode ACL, `attach_post_media_use_case.dart:87-90, 110-113, 249-252`), live on the relay under a **7-day TTL** (`go-relay-server/media.go:21`), and are never deleted by posts code. Posts media is relay-only — no LAN path, no thumbnail blobs (`thumbnailBlobId` is a dead pass-through field, sole references `post_media_attachment_model.dart:20, 40, 62, 95, 118, 136, 173, 193`).

**Receive/persistence surfaces are THREE, not two.** Besides `post_create` (key join, Phase 1.3) and `post_pass` (shipped join), there is a production-wired third surface: **`post_pin_update` snapshot merge**. Pinning or editing a pinned post fans out a **v1-plaintext-only** envelope (`PostPinUpdateEnvelope.buildJson`, `post_pin_envelope.dart:208-241` — no v2 form exists) whose media snapshot is built from `toRenderableJson` (crypto-free, `post_media_attachment_model.dart:125-138`); senders `edit_pinned_post_use_case.dart:62-95` / `pin_post_use_case.dart` via `post_pin_delivery_support.dart:31-117`, with the rawEnvelope persisted and replayed verbatim by `PendingPostFollowOnRetrier` (`pending_post_follow_on_retrier.dart:141-152`). On receive, `handleIncomingPostPinUpdate` (`handle_incoming_post_pins_use_case.dart:94-109`) calls `_mergeSnapshotMedia` (`:235-258`), which rebuilds rows from the **keyless** snapshot carrying over only `localPath`/`downloadStatus`/`createdAt` (`:250-255`) and then `replacePostMediaAttachments` — i.e. today it would **WIPE joined key material from every recipient's rows** the moment the author pins their own encrypted-media post. Wired in production (`main.dart:1841-1846` `PostPinListener`); staged pins replay right after the parent post lands (`reconcile_pending_post_child_events_use_case.dart:77`). Phase 1.3 closes this before the flip.

**Impact:** every author-attached post photo, video, and voice clip sits **readable by the relay operator for up to 7 days**, advertised with its **real mime** (the pass path leaks the real mime too, `pass_post_along_use_case.dart:593-594`). Product requirement: **no plaintext posts media on the relay.**

## 2. Goals / Non-goals

### Goals
- **G1** Every author-attached post blob (image, video, voice, carousel cell — blob encryption is kind-agnostic, whole-file) is AES-256-GCM encrypted with a fresh random per-blob key before upload, from **both** author-attach entry points (composer/`sendPost`, and recovery-item replay via `PendingPostMediaUploadRetrier`).
- **G2** Blob key/nonce/scheme/contentHash travel **only inside ML-KEM v2 encrypted payloads**, via the pass-along mechanism reused verbatim: a `media_keys` map `{mediaId → {key_base64, nonce, blob_id, scheme, content_hash}}` added to `PostCreateEnvelope`, serialized **exclusively in `toInnerJson`** — structurally absent from the v1 plaintext `toJson` (Section 3).
- **G3** Delivery of a post **whose attachment rows carry key material** is **fail-closed per recipient** (mirror `_buildPostPassWireEnvelope`, `post_delivery_runner.dart:552-592`): the existing silent plaintext-v1 downgrade (`:516-521, 534-539`) never ships such a post. Text-only posts keep today's fallback. **Scoping precisely:** the gate keys on `mediaKeys` non-emptiness, so a media post created **pre-flip** (plaintext upload done, keyless legacy rows — migration 038 defaults) whose delivery is retried **post-flip** still ships v1 plaintext via today's path — correct compat behavior (the blob is already plaintext on the relay, TTL-bounded ≤7 days), explicitly pinned in P2.2 as an accepted legacy residual, NOT a gate bug.
- **G4** Receiver joins `media_keys` onto attachment rows (mirror `handle_incoming_passed_post_use_case.dart:166-174`) and `downloadPostMedia` is hardened fail-closed: `isEncrypted`-with-null-keys no longer marks `done` (`download_post_media_use_case.dart:43-80` hole), decrypt failure cleans the `.enc` staging file (`:81-87` leak), unknown scheme never decrypts with v1 logic.
- **G5** Legacy plaintext posts (old senders, in-flight relay blobs draining ≤7 days) keep working permanently; mixed-version behavior is explicit and tested (Section 4).
- **G6** Doc-112 convention parity: scheme `kMediaAttachmentEncryptionSchemeBlobAesGcmV1` written explicitly always; `contentHash` = SHA-256 of the **ENCRYPTED** blob, verified pre-decrypt against downloaded ciphertext, never compared to decrypted bytes (MIG-012). Requires migration 076 (posts columns lack scheme/hash — unlike 1:1's migrations 058/059).
- **G7a** Encrypted posts uploads advertise the **opaque transport mime** (`kOpaqueMediaTransportMime`, `application/octet-stream` — shared constant with doc 112 Phase 2.6; whichever doc lands first introduces it). Recon-verified safe: the posts receive path **never consumes the relay-returned mime** — `downloadPostMedia` derives the local path from `attachment.mime` and passes only id+outputPath (`download_post_media_use_case.dart:16-20, 30-34`); the only relay-mime consumer in the app is group-gated (`download_media_use_case.dart:1330-1371`, per doc 112). The DB/model mime stays REAL (render policy checks need it, `media_grid_cell.dart:75-95`). Phase 3 retrofits opaque mime onto the pass path too.
- **G8** Multi-recipient relay-blob lifecycle stays TTL-bound: posts **never** call `media:delete` — pinned by test. The 1:1 ack-delete pattern is explicitly forbidden for posts blobs (the working-tree relay's `handleMediaDelete` authorizes ANY `AllowedPeers` member to delete the shared blob for everyone, `go-relay-server/media.go:577-591` — recipient-1 would starve recipients 2..N).

### Non-goals (deferred, with justification)
- **Profile avatars** — doc 112 Non-goal, unchanged; separate doc (doc-112 OQ-5).
- **Local-at-rest encryption** — the sender's durable plaintext copy in `post_media/<postId>/<blobId>.<ext>` (`attach_post_media_use_case.dart:267-280`) and the receiver's decrypted final file stay plaintext; same posture as doc 112. Per-blob keys/nonces stored plaintext in SQLCipher rows (`post_media_attachments`, migration 038) — same posture as the shipped pass path and doc-112's columns; the account-migration bundle carries these rows. **Transient plaintext temps are IN scope (doc-112 parity — its Phases 2.1/2.3/2.6 treat source temps as the same residue class):** `_prepareDraft` (`attach_post_media_use_case.dart:343-385`) writes a processed plaintext temp (`processImage`/`processVideo`) that is uploaded and never deleted, and the draft source (picker/camera/recorder temp) also persists. The processed temp is deleted post-upload (Phase 2.1/2.5, guarded `processedPath != source` — voice passes through unchanged); the draft source **cannot** be deleted before upload success because recovery replay re-reads it (`pending_post_media_upload_retrier.dart:208-222`, missing source fails the post permanently `:305-334`) — it is best-effort deleted only after recovery items are cleared (`attach_post_media_use_case.dart:215`). No relay exposure either way — local-at-rest only.
- **Cross-path key repair** — an encrypted pass arriving AFTER a key-less `post_create` never repairs the existing rows (`handle_incoming_passed_post_use_case.dart:134-159` early-returns without re-storing media; the reverse order is safe, `handle_incoming_post_use_case.dart:255-264` preserves keyed rows by mediaId). Repair would require swapping blobId+key+nonce together and re-hydrating — deferred, current behavior pinned by ordering tests (Phase 1.3); OQ-4.
- **Download retry / failure-state UX** — posts media downloads exactly once at receive-time hydration (`main.dart:1784-1802, 1823-1840` wire `hydratePostMediaFn` → `downloadPostMedia`; `post_card.dart:591` wires no retry). Encryption adds decrypt-failure surface to a permanent-`failed` model; fail-closed is still correct (vs today's silent garbage), but a retry story is a follow-up (OQ-6).
- **Streaming/chunked blob crypto** — Go `EncryptFile`/`DecryptFile` are whole-file-in-RAM (`go-mknoon/crypto/file_crypto.go:35, 83`); groups and pass-along already accept this. Stated limitation.
- **Relay-side changes** — none needed here. Doc-112 Phase 6 (sidecar `from` removal, G7b) covers posts blobs automatically — same `mediaMeta` sidecar (`media.go:33-41, 482-490`); no posts-specific relay work.
- **Pin-envelope metadata residual (accepted)** — `post_pin_update` envelopes are **v1-plaintext-only by design** (`post_pin_envelope.dart:208-241`) and ship the renderable media snapshot (`blob_id`, **real mime**, `size_bytes`, `waveform` — `post_media_attachment_model.dart:125-138`) for the same encrypted blobs, stored in relay inboxes for offline recipients and replayed by `PendingPostFollowOnRetrier`. Post-flip, a relay operator therefore still learns the blobId→real-mime/size mapping of every **pinned** encrypted post from cleartext pin envelopes — a metadata-only residual (no key material: renderable JSON is crypto-free, verified) that partially undercuts G7a's opaque-mime gain for pinned posts. Encrypting pin fan-out per-recipient (v2) is a separate workstream (OQ-10); §8 #2 inspects pin envelopes to confirm this residual is expected, not a regression.

## 3. Design decision

**Reuse the shipped pass-along key-distribution mechanism verbatim for the author-attach path.** Encryption moves **inside the default `uploadPostMedia`** (`attach_post_media_use_case.dart:222-305`), mirroring `_prepareRepostMedia` inline: `callBlobKeygen` → `callBlobEncrypt` → SHA-256 over the **encrypted** artifact → `callP2PMediaUpload(filePath: encryptedPath, mime: kOpaqueMediaTransportMime, toPeerId/allowedPeers unchanged)` → finally-delete the `.enc` temp (mirror `pass_post_along_use_case.dart:631-640`) → return the attachment with `encryptionKeyBase64`/`encryptionNonce`/`encryptionScheme`/`contentHash`/`isEncrypted: true`. The `UploadPostMediaFn` typedef (`attach_post_media_use_case.dart:31-42`) is **unchanged** — its inputs (raw path, real mime) stay as-is; the new fields ride the returned `PostMediaAttachmentModel`. The durable plaintext local copy (`:267-280`) is untouched and remains the sender's render source.

**Key carriage:** `PostCreateEnvelope` gains a `mediaKeys` field structurally identical to `PostPassEnvelope.mediaKeys` (`post_pass_envelope.dart:38-68, 88, 218-230, 445-449`) — a `media_keys` payload map keyed by **mediaId** (NOT blobId; pass precedent, join at `handle_incoming_passed_post_use_case.dart:166-174`), with `PostMediaCryptoEntry` extended by optional `scheme` + `content_hash` (old receivers ignore unknown entry fields — `PostMediaCryptoEntry.fromJson` reads only `key_base64`/`nonce`/`blob_id`, recon-verified). Crucially, and **better than the pass path**: `media_keys` is serialized **only in `toInnerJson`** (the ML-KEM v2 inner payload, `post_create_envelope.dart:312-314` region) and **never in the v1 plaintext `toJson`** (`:263-265`) — so even a future regression in the fail-closed gate cannot leak keys in cleartext (the pass path's `_buildPayloadJson` puts `media_keys` in v1 too, `post_pass_envelope.dart:369-378`, and relies solely on fail-closed sending). **The same v2-only rule holds on RECEIVE:** `fromEncryptedJson` decrypts the v2 inner payload and re-wraps it through the shared `fromJson` parser (`post_create_envelope.dart:231-240`), so naively adding `media_keys` to `fromJson` would also accept keys arriving in a v1 **plaintext** `post_create`. Instead, `fromJson` never parses `media_keys`; `fromEncryptedJson` extracts `media_keys` from the decrypted inner payload itself and attaches it to the parsed envelope — a v1 plaintext envelope carrying `media_keys` parses with `mediaKeys == null` (decision pinned in P1.2; a sender shipping keys in v1 has already leaked them, but the receiver must not legitimize the path). The media snapshot continues to ride `toRenderableJson`, which omits all crypto fields (`post_media_attachment_model.dart:125-138`) — keys travel only via `media_keys`, joined back by mediaId on receive.

**Fail-closed sending:** `_buildWireEnvelope` (`post_delivery_runner.dart:508-550`) currently downgrades to plaintext v1 when `bridge == null`, `recipient.mlKemPublicKey == null`, or `callEncryptMessage` fails (`:516-521, 534-539`), and recipient eligibility never filters on ML-KEM keys (`send_post_use_case.dart:379-432`) — so the plaintext path is **live in production**. When the envelope carries media (mediaKeys non-empty), the build becomes fail-closed per recipient: throw `_RecipientDeliveryBuildException` with reason codes mirroring the pass path (`post_media_encryption_unavailable` / `post_recipient_missing_mlkem_key` / `post_media_encrypt_failed`), recorded as per-recipient `failed` delivery (`:417-431` precedent). This plan chooses **per-recipient fail** (not the pass path's whole-post pre-abort at `pass_post_along_use_case.dart:225-242`) so capable recipients still receive the post — owner confirmation in OQ-1.

**One blob key shared by all N recipients** (per-recipient confidentiality comes from the ML-KEM outer envelope) — matches the shipped pass and group precedent; stated explicitly.

### Alternatives rejected
1. **Encrypt in `attachPostMedia` before the `uploadPostMediaFn` seam** — would change the typedef contract consumed simultaneously by `posts_wired`, `send_post_use_case`, and the retrier (recon sender-paths risk), and would put ciphertext paths into recovery items. Encrypting inside the default impl keeps recovery items plaintext-source-only (KC-P2's re-encrypt-from-source design) and zero seam churn. Consequence honestly stated: all existing typedef-stubbed tests stay green — so Phase 2 mandates new tests through the REAL `uploadPostMedia` (doc-112 §3.1/R6 precedent), and the existing seam-input pins (`attach_post_media_use_case_test.dart:112-119`) remain **valid**, not stale (they pin seam inputs, which genuinely don't change).
2. **Carry key/nonce inside the media snapshot (`toRenderableJson`)** — the snapshot rides BOTH v1 and v2 envelopes; with the live v1 fallback this ships blob keys in cleartext through the relay inbox — worse than today's plaintext blob. Also breaks the established pass-path convention of crypto-free renderable JSON.
3. **A separate follow-on key message** — would break ordering against the durable staged inbox drain (`p2p_service_impl.dart:856-937`); the per-recipient final wire envelope IS what sits in the relay inbox, so in-payload `media_keys` works for offline recipients with zero relay changes (recon key-distribution fact).
4. **Whole-post pre-abort when any recipient lacks an ML-KEM key** (pass precedent, `pass_post_along_use_case.dart:225-242`) — stricter than necessary for a broadcast surface; per-recipient fail keeps the post flowing to capable recipients. Flagged for owner sign-off (OQ-1).
5. **Reuse the 1:1 `uploadMedia`/ack-delete machinery** — posts blobs are multi-recipient group-mode; ack-delete is a starvation foot-gun (G8) and `uploadMedia`'s 1:1 durability behaviors (ack, `.part` adoption) don't apply to the posts one-shot hydration model.
6. **Skip the scheme/contentHash columns and keep the bare `is_encrypted` bool** — would fork the posts crypto contract from doc 112 permanently and make discriminator case 3 (unknown future scheme) inexpressible: bare key-presence routing would mis-decrypt future-scheme ciphertext with v1 logic. Migration 076 is cheap; old pass rows tolerate null scheme on receive (doc-112 discriminator case 2 analog).
7. **New scheme string for posts** — identical cipher mechanics (`blob:keygen`/`blob:encrypt`/`blob:decrypt`, `bridge.dart:687-773` → `go-mknoon/crypto/file_crypto.go`); a new string adds compat rows for zero crypto benefit (doc-112 Alternatives #1).

### Key-coherence contracts (must be pinned by tests)
- **KC-P1 (ordering):** media prep — encrypt + upload complete, attachment rows carrying final key/nonce/scheme/hash — finishes **before** `PostDeliveryRunner.execute` builds wire envelopes. Already structurally true: `sendPost` runs prepare-then-deliver (`send_post_use_case.dart:82-99`); the delivery retrier skips posts whose media upload hasn't completed (`pending_post_delivery_retrier.dart:205-212`). Pin it (green-on-arrival).
- **KC-P2 (retry):** every upload attempt mints a **fresh blobId+key+nonce** inside `uploadPostMedia`; recovery items carry NO key material by design (`post_media_upload_recovery_item.dart:3-26` — plaintext source path only; re-encrypt-from-source on replay); envelopes are always derived from current DB rows after prep, so **no stale-key envelope is constructible** (recon compat-skew: no KC-2 hazard by construction, unlike doc-112's 1:1 persisted-envelope replay). Residual accepted: a retry after a partially-recorded success orphans the prior (possibly plaintext, during rollout) blob on the relay with no delete — TTL-bounded (7 days), pinned and documented (`attach_post_media_use_case.dart:235, 156, 215`; `pending_post_media_upload_retrier.dart:208-241`).
- **KC-P3 (key confidentiality in transit):** `media_keys` exists ONLY inside ML-KEM v2 inner payloads — structurally absent from v1 `toJson` AND fail-closed sending for media posts (belt and braces; either alone is insufficient — structural omission without fail-close would still ship keyless ciphertext that old receivers render as garbage). **Receive side:** keys are parsed only from the v2 decrypt path (`fromEncryptedJson`), never from v1 plaintext `fromJson` (Section 3, P1.2 pin). **Persistence side:** joined keys must survive every later write to the rows — specifically the pin-update snapshot merge (`_mergeSnapshotMedia` preserves crypto fields, P1.3) — or the 'joined back by mediaId' invariant is void.
- **KC-P4 (custody, no-delete):** `downloadPostMedia` never issues `media:delete` — first downloader must not starve recipients 2..N (G8; mirror of the conversation guard precedent `download_media_use_case.dart:577-591` "Group blobs are never acked"). Inverse of doc-112's KC-3: instead of ack-after-commit, **never-ack**.

## 4. Backward / version-skew compatibility

**The two-release receiver-first hold IS required for the author-attach flip** — the recon settled this, for one precise reason: the decrypt machinery is shipped (`downloadPostMedia` + `callBlobDecrypt`, committed in 468fc6e9/2eb3aa9d, contained in main and Test-Flight-1) **but only the `post_pass` envelope carries keys**. `PostCreateEnvelope` has NO `media_keys` field (`post_create_envelope.dart:11-28`), its parser builds every attachment with `isEncrypted=false`/null keys (`:147-155` via `fromRenderableJson` defaults, `post_media_attachment_model.dart:69-100`), and `handleIncomingPost._storeIncomingMedia` performs no key join (`handle_incoming_post_use_case.dart:246-271`).

**Old app ← new sender (the dangerous direction):** an old receiver parses the encrypted post fine (unknown payload fields silently ignored), persists attachments with `isEncrypted=false`, downloads the raw **ciphertext to the FINAL path** (plaintext branch, `download_post_media_use_case.dart:27-29, 43-45`), marks `done` (`:66-80`), and renders garbage — silent corruption, no error, no retry signal, and dedup blocks healing (`handle_incoming_post_use_case.dart:260-270` preserve-existing skips re-delivered copies). **Mitigation: Release N (Phase 1) ships the full receiver capability — envelope `media_keys` parse + `_storeIncomingMedia` join + download hardening; the sender flip (Phase 2) is held until the Phase-1 build is the deployed floor.** The pass-along path needs **no hold** (encrypt + decrypt shipped bidirectionally); Phase 3 is hold-independent.

**New app ← old sender / in-flight plaintext blobs:** per-attachment branching keeps key-less attachments on the plaintext path permanently (`download_post_media_use_case.dart:43-45`; pass join sets `isEncrypted: cryptoEntry != null ? true : null`, `handle_incoming_passed_post_use_case.dart:166-174`). The plaintext receive branch is permanent compatibility surface, not deprecatable (old-build senders persist indefinitely) — pinned.

**Pin-update merge (third receive surface, post-flip hazard):** without Phase 1.3's fix, the author pinning their own encrypted-media post — mainline flow, any time in the post's life — strips Phase-1.3-joined keys from every recipient's rows (`_mergeSnapshotMedia` carries over only `localPath`/`downloadStatus`/`createdAt`, `handle_incoming_post_pins_use_case.dart:250-255`, then `replacePostMediaAttachments` `:109`). A recipient whose one-shot hydration hadn't completed (pending/failed — no retry, Non-goal) is left with key-less rows pointing at encrypted blobs, which discriminator case 1 routes to the legacy-plaintext path: ciphertext lands at the final path, `done`, garbage — the exact silent-corruption class this plan exists to prevent, on NEW builds, immune to every Phase-1.4 gate (those key on key material that is now gone). Even for downloaded rows, stored crypto metadata would be permanently lost (breaks Non-goal-2 account-migration row carriage and KC-P3's join invariant). Fix: the merge preserves existing crypto fields by mediaId (P1.3). **Ordering note:** staged pins replay immediately after the parent post lands (`reconcile_pending_post_child_events_use_case.dart:77`), so post_create-with-keys → staged-pin-replay is a same-tick sequence — pinned alongside the pass/create ordering pins in 1.3.

**v1 plaintext `post_create` carrying `media_keys`:** parsed with `mediaKeys == null` — keys join only from the v2 decrypt path (Section 3 decision, P1.2 pin). Old receivers are unaffected either way (no `media_keys` parsing exists).

**Discriminator (posts tri-state, per attachment):**
1. no key material (key or nonce absent) → **legacy plaintext** path, regardless of the `isEncrypted` bool — this closes today's `isEncrypted`-true/null-keys `done`-without-file hole by failing closed instead (`failed`, Phase 1.4);
2. key+nonce present AND scheme ∈ {null, `blob_aes_256_gcm_v1`} → **decrypt** (null tolerated on receive only — shipped pass rows and old pass senders never write a scheme; the new sender always writes it explicitly);
3. key+nonce present AND scheme outside the whitelist → **fail closed**: status `failed`, staged `.enc` removed (posts have no adoption/retry model to preserve artifacts for — unlike doc-112 case 3), **no relay delete** (KC-P4 — the blob stays for other recipients and within TTL).

**Size semantics:** `sizeBytes` stays the **plaintext** size on wire/DB (group + pass convention). Ciphertext = plaintext + 16-byte GCM tag. No size validation exists anywhere in posts receive (recon) — do not add one that confuses the two; the relay's exact-size enforcement uses the actual uploaded file (Go stats it).

**MIG-012:** `contentHash` is ALWAYS the hash of the ENCRYPTED blob, verified pre-decrypt against downloaded ciphertext bytes. Posts have zero hash plumbing today and NO `group_feed_media_verification.dart`-class deleter touches posts surfaces (recon model-storage: it is imported only by group-feed files) — doc 113 introduces hash verification fresh and must never add a decrypted-bytes comparison.

**G7a skew: zero rows.** Posts receive never reads the relay-returned mime (`download_post_media_use_case.dart:16-20, 30-34`); old receivers are unaffected by opaque-mime uploads even before Release N. The DB/model/envelope mime stays real (render policy, `media_grid_cell.dart:75-95`; extension derivation, `media_file_manager.dart:46-67`).

## 5. TDD phases

Order: **1 → 2 → 3 → 4**; Phase 1 must be the deployed receiver floor before Phase 2 ships (Section 4). Phase 3 is hold-independent (receiver-compatible). New test files go in `test/features/posts/improvement/` (implicit direct-suite bucket — zero gate edits, `test-gate-definitions.md:354-361, 684-689`) except the migration test (sibling pattern `test/core/database/migrations/`); `./scripts/run_test_gates.sh completeness-check` kept green throughout. RED honesty rule: green-on-arrival tests are explicitly labeled **pins**.

**Shared test infrastructure decision (deliberate deviation from doc-112's in-file-stub convention, justified):** extract `_EncryptedMediaBridge` (XOR-transforming `blob:keygen`/`blob:encrypt`/`blob:decrypt`) + `_RelayMediaStore` (captures `uploadedBytesByBlobId`/`allowedPeersByBlobId`/`mimeByBlobId`) from `test/features/posts/improvement/post_pass_encrypted_media_integration_test.dart:281-397` into `test/shared/fakes/encrypted_media_test_bridge.dart`, refactoring that file to consume it. **The extraction is NOT byte-identical — two deliberate fixes, because the in-file original is key-blind:** the source stub uses a STATIC `_fixedKey`/`_fixedNonce` (`:282-287`), returns the same key from every `blob:keygen` (`:302-307`), and `blob:encrypt` XORs with the static key while IGNORING the payload `keyBase64` (`:308-317`). Against that, this plan's distinct-key (P2.1) and fresh-key-on-retry (P2.3, KC-P2) assertions are unimplementable. The extracted fake must **(a)** mint a distinct random key per `blob:keygen` call and **(b)** XOR using the payload-provided `keyBase64`/`nonce` in `blob:encrypt`/`blob:decrypt`. 'Behavior-identical' applies to the refactored **consumer file's assertions** (they don't depend on key identity — they stay green by construction; if any does, expose an optional fixed-key mode for that file only), not to keygen determinism. Four-plus suites need the shared stub (attach encryption, download hardening, recovery replay, round trips, **and the Phase-3.1 pass-parity scheme/content_hash cases** — see 3.1) — in-file duplication would fork the one stub whose content-transformation property the whole plan depends on. ## 7. Risks and open questions

### Risks (actively mitigated; verify per phase)

- **R4** Content-blind AND key-blind stubs: shared `FakeBridge` `blob:encrypt` copies bytes unchanged (`fake_bridge.dart:196-232`; `PassthroughCryptoBridge` inherits it, `:324-369`), and the in-file `_EncryptedMediaBridge` uses a static fixed key + ignores the payload `keyBase64` (`post_pass_encrypted_media_integration_test.dart:282-317`) → mandated `encrypted_media_test_bridge.dart` extraction WITH the two key-fidelity fixes (per-keygen distinct keys, payload-key XOR — Phase 5 preamble); the refactored consumer file's own assertions are the behavior check (they don't depend on key identity).

## 9. Verified caveats

### 9.1 A DB migration IS needed (unlike doc 112)
`post_media_attachments` has `encryption_key_base64`/`encryption_nonce`/`is_encrypted` (migration 038) but NO `encryption_scheme`/`content_hash` (1:1 got them in 058/059). Migration 076 is the next free slot (verified: head is `075_contacts_ml_kem_key_updated_ts.dart`, `currentIdentityDatabaseVersion = 75`) — re-verify the slot before authoring; the 111 P0 work also added migrations on this branch.

### 9.2 No relay or Go-library change required
The relay is content-agnostic for blob bytes; posts blobs are group-mode (AllowedPeers) and TTL-bound. The single relevant relay change (sidecar `from` removal) belongs to doc-112 Phase 6 and covers posts automatically. Blob bridge commands (`blob:keygen`/`blob:encrypt`/`blob:decrypt`, `bridge.dart:687-773`; Go handlers `go-mknoon/bridge/bridge.go:2801-2808`, `file_crypto.go:26-109`) ship on both platforms — zero go-mknoon edits, zero `make all` reruns for this plan.

### 9.3 `implements`-based fakes / constructor churn
`UploadPostMediaFn` typedef unchanged (Alternatives #1). `PostCreateEnvelope` gains an optional `mediaKeys` constructor param — update every construction site and test fixture in the same step (the implements-no-default-bodies memory applies to interfaces; envelope is a concrete class, so this is constructor-call churn only). `PostMediaCryptoEntry` field additions are optional/tolerant both directions.

### 9.4 Routing predicate: key-material presence, never the bool alone
Posts' `isEncrypted` is a stored bool, not a derived whitelist like 1:1's `hasEncryptionMetadata` — and the shipped `isEncrypted`-true/null-keys hole (`download_post_media_use_case.dart:43-80`) is exactly what bool-only routing produces. Custody routes on key+nonce presence; decrypt additionally gates on scheme ∈ {null, v1}; unknown scheme fails closed without decrypt and without delete (Section 4 discriminator). Do not ship Phase 2 without the 1.4 pins.

### 9.5 Line-number re-check
All file:line anchors verified 2026-06-12 against the UNCOMMITTED 121-improvements tree. Re-verify before each session; re-run the recon if the tree shifts materially (the 111 P0, move-scale, and NET-REL work all touch adjacent files).

### 9.6 Recon conflict resolved: KC-2 analog
sender-paths flagged a "KC-2 hazard" for retries; compat-skew found "no KC-2 stale-key hazard by construction". Both are correct on inspection: there is **no stale-key/envelope mismatch** (envelopes built only after prep, from current rows — the doc-112 KC-2 failure mode is structurally absent), but retries DO orphan superseded relay blobs (fresh blobId per attempt, no delete). The plan treats the former as a green pin (KC-P1/P2) and the latter as an accepted TTL-bounded residual (R8).

### 9.7 `PostsWired` is test-only (production-entry inventory)
`posts_wired.dart` has zero `lib/` importers outside its own file (verified 2026-06-12; the app shell mounts only feed/orbit tabs, `app_shell_tab.dart:1-8`) — the whole posts presentation chain (`posts_wired.dart` → `posts_screen.dart` → `post_card.dart`) is exercised only by tests. The live production author-attach entries are the `sendPost` callers and the retriers (`main.dart:2200-2219`, which pass no `uploadPostMediaFn` override — verified). This creates no plaintext hole (Phase 2 encrypts inside the default `uploadPostMedia`, covering every caller), but the wiring assumption is otherwise unguarded: `posts_wired.dart:476` forwards `widget.uploadPostMediaFn`, so a future mount WITH an override would silently bypass the flip for the composer — see the Phase-2.5 mount guard.

Same disciplines as doc 112 §9.6, restated because implementation sessions for this plan will fan out the same way: (1) anchor `graphify query` on 1–2 exact symbol names (`attachPostMedia`, `_storeIncomingMedia`), never prose — empty results mean re-anchor, not "the code doesn't exist"; (2) refresh after every edit batch via `./graphify-arch/refresh_arch_graph.sh` from the repo root (NEVER graphify build/update with cwd inside `graphify-arch/`) plus `graphify update .` for the full graph — Caveat 9.5's per-session anchor re-verification only works against a current graph, and each phase shifts the next phase's line numbers.
