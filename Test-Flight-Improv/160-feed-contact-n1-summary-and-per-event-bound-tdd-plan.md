> 1. > 2. Card **VISIBILITY** depends on the full list: `feed_pending_projection.dart:55-65` — `answeredSince = item.messages.any(outgoing after newestIncoming)`. A cap dropping the answering outgoing **flips cards in/out of the inbox**.
> 3. `unreadCount` is **re-derived from the list** (`_buildThreadFeedItem:909` / `groupMessagesIntoThreads:43`), so a cap **undercounts** >K-unread threads. `summary.unreadCount` is the correct source, never wired.

## Exact Problem Statement
On every feed mount, `loadContactFeedItems` (`load_feed_use_case.dart:35-38`) loops `messageRepo.getMessagesForContact(peerId)` once per active contact with **no LIMIT** — `dbLoadMessagesForContact` (`messages_db_helpers.dart`) SQLCipher-decrypts the *entire* per-contact history, then `ConversationMessage.fromMap` runs over every row on the root isolate (`message_repository_impl.dart:153`). A second amplifier follows: `_loadReactionsForFeed` (`feed_wired.dart:1383-1395`) requests reactions for `_feedStore.contactMessageIds`, which `expand`s **every** message of **every** thread (`feed_store.dart:104-107`). So feed-mount cost grows linearly with total history depth × contact count — a startup/mount spike that stutters the first frame for any user with deep 1:1 histories. The cheaper batched alternative `getConversationThreadSummaries` (`message_repository_impl.dart:455` → single `GROUP BY` `dbLoadConversationThreadSummaries`) **already exists and is used by orbit** (`load_orbit_data_use_case.dart:191`, via a `is ConversationThreadSummaryRepository` cast), but the feed never calls it (`db-persistence-1`).

Separately, **every** feed-level event re-reads the full history through one funnel. Send-from-feed success (`feed_wired.dart:1800`) calls `_refreshContactFeedItem` → `loadContactFeedSnapshot` (`load_contact_feed_snapshot_use_case.dart:28`) → `loadConversation` → `getMessagesForContact` (unbounded), **discarding the `optimisticMessage` it already holds** (`feed_wired.dart:1765`). Delete/hide repo-change (`feed_wired.dart:1241-1248`) and both nav-return paths (`:1342`, `:1379`) hit the same unbounded snapshot. The bounded sibling `loadConversationPage` / `getMessagesPage` / `dbLoadMessagesPage` (commit `dc4731c6`, `DESC`+limit+cursor) already exists and powers the 1:1 conversation screen, but the feed snapshot was never migrated to it (`db-persistence-3`).

What must improve: feed-mount work scales **sub-linearly** with per-contact history depth (preview from a batched summary, not N unbounded decrypts); the full thread is fetched **lazily on focus**; send-success **merges in memory** (no DB read); delete/hide/nav-return reload through a **bounded, newest-first paged** snapshot.

What must stay unchanged (→ preserved-green sentinels): 134/135 feed "Letters" preview semantics (`hasReply`, multi-message preview, `unreadCount`, `ConversationState`, `hasEarlierHistory`/`hasEarlierInteractionHistory`, swipe-dismiss, `feedClearedRepository`); 134 REG-INV3 read-on-send deferral (`feed_wired.dart:1796-1799`); reaction-prune correctness (do NOT wrongly clear off-page ids); `_syncComposerStateForContact`; the unread-count source (`getTotalUnreadCountExcludingArchived`, kept separate); 131/141/145/146/147 notif-drain (a just-drained message stays visible as `latestMessage` — cap **newest-first**); the incoming/repo-change merge **routing** (status flips still route to the in-memory merge, NOT a reload — the merge BODY changes per corrected A5: count carry-forward + off-window-flip guard).
