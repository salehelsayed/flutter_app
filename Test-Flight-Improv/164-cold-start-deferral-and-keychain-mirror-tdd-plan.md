## Exact Problem Statement
On a normal (non-share) cold launch, the main isolate blocks before the first frame on serialized pre-`runApp` work that the app's own `deferredRuntimeStartup` machinery already proves is safely deferrable:

1. **`cold-start-1` / `main-isolate-blocking-2`** — `main.dart:390-391` `await ensureFirebaseReady()` (Firebase.initializeApp + `onBackgroundMessage` registration `:366` + `setForegroundNotificationPresentationOptions` MethodChannel `:369` + iOS recent-remote gate `:384`) AND `main.dart:3095-3096` `await startLiveServices()` (re-awaits Firebase `:3041`, `bridge.initialize` `:3042`, `notificationService.initialize` MethodChannel `:3044`, then ~25 listener `.start()` calls) both run before `runApp` at `:3105`. `deferredRuntimeStartup` at `:3186` is `isShareLaunch ? startLiveServices : null` — the deferral is wired and battle-tested for share-launch but deliberately NOT used on normal launch, so `_ensureRuntimeServicesReady` (`:3564`) short-circuits to `Future.value()` for normal launch (`deferredRuntimeStartup == null` at `:3571`) and all that work stays on the critical path.
2. **`cold-start-3`** — `main.dart:1312` `await groupRepository.mirrorAllKeysToSecureStore()` + `:1315` `await groupRepository.mirrorAllMutedGroups()` are top-level pre-`runApp` awaits that re-write **every** group key (`N` groups × `G` generations) and **every** mute projection to the iOS shared Keychain **on every launch**, with no idempotence guard (`_mirrorGroupKeyForPush:668` writes unconditionally; `_mirrorGroupMutedForPush:695/:697` writes/deletes unconditionally). Serial `pushSharedKeyStore.write` per key/mute is unbounded work in the splash critical path that grows with the user's group history.
3. **`cold-start-5`** — the share-intent probe (`main.dart:350`, `await shareIntentService.captureInitialIntent()`) and `getApplicationDocumentsDirectory()` (`:395`) run **serially**; they are independent and could overlap (`Future.wait`).

Who experiences it: every user on every cold start (heavier for users with many groups/key-generations). Why it matters: tens of ms of avoidable splash latency (audit honestly down-scopes the magnitude) plus an unbounded keychain-write blast that scales with group count.

What must improve: normal launch defers `startLiveServices` + Firebase off the pre-`runApp` critical path; the keychain mirror does ZERO redundant writes when the projection is already present (presence-diff) and its bulk backfill runs off the critical path while remaining guaranteed-to-run; the two independent launch probes overlap.

What must stay unchanged (→ preserved-green sentinels): cold LOCAL-notif tap still routes (`:3787` already awaits `_ensureRuntimeServicesReady` before `_handleInitialLocalNotificationLaunch:3788`→`consumeInitialPayload:3794`); cold FCM tap still routes (`startup_router.dart:738`/`getInitialMessage:757`, gated behind `_doStartP2P`'s `:629` await); foreground push still received (`_setupPushListeners` `onMessage:4435`); **FCM push-token registration still wired** (`pushRegistrationCoordinator.ensureStarted()` at `startup_router.dart:662`, fed by the non-null coordinator built at `main.dart:2289` — this is the path a fresh install / token-rotation depends on; see the SECOND regression in Root Cause); the deferred-startup TRIGGER on every launch (`initState` `:3561 unawaited(_handleInitialLocalNotificationLaunchWhenReady())`); **141** drain start-awareness (`_doStartP2P` `:629`→`rejoinGroupTopics:674`/`drainGroupOfflineInbox:693`); **145/146/147** notif-tap inbox-drain (non-blocking route, "catching up" banner, `NOTIFICATION_TAP_TO_LIVE_MESSAGE_TIMING` milestone, receipt deferral, decrypt fan-out — all live behind the same `_ensureRuntimeServicesReady`/`_doStartP2P` chokepoint, NOT moved); **134/135** feed contact-listener forwarders (`startLiveServices:3083`/`:3089`); **127/128** media-unavailable render boundary (`MediaFileManager.cacheDocumentsDir` seed at `:401` + `MEDIA_RENDER_RESOLVER_SEEDED:405` stay on the docs-dir path); **156** reduce-motion + DB indices (untouched; DB floor stays v94); eventual mirror completeness (iOS NSE group-preview decrypt + mute-honoring depend on every key/mute eventually present).

Confirmed on HEAD; `startLiveServices` internally re-awaits `ensureFirebaseReady` at `:3041`.
- **cold-start-1 LOAD-BEARING REGRESSION #1 — push LISTENERS (the kill that surfaced a real hazard):** `_setupPushListeners()` is invoked SYNCHRONOUSLY in `MyApp.initState` at `main.dart:3553` and early-returns on `if (widget.isDesktop || Firebase.apps.isEmpty) return;` (`:4432`). Today Firebase is ready pre-`runApp` (`:391`), so `Firebase.apps` is non-empty at `:3553` and `onMessage` (`:4435`)/`onMessageOpenedApp` (`:4447`) register. Deferring Firebase past `initState` makes `Firebase.apps` **empty** at `:3553` → `_setupPushListeners` no-ops → **silent loss of foreground push (`onMessage`) + push-tap routing (`onMessageOpenedApp`)**. The fix is NOT a pure deletion: it MUST re-arm `_setupPushListeners` (or an equivalent registration call) AFTER `_ensureRuntimeServicesReady` completes, and the re-arm MUST be idempotent (unconditional `_pushListenersArmed` latch) so the `initState` call + the re-arm call cannot double-register (`onMessage.listen` twice → duplicate foreground-push handling + duplicate routes).
- **cold-start-1 LOAD-BEARING REGRESSION #2 — push-TOKEN REGISTRATION (re-review confirmed, was MISSED; SAME class, DIFFERENT site):** `pushRegistrationCoordinator` is constructed at `main.dart:2289-2301` gated on `!isDesktop && Firebase.apps.isNotEmpty && !kE2ETestMode` (`:2290`). `:2290` executes AFTER the eager `ensureFirebaseReady()` at `:391` today (so non-null on normal launch) but BEFORE the deferred startup post-fix → `Firebase.apps` is **empty** at `:2290` → the ternary takes `: null` (`:2301`) → coordinator is `null` for the entire session. Its sole startup consumer `startup_router.dart:660-663` is null-guarded (`if (pushRegistrationCoordinator != null) { unawaited(pushRegistrationCoordinator.ensureStarted()); }`, correctly sequenced AFTER `await ensureRuntimeServicesReady():629`), so a null coordinator silently no-ops: no `onTokenRefresh` subscription (`push_registration_coordinator.dart:41`), no startup `registerPushToken()` (`:53`→`:135`). `register_push_token_use_case.dart:83 getToken()` is the ONLY fresh-FCM-token acquisition and is reachable ONLY via the coordinator; `p2p_service_impl.dart:3744 _reregisterStoredPushTokenIfAvailable` re-registers a *previously stored* token but NEVER `getToken()`s → the bug is **MASKED for upgraders** (stored token re-registers, so push appears to work) **but DEAD for fresh installs and FCM token-rotations** — exactly the "works for me, broken for new users" trap. - **cold-start-3:** `mirrorAllKeysToSecureStore` (`group_repository_impl.dart:537-557`) loops all groups × all key rows and calls `_mirrorGroupKeyForPush` (`:658`) which unconditionally `store.write(...)` (`:668`) — no presence check (only an `isSecureStoreReference` early-return at `:663`). `mirrorAllMutedGroups` (`:562-576`) loops all groups and calls `_mirrorGroupMutedForPush` (`:687`) which unconditionally writes (`:695`) / deletes (`:697`).   - **KEY vs MUTE diff-mode asymmetry (the correctness rationale):** the KEY mirror may use a pure `containsKey` PRESENCE-diff because a `(groupId, keyGeneration)` → `encryptedKey` mapping is **immutable** — the keychain name `sharedGroupPushKeyName(groupId, keyGeneration)` embeds the generation, and a key rotation mints a NEW generation (new name, `containsKey` false → writes), so a present name always holds the correct ciphertext and skipping is safe. The MUTE mirror must NOT use presence-diff: mute is a TOGGLING boolean under one stable name `sharedGroupMutedKeyName(groupId)`, so the fix uses a VALUE-diff (`read(name) == '1'` to skip a redundant write; `containsKey(name)` false to skip a redundant delete). TC-164-04 leg-3 (new generation → exactly one write) locks "presence-diff still admits new keys"; TC-164-05's change leg locks "value-diff still flips on a real mute transition."
