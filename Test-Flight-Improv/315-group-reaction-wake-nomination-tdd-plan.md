## Problem And Evidence

- **Behavior to improve:** a group member who reacts to another member's message can produce a reaction that never wakes the author's phone — no push, no banner until the author next opens the app — and every decline on the wake path is silent at every layer, so the loss is undiagnosable without redis forensics.
- **Impact:** reactions are the least reliable notification kind in the app. On 2026-07-31, an active multi-phone test day, the relay sent **zero** reaction pushes (current-process counters: 3 successes, all group messages) and the journal contains **zero** reaction-attributed lines — including for pushes that would have succeeded (see F4).

### Confirmed root causes (survived the refute pass and the review)

**F1 — An author missing from the reactor's roster loses the reaction ENTIRELY, silently and permanently.**
`sendGroupReaction` validates only the *sender's* membership (`send_group_reaction_use_case.dart:98`); it never checks that `message.senderPeerId` (the target author, `:209`) resolves to a roster row. The nomination loop requires an exact roster match (`:421 if (member.peerId != targetAuthorPeerId) continue;`). If the reactor rendered the author's message before the author's `member_added`/config snapshot landed locally, the nomination is `[]` while the replay set (built from the *other* members, `:405-414`) stays non-empty — so custody **stores without the author**, and the consequence is worse than a missed banner: the author is absent from `recipientPeerIds`, which is the relay's retrieval ACL (`inbox.go:1877`), so the relay refuses them the envelope, and even a served copy would be rejected by the drain's entitlement verifier (`drain_group_offline_inbox_use_case.dart:931` → `group_offline_replay_envelope.dart:577-581`, `recipient_not_entitled`). **The reaction never reaches the author at all** — which is also why the fix must widen custody, not merely the wake list. The relay's fan-out silently declines the empty wake (`go-relay-server/inbox.go:1528`), and because the retry lane replays the **byte-frozen** `inboxRetryPayload` verbatim (`retry_failed_group_inbox_stores_use_case.dart:361`) and a re-store of the same `transitionId` short-circuits as a Duplicate *above* the reaction branch (`inbox.go:1501-1503`, dedupe key = transitionId per `:1112-1117`), **the wake decision happens exactly once per transition and the empty nomination is permanent**. Window: from message render until the author's roster row lands — unbounded in time.
**Review constraint (blocker R1, resolved in this v2):** "no roster row" is also the exact **post-removal** state — member removal hard-deletes the row (`group_message_listener_system_transition_processor.dart:1936/:2385/:3706` → `group_repository_impl.dart:1173-1181` → `group_members_db_helpers.dart:192-196`) while the removed member's messages survive and stay reactable, and removal does **not** reliably rotate the group key (creator-gated best-effort). An unguarded fallback would therefore grant a REMOVED ex-member the five ACL verbs plus a wake. The fallback is gated on the removed-member snapshot (see Step 2 / TC-15).

**F2 — An empty replay recipient set becomes a silent false success (`stored`) that nothing ever retries — via THREE store paths.**
The envelope builder *omits* `recipientPeerIds` when the set is empty (`group_offline_replay_envelope.dart:224-225`). With a cached group config, the Go bridge then returns **success without calling the relay** (`go-mknoon/node/group_inbox.go:190-192 — if len(recipientPeerIds) == 0 { return nil }`, no log, no error); `_attemptReactionInboxStore` therefore marks the outbox row **`stored`** (`send_group_reaction_use_case.dart:486-492`), and the retry loader selects only `delivery_status IN ('pending','failed')` (`group_reaction_replay_outbox_db_helpers.dart:128-133`) — terminal, invisible. Without a cached config the empty list reaches the relay, which rejects it (`inbox.go:2189-2190` / `:1448`), marking the row `failed` — which then retries the same frozen empty payload forever. **The three store paths are: the stage attempt (`:384`), the `exactRetry` re-tap (`:189-198`, which bypasses staging entirely and re-drives the frozen payload — review blocker R2), and the resume/periodic retrier (`retry_failed_group_inbox_stores_use_case.dart:361`).** Any guard must therefore live at the shared choke point (`_attemptReactionInboxStore`) plus the retrier, or a same-emoji re-tap converts a loud `failed` back into a false `stored`. **The repo's flagship custody test (EK004, `send_group_reaction_use_case_test.dart:912`) is green on exactly this dropped shape**: its fixture roster never contains the target author, its stored envelope has an empty replay set and empty nomination, and its assertion helper never inspects recipients (`:38-54`).

**F4 — Every decline on the relay's reaction wake path is unobservable, and even successes are unattributed.**
Complete branch census (workflow, verified at HEAD): handler rejections ×5 (`inbox.go:2185-2204`), `store()` empty-recipients (`:1448`), the Duplicate short-circuit (`:1501`), the `!valid` conflation — ~15 distinct rejection sites in `extractGroupReactionPushMetadata` collapsing into one silent return (`:1507`, comment at `:1505` names the conflation), flag-off (same branch), the **empty-nomination return** (`:1528`), and the **per-recipient capability skip** (`:1532-1534`) — which also renders the existing `group_reaction_incapable` counter (`:206`) unreachable dead code, since `:1536` is its only production caller and the fan-out pre-filter `continue`s first. A *successful* reaction push logs only the generic `[PUSH] Notification sent` line (every attribution branch tests `pushKind == "group"` exactly, `:277/:340`) and shares the un-labeled `success` counter (`:276`). There is not one reaction-attributed journal line anywhere on the ingress→push path (only the one-shot startup flag line, `main.go:110`).
**Review constraint:** the literal string `[PUSH] Notification sent to` is a **load-bearing device-lane artifact contract** — the criteria validator counts exact occurrences of that substring (`group_reaction_notification_device_criteria.dart:1795-1806`, `:1977-1979`). New reaction-attributed lines must therefore use a distinct prefix and never contain that substring (see Must preserve).

**F5 (fact shaping the fix, not separately fixed here) — the wake decision is once-per-transitionId.** Any fix must make the nomination correct **at first store**; client-side retries can never rescue a missed wake (see F1's Duplicate mechanics). The only F5-compatible recovery for an unroutable row is **retirement**: delete it so a later re-tap mints a fresh transition with recomputed recipients (idempotent at receivers via the deterministic reaction id, `:143-148/:276-291`). Changing duplicate semantics is deliberately out of scope (see Deferred).

**F6 — Coverage/lane gaps:** no test at any tier pins a *non-empty* nomination for a cross-phone reaction; no self-reaction test exists; no Go test supplies an empty nomination or asserts any `pushSentCounter` label; **zero group-reaction relay tests are reachable from the `groups` gate** (filter `^TestRelayNotificationClosure_`, `run_test_gates.sh:1038`, matches only 8 functions, all in `push_payload_closure_test.go`); and every Android device-lane reaction scenario **kills the recipient process before the reaction is sent** (`capture_group_reaction_notification_device.dart:2008/:2611-2636`; criteria require `pid_absent_before_delivery=true`, `group_reaction_notification_device_criteria.dart:390/:469`) — no tier exercises a backgrounded-but-connected recipient, the exact topology of the 2026-07-31 user test.
