## Problem And Evidence

- Behavior to improve: a newly authored ordinary 1:1 image, video, GIF, audio/voice, file, captioned-media, quoted-media, forwarded-media, or multi-attachment message must retain the exact encrypted initial event locally until a Plan 344 ACK-or-expiry relay accepts it, independent of direct-send success, node state, app restart, or the retry entry point.
- Impact: current media can reach direct transport or generic relay storage while no immutable sender-owned row exists. A live ACK, crash, generic `OK`, or legacy capacity eviction can therefore erase or falsely settle the only initial-event obligation, contrary to PRD §5 requirements 1 and 3 and GAP-N01.
- Confirmed current gap: `ownsDirectTextInboxCustody` explicitly requires `!hasAttachments` at `lib/features/conversation/application/send_chat_message_use_case.dart:550-555`; media instead enters `stageOutgoingOrdinaryAttemptWithMedia` at `:809-888` and generic detailed/bool storage at `:1118-1168`. Only the text branch creates/completes/retains a v108 handle at `:906-940`, `:1028-1086`, and `:1170-1186`.
- Confirmed producer shape: ordinary composer media is pre-saved before upload and reaches `sendChatMessage` with `preassignedMessageIdIsFresh == false` (`lib/features/conversation/presentation/screens/conversation_wired.dart:3372-3429,3782-3799`). Voice similarly pre-saves a `sending` parent and `upload_pending` attachment, then omits the freshness flag (`:4775-4813,4926-4943`; `send_voice_message_use_case.dart:188-206`). External direct share is the separate no-predecessor case (`lib/features/share/application/share_batch_delivery_coordinator.dart:1240-1319`).
- Confirmed atomic seam: `dbStageOutgoingOrdinaryAttemptWithMedia` already commits the parent/envelope CAS and exact direct-owned attachment projection together (`lib/core/database/helpers/media_attachments_db_helpers.dart:868-1071`); `MediaAttachmentRepositoryImpl.stageOutgoingOrdinaryAttemptWithMedia` wraps it in the global attachment lifecycle lock and compensates secure-key writes (`lib/features/conversation/data/repositories/media_attachment_repository_impl.dart:1899-2000`). The v108 table stores recipient, message, incarnation, and opaque envelope only (`lib/core/database/migrations/108_direct_inbox_custody_outbox.dart:23-46`), so final media custody needs no media column or second outbox.
- Confirmed provenance ambiguity: `retry_incomplete_uploads_use_case.dart:472-524` deliberately clears an old ordinary envelope when a re-upload rotates key/nonce. After a crash, that legacy/re-keyed row and a never-authored fresh prepared row can both be `sending|failed`, ordinary, and `wire_envelope == null`. A caller flag or state-derived null check cannot prove that minting a new initial-event custody incarnation is safe.
- Confirmed preparation ambiguity: composer persists the parent before sequential attachment rows (`conversation_wired.dart:3383-3429,5709-5730`). A random intent plus the current surviving projection could mistake a one-of-two partial save for the authored whole; the local token therefore has to bind the message ID and canonical full authored attachment-ID set. This preserves crash evidence without redesigning upload preparation into another cross-store transaction.
- Confirmed transition hazard: generic `dbInsertMessage` replaces an existing row from the caller map (`lib/core/database/helpers/messages_db_helpers.dart:26-32,84-88`). Unless v110 changes that field's update discipline, a delayed stale save can erase a pending intent or restore one after custody consumed it. `ConversationMessage` equality is intentionally ID-only (`conversation_message.dart:325-332`) and must remain so.
- Confirmed bypasses: `retry_unacked_messages_use_case.dart:225-267` stores every sent envelope through the legacy bool API without consulting v108. `retry_failed_messages_use_case.dart:442-485` correctly checks v108 first, but its no-outbox media rebuild stays generic. Incomplete upload can rotate keys and rebuild (`retry_incomplete_uploads_use_case.dart:641-696`). These paths must distinguish a persisted fresh intent, an existing v108 owner, and a historical/no-intent row.
- Existing coverage: Plans 342-344 prove v108 exact-envelope CAS/drain, status-independent lifecycle cadence, live-ACK non-cancellation, `ack_or_expiry_v1` receipt parsing, non-destructive protected capacity, mixed-version relay behavior, and Android SQLCipher v108/v109 reopen. Existing ordinary media tests prove encrypted attachment validation, exact media projection, secure-key compensation, voice upload, incomplete-upload recovery, and external share.
- Missing coverage: no test proves durable manifest-bound fresh-media provenance, insert-once/consume-only token transitions, one-transaction parent + exact attachments + v108 insertion, competing-finalizer winner adoption, strict media store outcomes, stopped-node media custody, retry-unacked suppression, transaction-bound key-rotation refusal after custody, production composition, outbox-only account-transfer continuity, the one-way v110 schema floor, or v109-to-v110 SQLCipher migration.
- Refuted findings: setting `preassignedMessageIdIsFresh = true` for media is not sufficient because the durable parent already exists; routing through `stageOutgoingDirectTextInboxCustody` is invalid because it intentionally rejects `staged.media`; adding a new relay action/kind, outbox table, scheduler, platform binding, receiver model, or blob protocol is not required for the encrypted initial `chat_message` envelope.
- Unresolved/accepted difference: Plan 345 protects the authenticated message envelope and its attachment descriptors, not the separately uploaded relay blob. The relay media store still has independent TTL/capacity/overwrite behavior (`go-relay-server/media.go`); end-to-end blob retention is a distinct GAP-N01 follow-up and is not silently claimed here. Plan 344 admission also remains default-off pending its S2 operational gates.
- Affected production, test, and gate files: DB v110 version/registry/migration and `ConversationMessage`; direct-inbox/message/media DB helpers; message/media repository contracts and implementations; production bootstrap; send/composer/voice/share and three retry paths; focused migration/repository/application/widget/account-transfer/device tests; the two 1:1 migration arrays, reliability discovery label/contract, and allowlisted current-version pins.

## Scope Contract And Guard

In scope:

- Add DB v110 nullable `messages.direct_media_custody_intent_id` (exact 32-character lowercase hex) with no historical backfill or index. One pure shared helper computes lowercase hex of the first 16 bytes of SHA-256 over UTF-8 `jsonEncode(['direct_media_custody_v1', messageId, ...sortedUniqueAttachmentIds])`; the array length and ordered string encoding bind the complete authored ID set without ambiguous concatenation. Prepared composer/voice producers and the DB authority reuse that helper. The token proves the intended manifest, not upload completion or content bytes. External share remains the legitimate insert-fresh/no-predecessor case and receives a new random outbox incarnation only inside final staging.
- Persist the local token through `ConversationMessage` constructor/fromMap/toMap/sentinel-aware copyWith and account transfer while preserving ID-only `==`/hashCode. Never put it in `MessagePayload`, a send-function argument, the encrypted event, relay/provider data, logs, or a remote message. `sendChatMessage` reloads it from the durable predecessor; the wire-derived staged message may carry null until the combined helper performs its one allowed exact token-clear transition.
- Make the token insert-once/consume-only. A true new-row `dbInsertMessage` may introduce it; every generic update preserves the current database value regardless of a stale caller's null/non-null value; only the exact combined custody transaction may clear it. For a prepared row that validated token becomes the local v108 incarnation; a no-parent fresh stage generates a random 32-hex incarnation inside the transaction. A non-null token is exclusive authority: generic ordinary, edit, old media-only, and text-v108 staging must reject it, while no-token legacy behavior remains unchanged.
- Add one narrow optional combined-media-custody staging capability on `MediaAttachmentRepository`. Under the existing exclusive lifecycle lock, one SQLCipher transaction must: revalidate either an absent fresh parent or the exact durable manifest-bound prepared predecessor; validate the outer direct-chat-v2 envelope; bind the parent and complete direct-owned attachment set; stage the exact encrypted envelope; insert/adopt the v108 outbox row; and consume the token. Pre-commit refusal/exception restores secure-key snapshots and leaves every DB projection unchanged. After commit, hydrate/cache/stream publication is best effort: failure retains keys, envelope, attachments, and outbox and returns the committed authority rather than compensating it.
- Follow the already-used reaction-custody result shape with one narrow media result carrying outcome, committed message projection, and exact `DirectInboxCustodyOutboxEntry`. The storage helper returns the exact row from the transaction, so no racy post-commit lookup or reconstruction is needed and a competing finalizer can return the winner's bytes/incarnation. Do not widen generic `OutgoingOrdinaryMutationResult` or alter the v108 row model.
- Accept a prepared predecessor only when it is outgoing to the exact recipient/from the current sender, action `send`, ordinary policy v0/mode ordinary, `sending|failed`, manifest digest exact, `wire_envelope/transport/relay_expires_at/custody_checked_at` null, and edit/delete/hide/private lifecycle fields absent. The current DB attachment projection must contain every digest member and no other row; missing, deleted, duplicate, or added rows refuse and are never reinserted from caller candidates. Each row is direct-owned, bound to the message, non-transient, and either already exact `done` or the narrowly allowed exact `upload_pending` -> final `done` transition for the same voice/media ID, parent, and owner, with complete outbound encryption/hash metadata. The DB helper, not the caller predicate or `hasAttachments`, is final authority.
- Validate the combined helper's outer bytes with the existing shared direct-chat-v2 discriminator: exact type/version/message/sender and encrypted shape, no `eventId`; wrong edit identity or malformed outer bytes leave zero mutation. Two finalizers that encrypted different bytes for the same prepared token race safely: the winner commits once, and the loser reloads/adopts/drains that exact existing v108 entry without generic fallback, failed status, or a second incarnation.
- Reuse `direct_inbox_custody_outbox`, `DirectInboxCustodyOutboxEntry`, its fair drain/completion, and `AckCustodyKind.directTextV108`. Document and test that the frozen wire value `direct_text_v108` is a compatibility label for DB-v108 initial direct `chat_message` custody, including ordinary media hidden inside ciphertext. Do not rename the wire value or require a new persisted kind: installed Plan 344 binaries must be able to drain the same row.
- Generalize only send-path local naming/eligibility needed to treat fresh ordinary media as v108-owned. Before envelope encryption, reload the durable parent and current direct-owned attachments through existing lookup seams and reject a token/manifest mismatch or missing capability; exact custody then commits immediately after serialization and before stopped-node exit or any initial chat-envelope direct-send/inbox-store call. The transaction revalidates to close a change after preflight. Encrypted blob preparation/upload and voice LAN blob transfer necessarily precede that boundary and are not called event egress. Eligible media fails closed if the combined staging, v108 completion, or strict ACK-or-expiry capability is absent. Only exact `ackOrExpiryAccepted` completes/removes; live ACK, generic `stored|duplicate`, missing proof, full, timeout, throw, or local-completion failure retains the row.
- Reuse the existing lifecycle drain rather than add a worker/timer. Failed retry must drain an existing v108 row before attachment rebuild/upload/encryption. Incomplete-upload and generic-unacked paths skip/reject any message already owned by v108; the outbox-absence predicate belongs inside the same DB transaction as envelope invalidation/key rotation so a pre-check cannot race custody. A token-bearing crash-resumed preparation with the exact complete manifest may finish upload then acquire custody once; missing/partial/mismatched token-bearing preparations remain dormant and fail closed; historical/no-token rows remain on their legacy path and are not backfilled.
- Cover fresh ordinary image/video/GIF/audio/voice/file, textless and captioned media, quote/forward metadata, and a multi-attachment exact set. `media` describes the encrypted inner event only; relay validators continue to authenticate the exact outer v2 chat shape and sender.

Freshness/ownership truth table:

| Durable state at final send | Plan 345 authority | Required result |
|---|---|---|
| No message row, action `send`, ordinary complete media | Insert-fresh combined stage | Atomically insert message + attachments + v108 row; generated incarnation becomes sole local envelope owner. |
| Exact outgoing ordinary `sending|failed` row with matching manifest-bound intent, null envelope, and full authored attachment-ID projection | Prepared-fresh combined stage | CAS all inputs, consume token, insert v108 row in one transaction. |
| Manifest-bound intent exists, but a member is missing/incomplete/deleted, an extra member exists, or identity/metadata differs | Exclusive fail-closed preparation | Preserve token/current rows; zero token consumption, encryption, event egress, generic/text/media staging, or v108 insert. |
| Exact v108 row already exists, including after the parent/media was user-deleted | Existing v108 drain/replay | Replay only stored envelope bytes; no upload, key rotation, re-encryption, generic store, or second incarnation. A competing finalizer adopts the winner. |
| Existing row has an envelope but no v108 row | Legacy retry | Do not mint Plan 345 custody or change existing generic retry semantics. |
| Existing row is null-envelope but has no fresh-media intent | Historical/ambiguous legacy | Do not infer freshness and do not backfill; retain current retry behavior. |
| Private/protected/view-once/disappearing, edit/delete, incoming, or group | Excluded | No token mint/consumption, v108 insert, or strict media custody call. |

Hard `Do not`:

- Do not add a second direct-media outbox, new ACK-custody action/kind/contract, Go/relay/native/binding change, new scheduler, backfill, content hash protocol, recipient notification model, or provider payload change.
- Do not claim durable media-blob availability, private/disappearing media custody, edits/deletes, group custody, every-device fanout, presentation outcomes, Plan 344 production activation, or standalone release eligibility.
- Do not trust `preassignedMessageIdIsFresh`, a null envelope, status, timestamp, attachment presence, or UI memory as durable prepared-fresh proof.
- Do not split parent, attachment, intent consumption, and outbox insertion across transactions; do not call bridge, secure storage, cache publication, or filesystem operations from inside the SQL transaction.
- Do not let a generic save erase/re-arm a token, let a token-bearing row enter any sibling staging seam, reconstruct a missing authored attachment from a caller candidate, or compensate keys after custody committed.
- Do not let live ACK, generic relay success, attachment cleanup, cancellation, re-upload, or message deletion delete a non-exact v108 incarnation.
- Do not describe reinstalling a v109 binary as rollback after v110 opens a profile. The supported rollback is a forward-fix v110+ binary or explicit profile reset/restore; Plan 344's relay flag rollback cannot reverse the local schema floor.
- Do not require an iPhone, iOS simulator, unavailable OS/API band, or two-peer harness for this non-iOS SQLCipher/storage slice.

Deferred / accepted difference:

- Direct protected/view-once/disappearing media initial-event custody -> later GAP-N01 slice, because it has separate private lifecycle and reveal/cleanup authority.
- Direct edit/delete, group events, and per-device fanout -> later WP-01/GAP-N01 slices.
- Relay media-blob non-destructive retention/identity/replication -> dedicated GAP-N01 follow-up before claiming end-to-end media retrievability.
- Pre-envelope preparation atomicity -> accepted baseline. Composer/voice can recover only when the manifest-bound parent and required upload-preparation rows already exist; a crash during their sequential preparation may leave a dormant partial intent. Marker-free external share remains unrecoverable if the process dies before final combined staging. Plan 345's restart guarantee begins when exact custody commits, not when blob preparation starts.
- Opaque provider wake, outcome ledger, and presentation arbitration -> GAP-N02/N03; consolidated Apple runtime evidence -> GAP-N12 after the Android-first dependency wave.
- Plan 344 S2/S3 Redis activation, restart/restore, rollback artifact, thresholds, and legacy retirement -> its existing operations owner.

Dependencies:

- Plan 342 supplies the v108 local row/drain/completion; Plan 344 supplies exact `ack_or_expiry_v1` protected acceptance. Plan 345 may be code-closed while admission is off, but it cannot ship independently of Plan 344's relay-first S2 activation and the GAP-N01/N02/N03 release wave.

## Risks And Blind Spots

- False freshness after key rotation could create a second event under the same message ID -> DB v110 token is minted only at new local preparation, is exact-CAS consumed, and legacy invalidation checks v108 absence in the same transaction and never creates a token (TC-345-01/02b/07).
- A partial two-item preparation could be mistaken for the authored whole -> the token binds message ID/count/canonical full ID set, the combined transaction requires that exact current projection, and partial/deleted/added states remain dormant (TC-345-02/05/07).
- A stale generic writer could erase or re-arm custody authority -> insert-only introduction, DB-preserving generic updates, combined-only clear, and crossed-save barriers lock the state machine (TC-345-02b/09).
- A split transaction or secure-key side effect could leave an envelope referencing a crossed/missing key or attachment -> one DB transaction under the media lifecycle lock plus pre-commit compensation/failpoint proof; post-commit publication failure deliberately retains keys/outbox (TC-345-02/11).
- Competing finalizers could encrypt different bytes -> one manifest token/incarnation wins atomically and every loser adopts/drains the committed entry rather than minting or failing the message (TC-345-02b/03).
- Generic retry could falsely settle protected custody -> outbox-first guards in failed/incomplete/unacked paths and sibling-progress assertions (TC-345-07/08).
- Lifecycle / derived-state durability: the token, exact attachments, and outbox are reloaded after process recreation, account transfer, and encrypted DB reopen, while the pre-stage partial-preparation limitation stays explicit (TC-345-05/07/10/11).
- Sibling-surface consistency: composer, voice, external share, failed retry, incomplete retry, and generic unacked entry points have named causal rows; private/disappearing/edit/delete/group siblings are named exclusions (TC-345-05 through 09).
- Destructive-action side effects: exact completion may advance/remove the message projection but never removes media files/rows; user deletion may remove the message while the independent v108 row remains exact-completable; rollback and key/file preservation are asserted in TC-345-02/04/07.
- Invariant re-verification under new transitions: retry, resume, marker consumption, exact replay, key rotation, transfer, and reopen all re-check recipient/message/incarnation/envelope/attachment identity instead of trusting prior in-memory qualification (TC-345-02/07/10/11).
- Schema rollback is asymmetric: once v110 opens a profile, Plan 344's relay flag can roll back service admission but a v109 app binary cannot open that profile; forward-fix or explicit reset/restore is the only supported recovery (TC-345-01/11).
- Relay protected envelope can outlive or point at an evicted/expired blob -> explicitly deferred blob-retention owner; Plan 345's status and coverage wording may claim initial-event custody only.
- Plan 344 feature-family concurrency 2 exposed unrelated load-sensitive group UI failures -> use the complete stable serial feature-family gate for this plan and treat any exact focused failure as scope evidence, not as the old harness caveat.
