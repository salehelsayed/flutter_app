## Problem And Evidence

- Behavior to improve: direct, group and announcement surfaces need a durable, paged media source plus local bookmark and video-resume state without mixing conversations or transport lanes.
- Impact: HEAD can hydrate attachments only after loading message rows, so it cannot efficiently build Shared Media, stable cross-message swipe, batch selection, or durable bookmark/resume behavior.
- Confirmed current mechanism: `messages.id` and `group_messages.id` are independent table primary keys (`lib/core/database/migrations/002_messages_table.dart:7`, `lib/core/database/migrations/018_group_messages_tables.dart:18`), while `media_attachments` stores only `message_id` (`lib/core/database/migrations/010_media_attachments.dart:18`). The same parent ID can therefore match both lanes.
- Confirmed current gap: `MediaAttachmentRepository` and media DB helpers load/delete by untyped `message_id` (`lib/features/conversation/domain/repositories/media_attachment_repository.dart:11`, `lib/core/database/helpers/media_attachments_db_helpers.dart:41`, `:230`). A direct/group same-ID collision can cross-read or cross-delete attachments.
- Confirmed replay gap: `dbInsertMediaAttachment` uses `ConflictAlgorithm.replace` (`lib/core/database/helpers/media_attachments_db_helpers.dart:19`), while `_preserveCompletedLocalPathIfNeeded` preserves only `localPath` and completed download status (`lib/features/conversation/domain/repositories/media_attachment_repository_impl.dart:282`). A normal replay would overwrite bookmark/resume defaults.
- Confirmed visibility gap: the direct visible-row predicate checks `hidden_at IS NULL` but not `deleted_at IS NULL` (`lib/core/database/helpers/messages_db_helpers.dart:5`); group deletion records a durable tombstone and deletes the parent (`lib/core/database/helpers/group_messages_db_helpers.dart:739`).
- Confirmed migration-test gap: production runs migrations 092-095 in both create/upgrade paths (`lib/main.dart:595`, `:885`), but `full_migration_chain_test.dart` imports/runs only through 091 (`test/core/database/integration/full_migration_chain_test.dart:67`, `:197`). Its hand-maintained helper is not the production registry.
- Confirmed downgrade gap: `openEncryptedDatabase` passes no `onDowngrade` callback (`lib/core/database/encrypted_db_opener.dart:96`, `:250`). Pinned `sqflite_common` 2.5.6 lowers `user_version` even when no downgrade callback runs; a pre-v96 model then omits the new local columns and its `INSERT OR REPLACE` can reset them to defaults. Application code added in v96 cannot retrofit an already-built v95 binary.
- Confirmed destructive/retry bypasses: contact cleanup, message terminalization, global upload-pending loads and both incomplete-upload retriers operate by untyped `message_id` (`lib/core/database/helpers/media_attachments_db_helpers.dart:265`, `:301`, `:345`; `lib/features/conversation/application/retry_incomplete_uploads_use_case.dart:77`; `lib/features/groups/application/retry_incomplete_group_uploads_use_case.dart:100`). A same-ID sibling can be deleted, terminalized or retried through the wrong lane.
- Confirmed secure-key ordering gap: repository serialization writes the attachment key to the attachment-ID-only secure-store name before the database insert/re-parent rejection (`lib/features/conversation/domain/repositories/media_attachment_repository_impl.dart:265`; `lib/core/secure_storage/secret_storage_references.dart:12`). A rejected cross-owner save can leave the original row hydrating the incoming key.
- Confirmed custom-fixture gap: `integration_test/group_multi_device_real_harness.dart` and `integration_test/smoke_test.dart` own old encrypted schemas and instantiate `MediaAttachmentRepositoryImpl`. The cited `transport_e2e_test.dart` v79 opener is not a causal missing-column example at HEAD because that test does not instantiate or pass the real media repository.
- Existing coverage: media helper/repository tests cover untyped per-message hydration and completed-local-path preservation; migration 010 covers the old schema. These are preservation sentinels, not owner-lane, replay-state, scoped-library or current-registry proof.
- Missing coverage: exact ordered v95 registries, deterministic owner backfill, enforced owner CHECK, ambiguous/orphan fail-closed behavior, required owner propagation, destructive/retry collision bypasses, pre-side-effect re-parent rejection, replay-safe local state, actual deletion workflows, scope/filter-bound cursors, a literal page ceiling, unknown-duration/non-video playback, aliased mapping, exact indexes, fail-closed downgrade, current-schema real-repository fixtures, physical-device identity, SQLCipher capability/wrong-password failure, and exact discovery classification.
- Refuted findings: the previous claim that message IDs are globally unique across direct and group tables is false. A shared table remains valid only with a local owner-lane discriminator and owner-aware APIs.
- Unresolved findings: N/A — this plan fixes owner identity locally and does not change wire, relay or go-libp2p behavior.
- Affected production, test and gate files: migration 096; DB version; encrypted opener downgrade policy; extracted target-version-aware production create/upgrade migration registry used by `main.dart` and current-schema test fixtures; `MediaAttachment` local map/copy paths; media DB helpers/repository and all direct/group media write/read/delete/retry callers; scoped library types; migration/helper/repository/application/full-chain tests; SQLCipher proof; physical-device guard; discovery classification.

## Scope Contract And Guard

In scope:
- DB v96 adds `owner_lane TEXT NOT NULL DEFAULT 'unresolved'` constrained to `direct`, `group`, or `unresolved`, plus `is_bookmarked INTEGER NOT NULL DEFAULT 0` and `last_playback_position_ms INTEGER NOT NULL DEFAULT 0`.
- DB v96 is a one-way supported release floor. The v96+ encrypted opener passes `onDowngrade: onDatabaseVersionChangeError` (or an equivalent fail-closed callback), and supported distribution must not install or run a pre-v96 build over a profile already opened at v96. A manually sideloaded pre-v96 binary is unsupported and requires profile reset/restore; it must never be represented as a compatible rollback.
- Migration 096 backfills `direct` only when a parent exists solely in `messages`, `group` only when it exists solely in `group_messages`, and leaves rows `unresolved` when both or neither parent exists. `unresolved` rows are retained but excluded from direct/group reads and mutations.
- Add and assert exact indexes `idx_media_attachments_owner_message(owner_lane, message_id)` and `idx_media_attachments_owner_bookmark_message(owner_lane, is_bookmarked, message_id)`.
- Introduce a local `MediaOwnerLane.direct/group` contract. Every direct/group attachment save, replay, per-message and multi-message load, upload-pending load, retry re-read/save, pending/failure transition, contact cleanup and message-scoped delete must carry or derive an explicit owner. Owner filtering occurs in SQL before ordering/`LIMIT`; no default-to-direct/group inference or post-query Dart filtering by `message_id` is allowed. Announcement conversations use `group` because their stored parents are group messages.
- Ordinary attachment replay/re-save must preserve existing local-only owner, bookmark, playback and completed-local-path state atomically while allowing transport metadata to update. A save may not silently re-parent an existing attachment ID to another owner lane. Explicit bookmark/playback APIs remain able to clear their own state.
- Before `_toStorageRow` or any secure-store/file/database side effect, a save of an existing attachment ID validates the immutable `(attachmentId, ownerLane, messageId)` identity. A rejected cross-owner/cross-parent save leaves the existing DB row, secure-store reference/value and decryptability unchanged; database enforcement remains the final race guard.
- Add a shared `MediaLibraryRepository` capability implemented by `MediaAttachmentRepositoryImpl` and page visual media for `direct(contactPeerId)` and `group(groupId)` scopes.
- Direct queries require `owner_lane='direct'`, the named contact, `hidden_at IS NULL`, and `deleted_at IS NULL`. Group queries require `owner_lane='group'`, a live parent in the named group, and no matching durable local-deletion tombstone.
- Generic parent DB helpers remain non-cascading: if cleanup is absent or best-effort cleanup fails, retained attachment rows become invisible through parent/tombstone predicates. This is not a product-visible retention change. Direct `deleteMessageForMe` continues its existing explicit direct-owned attachment/file cleanup before parent deletion; the current group failed-media deletion workflow continues explicit group-owned cleanup. Both real workflows preserve same-ID sibling lanes and unresolved legacy rows. New journaled group/announcement received-delete semantics remain owned by plans 235/239.
- Every selected parent/attachment column has an explicit SQL alias consumed by mapping code; no unqualified duplicate `id`, `created_at`, or timestamp field is mapped.
- Stable newest-first keyset pagination orders by `(parentTimestamp DESC, messageId DESC, attachmentId DESC)`. The opaque cursor also embeds scope kind/id and the complete filter signature; reuse with another scope/filter fails with a typed argument error before SQL.
- `kMediaLibraryMaxPageSize = 100`; valid limits are `1..100`, and invalid limits fail before SQL. Filters are image, video, both and bookmarked-only combinations.
- Bookmark writes apply to image/video attachments. Playback writes reject non-video attachments; known-duration video positions clamp to `0..duration`; unknown-duration videos store a non-negative position and re-clamp when a later replay supplies duration; completion resets position to zero.

Must preserve:
- Encryption metadata remains hydrated through the existing secure-store path -> TC-228-12.
- `MediaAttachment.toJson` remains wire-only and omits owner/bookmark/playback state -> TC-228-03.
- Existing direct/group send, receive, download and retry paths retain their media behavior while supplying the correct local owner -> TC-228-04.
- Per-message ordering, completed local paths, download/retry transitions, pending queries, contact cleanup, manual retry and stale-pending cleanup remain functional under owner-aware signatures -> TC-228-04/05B/08 and existing media helper/repository sentinels.
- Existing direct `deleteMessageForMe` attachment and owned-file cleanup remains intact; helper-only/tombstone deletion may retain hidden orphan rows after best-effort cleanup failure -> TC-228-11/11W.
- Announcements continue to use group storage and authorization; no third transport lane is introduced -> TC-228-04 plus plan 241 UI ownership.

Hard `Do not`:
- Do not add owner/bookmark/resume fields to direct, group or announcement encrypted payloads.
- Do not infer owner from a parent-ID existence check during ordinary writes; existence checks are migration-only because collisions are legal.
- Do not expose `unresolved` legacy rows through a direct/group library or owner-scoped mutation.
- Do not change message delivery, group permissions, announcement policy, relay retention, media encryption, go-libp2p, or download-status policy.
- Do not preload unbounded history, use offset pagination, accept a cursor from another query signature, or accept a page limit above 100.
- Do not cascade parent deletion inside the generic message DB helpers as part of this plan.
- Do not claim or test pre-v96 binary rollback compatibility. If supported downgrade is required, stop and replan cross-version storage plus actual-old-binary proof instead of weakening the release floor.

Deferred / accepted difference:
- Gallery UI, batch actions, Go to message, and viewer-list wiring -> plans 233, 237 and 241.
- Bookmark sync across a user's devices -> future multi-device local-state plan; no wire contract exists.
- Cache eviction/download controls -> plan 229; advanced player UI -> plan 230.
- Resolving legacy rows whose parent is both absent and ambiguous -> future recovery tooling; v96 deliberately retains them as `unresolved` and fail-closed.

Dependencies:
- DB v95 at HEAD; this plan exclusively reserves DB v96 and stops if another accepted change claims it.
- Production create/upgrade migration sequences must first be extracted into one shared registry used by both `main.dart` and tests without changing the existing order through v95.
- The shared migration registry must be target-version-aware so tests can literally create v95 through the production create callback, then reopen through the production v96 upgrade callback. Its manifest locks the exact existing ordered create/upgrade sequences and their intentional differences through v95, rather than assuming numeric order.
- Attachment IDs remain the table's global row identity; ordinary saves must reject an attempted cross-owner re-parent instead of replacing it.
- Current-schema encrypted fixtures that instantiate `MediaAttachmentRepositoryImpl` or persist `MediaAttachment.toMap()` use the shared registry/current v96 schema. Specifically, `group_multi_device_real_harness.dart` and `smoke_test.dart` move off their hand-maintained v79/v11 callbacks. `test_db_seeder.dart` exposes a current-production v96 opener separately from any explicitly versioned historical seeder. Historical fixtures may not write the v96 model.
